# 10 · 微服务拆分的决策框架

> **阶段**：架构演进 / 服务治理
> **痛点**：拆完之后每个服务都能独立部署，但改一个字段要发 6 个服务；调用链从 1 跳变成 7 跳，P99 从 80ms 涨到 900ms；出了故障没人能说清边界在哪。

---

## 1. 真实故障场景

### 场景 A：拆了 12 个服务，共享 1 个数据库

```
order-service ─┐
pay-service   ─┼──▶ 同一个 MySQL 库（同一个 schema）
stock-service ─┘
```

表现：

- 订单表加一个字段，库存服务、支付服务的 XML 都要改（否则 `SELECT *` 反序列化失败）；
- 库存服务直接 join 订单表，**表结构变成事实上的公共 API**；
- DBA 改一个索引，要在 4 个团队的群里通知；
- 谁都能改库，出问题无法定位"谁写坏的"。

**这是"分布式单体"**：部署上分开了，数据与变更上完全耦合，付出了微服务的全部成本，没有获得任何收益。

### 场景 B：一次下单 7 次串行 RPC

```
Gateway → order → user → member → coupon → stock → price → promotion
```

每跳 5–15ms，串行累加 P99 达到 900ms；任何一跳抖动，整条链路超时。更糟的是**没有超时预算分配**：每一跳都设 3s 超时，理论上最坏要 21s，而用户 3 秒就走了。

### 场景 C：引入 Service Mesh 后，故障定位时间翻倍

某团队为了"统一治理"，给 40 个服务全部注入 Sidecar。结果：

- 每笔请求多 2 次代理转发，P99 增加 3–8ms；
- 排查网络问题时，`tcpdump` 看到的是 localhost 流量，真实链路要看 Sidecar 日志；
- Sidecar 版本升级要协调 40 个服务的发布窗口；
- 每个 Pod 多 100–200MB 内存，集群成本上涨 15%。

**收益（统一 mTLS、灰度、可观测）确实存在，但团队只有 3 个 SRE**。

### 场景 D：环形依赖

```
order → stock → promotion → order   （promotion 需要查订单判断是否首单）
```

启动时循环依赖、发布时必须同时上线、任何一方接口变更都可能引发对方故障。**这是拆分维度的错误，不是技术问题。**

---

## 2. 原理剖析

### 2.1 拆分的四个维度

| 维度 | 依据 | 优点 | 风险 |
|---|---|---|---|
| **业务能力** | 组织/业务流程（下单、支付、履约） | 与业务语言一致，沟通成本低 | 容易拆出"贫血服务"（只有 CRUD） |
| **DDD 子域/限界上下文** | 领域模型边界、聚合根 | 数据边界清晰，模型独立演进 | 需要真正的领域专家参与，成本高 |
| **变更频率** | 哪些代码总是一起改 | 减少联动发布 | 频率会变化，边界不稳定 |
| **团队边界（康威定律）** | 谁负责维护 | 权责清晰，减少协调 | 组织调整会导致架构扭曲 |

**实践中的组合判断**（按优先级）：

```
① 先看数据：这两块数据是否必须强一致（同一事务）？
   → 是：不要拆（或拆了也用同一个库 + 分布式事务，得不偿失）

② 再看变更：它们是否总是同时修改？
   → 是：不要拆（拆了就是"分布式单体"）

③ 再看团队：是否有独立的负责人与发布节奏？
   → 否：不要拆（没人负责的服务必然腐化）

④ 最后看规模：是否真的需要独立扩容？
   → 否：可以先用模块化单体（Modular Monolith）
```

### 2.2 康威定律的现实版本

> 系统的架构会不可避免地复制组织的沟通结构。

它的工程推论是：**如果你想得到某种架构，先调整组织结构**。反过来也一样——如果团队是一个 5 人小组，拆成 8 个微服务后，"每个服务一个 owner"必然落空，最终变成"谁有空谁改"，边界迅速腐化。

**因此拆分的现实约束是**：

```
服务数量 ≤ 团队可承载的运维能力
经验值：1 个服务 ≈ 0.5–1 人长期投入（含 on-call、容量、升级、故障处理）
```

一个 10 人团队，8–15 个服务是合理上限；超过这个数，要么加人，要么合并。

### 2.3 "分布式单体"的七个检测信号

| 信号 | 含义 |
|---|---|
| 多个服务共享数据库/schema | 数据未拆分 |
| 服务之间直接 join 或读对方表 | 边界形同虚设 |
| 一个需求要同时改 3 个以上服务并一起发布 | 变更未拆分 |
| 服务之间共享"公共实体类"jar | 模型未拆分，编译期耦合 |
| 任何服务故障都导致全站不可用 | 没有故障隔离 |
| 无法单独对某个服务做容量评估 | 调用关系不清晰 |
| 团队无法说清"这个服务负责什么、不负责什么" | 边界未定义 |

### 2.4 Spring Cloud Alibaba 落地组合（2026 视角）

| 能力 | 组件 | 说明 |
|---|---|---|
| 注册中心 + 配置中心 | **Nacos 2.x** | 一个组件两件事；配置支持灰度与监听 |
| 网关 | Spring Cloud Gateway | 路由、鉴权、限流（可对接 Sentinel） |
| 服务调用 | OpenFeign（HTTP）/ Dubbo 3（RPC） | 内部高频用 Dubbo（性能），对外/跨团队用 HTTP |
| 负载均衡 | Spring Cloud LoadBalancer | 替代已停更的 Ribbon |
| 流控降级 | **Sentinel** | QPS/线程数限流、熔断、系统自适应保护 |
| 分布式事务 | Seata | 见 09 篇 |
| 消息 | RocketMQ | 见 08 篇 |
| 链路追踪 | Micrometer Tracing + OTel / SkyWalking | 见 15 篇 |
| 分布式任务 | XXL-Job / SchedulerX | 定时任务统一调度 |

**版本矩阵要锁死**（这是升级时最大的坑）：

```xml
<properties>
  <spring-boot.version>3.3.x</spring-boot.version>
  <spring-cloud.version>2023.0.x</spring-cloud.version>
  <spring-cloud-alibaba.version>2023.0.3.x</spring-cloud-alibaba.version>
</properties>
```

Spring Cloud Alibaba 的版本必须与 Spring Boot 主版本对齐，**不要跨大版本混搭**（`2021.x` 的 Alibaba 组件跑在 Boot 3 上会出现 `javax`/`jakarta` 冲突）。

### 2.5 服务网格（Service Mesh）的成本模型

```
无 Mesh：     应用（含治理 SDK）──▶ 应用
              治理逻辑在进程内，SDK 与业务同生命周期

有 Mesh：     应用 ──▶ Sidecar ──▶ Sidecar ──▶ 应用
              治理逻辑下沉到 Sidecar（iptables 拦截流量）
```

| 维度 | 无 Mesh | 有 Mesh |
|---|---|---|
| 语言支持 | 仅 JVM（SDK 绑定） | **任意语言**（Sidecar 无关语言） |
| SDK 升级 | 每个服务改依赖、重新发布 | 只升级 Sidecar/控制面 |
| 延迟 | 无额外跳 | +1–2ms（P99 可能 +3–8ms） |
| 资源 | 无额外 | 每 Pod +100–200MB，+0.1–0.5 core |
| 排障 | 应用日志/APM | 需理解 iptables、Envoy 配置、xDS |
| 运维复杂度 | 中 | **高**（控制面、证书轮转、版本兼容） |

**引入时机判断**（建议同时满足 ≥3 条）：

```
□ 技术栈多语言（Java + Go + Python + Node），SDK 方案无法统一
□ 服务数量 > 30，且 SDK 版本碎片化严重（一次治理规则升级要半年）
□ 有强制的 mTLS / 零信任要求（合规驱动）
□ 有专职平台团队（≥2 人）能承担控制面运维
□ 现有 APM 无法满足流量可观测需求
```

**不满足时的替代方案**：统一 SDK + 服务框架（Spring Cloud Alibaba / Dubbo），加 API 网关做统一入口治理。**先用 SDK 把治理做对，再考虑下沉**——顺序反了会得到一个"又复杂又没治理好"的系统。

## 3. 工程解法

### 3.1 拆分评估矩阵（可直接用于评审）

对候选服务打分（1–5 分），总分 ≥ 18 才建议独立拆分：

| 维度 | 判断问题 | 权重 |
|---|---|---|
| 数据独立性 | 是否拥有独立的数据存储，且不需要与其他服务强一致？ | ×3 |
| 变更独立性 | 是否大部分需求只需改这一个服务？ | ×3 |
| 扩容独立性 | 是否有与其他服务不同的容量特征（如 CPU 密集 vs IO 密集）？ | ×2 |
| 团队归属 | 是否有明确的负责人与发布节奏？ | ×3 |
| 故障隔离价值 | 它挂掉时，是否应该不影响其他功能？ | ×2 |
| 复用价值 | 是否被 ≥2 个上游以相同语义调用？ | ×2 |
| 领域边界清晰度 | 是否有明确的聚合根与不变量？ | ×3 |

**反例打分**（一个"用户基本信息查询"服务）：

| 维度 | 分 | 理由 |
|---|---|---|
| 数据独立性 | 2 | 常与订单一起 join |
| 变更独立性 | 3 | 字段变更较少 |
| 扩容独立性 | 1 | 与主站同量级 |
| 团队归属 | 2 | 无专人 |
| 故障隔离 | 2 | 挂了全站不可用 |
| 复用价值 | 5 | 多处复用 |
| 领域边界 | 4 | 边界清晰 |
| **总分** | **19×权重后 ≈ 17** | **不建议拆**：应做成共享库/本地缓存，或留在主服务内 |

### 3.2 拆分的正确顺序：先数据，后服务

```
错误顺序：先按功能拆服务 → 服务之间共享库 → 后期再拆库（几乎不可能）
正确顺序：
  ① 定边界：画出领域模型与聚合，明确"谁拥有哪张表"
  ② 拆数据：把表的所有权收敛到单一服务（其他服务只能通过 API 访问）
  ③ 拆服务：把代码按数据边界移动（绞杀者模式逐步迁移）
  ④ 拆部署：独立流水线、独立扩容、独立 on-call
```

**表所有权规则**（写进架构规范）：

| 规则 | 说明 |
|---|---|
| 一张表只能有一个"写服务" | 其他服务只读，且只读视图/API，不直接连库 |
| 跨服务查询走 API 或冗余字段 | 禁止跨库 join |
| 每个服务独立 DB 账号，只有自己表的权限 | 用权限强制边界 |
| 共享表走"数据同步 + 本地副本" | 接受最终一致 |

### 3.3 绞杀者模式（Strangler Fig）：存量系统的渐进拆分

```
阶段1：新功能在新服务实现，老系统通过网关把新路径路由过去
阶段2：逐个把老功能"搬到"新服务（双写 + 比对 + 切流）
阶段3：老系统只剩空壳 → 下线
```

**关键工程手段**：

```yaml
# 网关层按比例切流（Spring Cloud Gateway + 权重路由）
routes:
  - id: order-new
    uri: lb://order-service-v2
    predicates: [ Path=/api/order/** ]
    metadata:
      weight: 10          # 10% 流量走新服务
  - id: order-old
    uri: lb://order-service-legacy
    predicates: [ Path=/api/order/** ]
    metadata:
      weight: 90
```

**双写比对的实现要点**：

- 双写要**异步**，不能拖慢主流程；
- 比对的是**结果**（响应体/最终状态），不是过程；
- 差异要有采样与告警，允许一定的不一致率（因为时序不同）；
- 切流粒度：先内部员工 → 再 1% 真实用户 → 10% → 50% → 100%，每档观察 ≥ 24h。

### 3.4 服务依赖治理：禁止环、控制深度

```java
// 用 ArchUnit 在 CI 中强制依赖规则（编译期拦截，比人工 review 可靠）
@AnalyzeClasses(packages = "com.example")
class ArchitectureTest {

    @ArchTest
    static final ArchRule no_cyclic_dependency =
        slices().matching("com.example.(*)..").should().beFreeOfCycles();

    @ArchTest
    static final ArchRule order_must_not_depend_on_promotion =
        noClasses().that().resideInAPackage("..order..")
            .should().dependOnClassesThat().resideInAPackage("..promotion..");

    @ArchTest
    static final ArchRule domain_must_not_depend_on_infra =
        noClasses().that().resideInAPackage("..domain..")
            .should().dependOnClassesThat().resideInAPackage("..infrastructure..");
}
```

**调用深度控制**：

| 深度 | 建议 |
|---|---|
| ≤ 3 跳 | 健康 |
| 4–5 跳 | 需要审查，考虑合并或异步化 |
| > 5 跳 | 必须重构（延迟累积 + 故障放大） |

**超时预算分配**（配合 11 篇）：

```
用户可接受 800ms
├─ 网关鉴权        20ms
├─ order 服务自身  50ms
├─ 下游调用预算    700ms，按扇出拆分：
│   ├─ 核心依赖（库存、价格）串行 2 跳 × 200ms
│   └─ 弱依赖（推荐、评价）并行 150ms，超时直接返回兜底
```

### 3.5 API 契约管理

| 实践 | 说明 |
|---|---|
| 契约先行 | OpenAPI / Protobuf 定义先合并，再写实现 |
| 向后兼容 | 只增不改不删；新增字段必须可选；废弃字段标 `@Deprecated` 并保留 ≥ 2 个版本 |
| 契约测试 | Consumer-Driven Contract（Pact）：消费方定义期望，提供方 CI 验证 |
| 版本策略 | URL 版本（`/v1/`）用于不兼容变更；内部服务优先做到"无需版本"的兼容演进 |

```java
// 兼容性检查的 CI 任务（使用 openapi-diff）
// 破坏性变更（删字段、改类型、加必填）→ 流水线失败
openapi-diff old.yaml new.yaml --fail-on-incompatible
```

## 4. 边界条件与反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 为拆而拆（"微服务是趋势"） | 支付全部成本，没有收益 | 用 3.1 的矩阵评估，达不到就不拆 |
| 按技术分层拆（controller 服务、service 服务） | 每次需求都要改 3 个服务 | 按业务能力/领域拆 |
| 共享数据库 | 数据耦合，边界失效 | 一表一主，跨服务走 API |
| 共享实体 jar | 编译期耦合，版本地狱 | 各自定义 DTO，用契约测试保证一致 |
| 服务数超过团队运维能力 | 无人负责的服务必然腐化 | 服务数 ≤ 团队可承载量，或用模块化单体 |
| 一开始就上 Service Mesh | 复杂度超过收益，排障能力不足 | 先用 SDK 治理，满足 5 条判据再下沉 |
| 同步调用链过深 | 延迟累积、故障放大 | ≤3 跳；深链路改异步/事件驱动 |
| 没有超时预算 | 每跳都等 3s，总超时不可控 | 自顶向下分配超时预算 |
| 拆分不做数据迁移方案 | 老数据无法归属，长期双库 | 绞杀者模式 + 双写比对 + 切流 |

## 5. 落地检查表

**拆分决策**

- [ ] 每个服务都能用一句话说清"负责什么、不负责什么"
- [ ] 通过拆分评估矩阵（≥18 分），评估记录留档
- [ ] 服务数量与团队规模匹配（有明确的 owner 与 on-call 安排）
- [ ] 已明确"不拆"的部分（模块化单体），并有内部模块边界约束

**数据边界**

- [ ] 每张表有唯一"写服务"，其他服务无写权限
- [ ] 无跨库 join，无服务直接读他人表
- [ ] 跨服务查询通过 API 或冗余字段（有同步机制与延迟说明）
- [ ] DB 账号按服务隔离，权限最小化

**依赖与调用**

- [ ] ArchUnit 在 CI 中强制：无环、无越界依赖、domain 不依赖 infra
- [ ] 调用深度 ≤ 3 跳（超过有评审记录）
- [ ] 每跳有超时，且有全局超时预算表
- [ ] 弱依赖（推荐、评价）异步或可降级

**演进**

- [ ] 存量系统有绞杀者迁移计划（分阶段、可回滚）
- [ ] 灰度切流有明确比例阶梯与观察窗口
- [ ] API 契约有兼容性检查（CI 拦截破坏性变更）
- [ ] 引入 Service Mesh 有明确的 5 条判据评估与成本测算

## 6. 三个追问

1. **为什么拆微服务，而不是继续用单体？**
   拆分的收益来自三处：**独立扩容**（不同模块容量特征差异大）、**独立发布**（变更频率差异大）、**故障隔离**（非核心模块不该拖垮核心）。如果这三点在你的系统里都不成立（模块容量相近、变更总是一起、故障本来就连带），那么单体的开发效率与排障便利性明显更高。**"模块化单体"（清晰的模块边界 + 单库事务）是被严重低估的选项。**

2. **引入它之后，运维成本由谁承担？**
   每个服务都是一份长期负债：独立的流水线、监控看板、告警规则、容量评估、依赖升级、on-call 轮值、故障演练。**10 个服务的运维成本约是 3 个服务的 3–4 倍**（不是线性，因为还有跨服务排障的额外成本）。这个成本必须在上线前分配到具体的人与时间。

3. **当它失效时，系统如何优雅退化？**
   服务化的失效模式是"级联故障"。退化手段：① 弱依赖降级（返回兜底）；② 熔断（下游挂了不重试）；③ 服务降级开关（关闭非核心链路）；④ 单服务故障时，网关路由到降级页而不是 502。**核心原则：一个服务挂掉，只应该让"依赖它的那部分功能"不可用，而不是全站。**

| §3.3 「一套代码两种装配」怎么做到的 | 各服务 `pom.xml` 的 `spring-boot-maven-plugin` | `<classifier>exec</classifier>` 把 fat jar 降级成副产物，主产物保持普通 jar 才能被依赖。**写反了就是 `NoClassDefFoundError`** |
| §3.5 API 契约管理 | `contract/src/main/java/com/polaris/trade/contract/stock/InventoryClient.java` | 契约层只有接口与 DTO，没有实现；服务方 `LocalInventoryClient` / 调用方 `HttpInventoryClient` 各自实现 |
| §3.2 先数据，后服务 | `services/*/src/main/resources/db/migration/` | Flyway 版本号**分段**：V1xx 订单 / V2xx 库存 / V3xx 支付 / V4xx 会员 / V5xx 促销 / V6xx 通知。不分段，六个 `V1__` 会在单体里撞车 |
| §2.3 「分布式单体」的检测信号 | `MonolithApplication.java` 注释第三条 | 单体下"反正同一个事务"的跨域写法，是拆分时最大的返工来源；ArchUnit 规则 `no-cross-domain-transaction` 就是拦它的 |
| §3.3 灰度切流 | `services/gateway-service/src/main/java/com/polaris/trade/gateway/filter/CanaryRouteFilter.java` | 按 userId 粘性分流，输出 `X-Route-Version` 头 |

### B. 跑验证：同一份代码，两种装配

```bash
# 单体装配（local）：6 个服务的类在同一个 JVM 里，进程内直调
POLARIS_DEMO=true scripts/run-monolith.sh --bg
curl -s http://127.0.0.1:18080/internal/stock/90001 | head -c 200
scripts/stop-monolith.sh
```

单体模式下 `InventoryClient` 的实现是 `LocalInventoryClient` —— **没有网络、没有序列化**。
这正是 §2.3 说的"拆之前先想清楚你在拆什么"：现在这条调用链路上没有任何分布式故障点。

想看微服务装配：

```bash
scripts/up.sh micro                                     # + RocketMQ
scripts/mvnw.sh -DskipTests install
# 各服务的 fat jar 在 target/*-exec.jar
java -jar services/stock-service/target/stock-service-1.0.0-SNAPSHOT-exec.jar --server.port=18083
```

此时 `InventoryClient` 的实现换成 `HttpInventoryClient`，
**同样的业务代码开始出现超时、重试、序列化、网络分区** —— 拆分带来的全部新问题都从这里开始。

### C. 看结果：拆分前后多了哪些故障面

| 维度 | 单体（local） | 微服务（micro） |
|---|---|---|
| 库存调用 | 进程内方法调用（`LocalInventoryClient`） | HTTP（`HttpInventoryClient`），有超时与重试 |
| 事务 | 一个 JDBC 连接可跨域 | 必须分布式事务或最终一致（ch09） |
| 失败模式 | 无 | 超时、连接拒绝、序列化不兼容、部分成功 |
| 超时预算 | 本地调用无需预算 | `TimeBudget` 必须逐层收敛（ch11） |

> **诚实说明（缺口）**：灰度切流只能**读代码，不能真演示**。
> `CanaryRouteFilter` 已就绪，但本仓库只起一个实例，`X-Route-Version` 分出去也没有第二个
> 可路由的目标。真分流要等 M7（拆分）起双实例 + 网关权重。ArchUnit 规则同样未落地。

### D. 一句话结论

拆分的代价不在"多了几个进程"，而在**每一次进程内调用都变成了一次可能失败的远程调用**。
本案例用「一套代码两种装配」把这句话变得可验证：切到 `micro` 之后，
`InventoryClient` 的实现从 `LocalInventoryClient` 换成 `HttpInventoryClient`，
业务代码一个字没改，但链路上凭空多出了超时、重试与部分成功 ——
这就是拆分的账单。
