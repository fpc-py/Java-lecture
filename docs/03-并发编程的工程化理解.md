# 03 · 并发编程的工程化理解

> **阶段**：核心编码 / 高并发设计
> **痛点**：线程池参数是拍脑袋填的 200/1000，队列长度是默认的 `Integer.MAX_VALUE`；`CompletableFuture` 用得飞起，但一次下游抖动就把整个 JVM 拖死。

> 这一篇不以"面试要点"为目标。AQS、`ConcurrentHashMap`、`CompletableFuture` 的源码之所以要看，是因为**当吞吐骤降、线程全部卡住时，你必须知道该看哪里、哪些状态是正常的、哪些是死锁前兆**。

---

## 1. 真实故障场景

### 场景 A：一个下游超时，整个服务雪崩

某商品详情服务，用 `CompletableFuture` 并发调用 4 个下游（价格、库存、评价、推荐）：

```java
CompletableFuture<Price> p = CompletableFuture.supplyAsync(() -> priceClient.get(id));
CompletableFuture<Stock> s = CompletableFuture.supplyAsync(() -> stockClient.get(id));
...
```

`supplyAsync` 不传 Executor 时使用 **`ForkJoinPool.commonPool()`，其并行度 = CPU 核数 − 1（8 核机器上为 7）**。

故障时评价服务 P99 从 200ms 涨到 8s，于是 7 个 commonPool 线程全部堵在 `evaluationClient.get()` 的 socket 读上。**所有商品的详情接口一起挂**——包括那些不需要评价数据的请求。线程 dump 特征：

```
"ForkJoinPool.commonPool-worker-3" #21 daemon prio=5 BLOCKED
   at java.net.SocketInputStream.socketRead0(Native Method)
   at com.xxx.EvaluationClient.get(EvaluationClient.java:88)
```

`jstack` 里 7 个 worker 全在这个栈上，且 `activeCount == parallelism`。

### 场景 B：`ConcurrentHashMap.computeIfAbsent` 死锁

```java
private final Map<String, Config> cache = new ConcurrentHashMap<>();

public Config get(String key) {
    return cache.computeIfAbsent(key, k -> loadFromDb(k));  // loadFromDb 内部又调 get(otherKey)
}
```

现象：接口偶发卡死，线程 dump 显示多个线程在 `ConcurrentHashMap.computeIfAbsent` 的 `synchronized` 上等待，形成环。

**根因**：`computeIfAbsent` 会对目标 bin 加 `synchronized`（JDK 8+ 的桶锁），mapping function 在锁内执行。若 mapping function 内部又对**同一个 bin 中的另一个 key** 调用 `computeIfAbsent` 或修改该 map，即自死锁/环死锁。同理适用于 `compute`、`merge`。

### 场景 C：线程池队列是 `LinkedBlockingQueue` 无界，OOM

```java
new ThreadPoolExecutor(50, 50, 0L, TimeUnit.MILLISECONDS, new LinkedBlockingQueue<>());
```

无界队列 → `maximumPoolSize` 永久无效（50 个线程满了就入队，永不扩容）→ 下游变慢时队列堆到 200 万任务 → 每个任务持有请求上下文 → 堆 OOM。同时监控显示"线程池 active=50, queue=2000000"，但告警只配了"线程数"。

## 2. 原理剖析

### 2.1 AQS：一个 `int` 撑起的同步框架

`AbstractQueuedSynchronizer` 是三件事的组合：

```
volatile int state          // 同步状态（ReentrantLock: 重入次数；Semaphore: 剩余许可；CountDownLatch: 计数）
CLH 双向队列（Node）         // 未获取到锁的线程排队，prev/next 指针 + waitStatus
CAS                         // 修改 state / 入队 / 唤醒的原子性
```

`ReentrantLock.lock()` 的路径：

```
tryAcquire(state CAS 0→1)
   ├─ 成功 → 直接持有（无竞争时零排队开销）
   └─ 失败 → addWaiter(EXCLUSIVE) 入队 → acquireQueued 自旋 + park
                      ↑
              前驱是 head 才尝试 tryAcquire（避免惊群）
              否则 LockSupport.park()（被中断/超时/unpark 唤醒）
```

**排障时要用到的三个信号**：

| 现象 | 含义 |
|---|---|
| `jstack` 中大量 `WAITING (parking)` 且栈顶是 `LockSupport.park` → `AQS.xxx` | 正常等待，看是哪个锁（栈里的类名） |
| 同一把锁的持有者线程处于 `RUNNABLE` 但栈在 socket read / DB 查询 | **持锁做 I/O**，这是最常见的吞吐杀手 |
| 队列长度（`getQueueLength()`）持续增长 | 临界区太慢或竞争过热，需要拆分锁/减小粒度 |

**公平 vs 非公平**：非公平锁允许"插队"（新来的线程直接 CAS），吞吐高但有饥饿风险；公平锁严格 FIFO，吞吐低约 10–30%。**默认非公平**，除非有明确的公平性需求（如防止大批量任务饿死小任务）。

### 2.2 `ConcurrentHashMap` 的三个关键机制

| 机制 | 实现 | 工程含义 |
|---|---|---|
| 桶级锁 | `synchronized (f)` 锁首节点（JDK 8+） | 并发度 ≈ 桶数，锁粒度小；但**在锁内执行用户代码**（compute/merge）就是把业务逻辑塞进临界区 |
| 计数 | `baseCount` + `CounterCell[]` 分散热点 | `size()` 是估算值（弱一致），**别用它做业务判断** |
| 扩容 | 多线程协助迁移（`ForwardingNode` 标记） | 扩容期间读仍可用，写会协助迁移；大 map 扩容有 CPU 尖刺 |

```java
// ❌ 在 computeIfAbsent 里做 I/O：锁住一个 bin 直到 DB 返回
configs.computeIfAbsent(key, k -> jdbc.queryForObject(...));   // 阻塞整个 bin 的所有 key

// ✅ 读多写少 + 允许重复加载：双重检查 + putIfAbsent（最多浪费一次查询）
Config c = configs.get(key);
if (c == null) {
    c = loadFromDb(key);
    Config prev = configs.putIfAbsent(key, c);
    if (prev != null) c = prev;
}

// ✅ 需要严格只加载一次：用 per-key 锁（分片锁），而不是 map 的 bin 锁
private final Striped<Lock> locks = Striped.lock(64);   // Guava
Config load(String key) {
    Lock l = locks.get(key);
    l.lock();
    try {
        return configs.computeIfAbsent(key, this::loadFromDbNoNested);  // mapping function 内不再操作该 map
    } finally { l.unlock(); }
}
```

### 2.3 `CompletableFuture`：依赖栈与线程归属

```java
cf.thenApply(f1).thenCompose(f2).thenAccept(f3)
```

每个 stage 是一个 `Completion` 节点，形成链表（依赖栈）。**线程归属规则**：

| 写法 | 执行线程 | 风险 |
|---|---|---|
| `supplyAsync(fn)` | `ForkJoinPool.commonPool()` | 并行度 = CPU−1，**阻塞 I/O 会污染全局池** |
| `supplyAsync(fn, executor)` | 指定池 | 推荐；池满后由拒绝策略决定 |
| `thenApply(fn)` | **完成 previous 的那个线程**，或调用 `complete` 的线程 | 若上游在 commonPool 完成，`thenApply` 也在 commonPool 跑，级联阻塞 |
| `thenApplyAsync(fn)` | commonPool（无 executor 时） | 同上 |
| `get()` / `join()` 在 Tomcat 线程 | 阻塞 Tomcat 线程 | 虚拟线程场景下可接受，平台线程下会打满容器线程 |

**结论**：所有异步编排都必须显式传 Executor，且该 Executor 按下游隔离（舱壁）。`thenApply` 与 `thenApplyAsync` 的区别不是"性能"，而是"这段代码跑在谁的线程上"。

### 2.4 线程池：参数不是猜的，是算的

**Little's Law**（利特尔法则）：

```
并发任务数 L = 到达速率 λ × 平均停留时间 W
```

例：接口 QPS 500，平均 RT 50ms → `L = 500 × 0.05 = 25` 个并发在途任务。

| 任务类型 | 核心线程数公式 | 示例（8 核） |
|---|---|---|
| CPU 密集 | `N_cpu + 1` | 9 |
| I/O 密集 | `N_cpu × (1 + W_block/W_compute)` | 阻塞/计算 = 10 → 88，**但必须再受下游配额约束** |
| 混合 | 按调用链拆分，分别建池 | 见下 |

**实际取值的三重约束**（取最小值）：

```
poolSize = min(
    Little's Law 计算值,        // 理论并发需求
    下游配额 ÷ 单任务下游调用数,  // DB 连接数 50 / 每任务 1 次 = 50
    N_cpu × 目标利用率 × 2      // 防止过度上下文切换（平台线程时代）
)
```

## 3. 工程解法

### 3.1 线程池标准模板（带监控与动态调整）

```java
public final class ThreadPools {

    public static ThreadPoolExecutor build(String name, int core, int max, int queueCap) {
        AtomicInteger idx = new AtomicInteger();
        ThreadFactory tf = r -> {
            Thread t = new Thread(r, name + "-" + idx.incrementAndGet());
            t.setDaemon(false);            // 业务线程非守护，避免优雅停机时任务被丢
            t.setUncaughtExceptionHandler((th, e) ->
                log.error("uncaught in {}", th.getName(), e));
            return t;
        };

        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                core, max,
                60L, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(queueCap),   // 有界！有界！有界！
                tf,
                new ThreadPoolExecutor.AbortPolicy()  // 快速失败，由调用方降级
        );
        pool.allowCoreThreadTimeOut(true);            // 低峰期释放线程
        return pool;
    }
}
```

**队列与拒绝策略的选择逻辑**：

| 队列 | 行为 | 适用 |
|---|---|---|
| `SynchronousQueue` | 不排队，直接交给线程；无空闲线程则扩容到 max，再拒绝 | 短任务、要求低延迟（如 Netty 业务线程池） |
| `ArrayBlockingQueue(n)` | 有界，排队 | **默认推荐**，n = 峰值 QPS × 可容忍排队秒数 |
| `LinkedBlockingQueue()` 无参 | **无界** | 生产禁用 |
| `PriorityBlockingQueue` | 优先级 | 任务有优先级语义时（注意饥饿） |

| 拒绝策略 | 行为 | 适用 |
|---|---|---|
| `AbortPolicy` | 抛 `RejectedExecutionException` | 默认；调用方必须 catch 并降级 |
| `CallerRunsPolicy` | 由提交线程执行 | 能天然限速（Tomcat 线程被占 → 上游变慢），但会拖慢请求线程 |
| `DiscardPolicy` / `DiscardOldestPolicy` | 静默丢弃 | 仅用于可丢弃任务（埋点、日志），且**必须打点计数** |

### 3.2 舱壁模式：按下游隔离

```java
@Configuration
public class ExecutorConfig {

    // 每个下游独立池，互不影响
    @Bean("pricePool")  ThreadPoolExecutor pricePool()  { return ThreadPools.build("price",  16, 32, 200); }
    @Bean("stockPool")  ThreadPoolExecutor stockPool()  { return ThreadPools.build("stock",  16, 32, 200); }
    @Bean("recPool")    ThreadPoolExecutor recPool()    { return ThreadPools.build("rec",     8,  8,  50); }  // 弱依赖，小池 + 快速失败

    // 弱依赖超时后直接返回兜底值，不影响主流程
    public List<Item> recommend(Long id) {
        try {
            return recPool.submit(() -> recClient.list(id)).get(120, TimeUnit.MILLISECONDS);
        } catch (Exception e) {
            metrics.counter("rec.fallback").increment();
            return Collections.emptyList();
        }
    }
}
```

**为什么不用一个共享池**：共享池里一个慢下游会占满所有线程（场景 A）。隔离的代价是线程总数变多（每个池都要为峰值预留），这是**用内存换可用性**的典型权衡。

### 3.3 监控：必须能回答"池子现在什么状态"

```java
@Bean
public MeterBinder executorMetrics(Map<String, ThreadPoolExecutor> pools) {
    return registry -> pools.forEach((name, pool) -> {
        Gauge.builder("executor.active", pool, ThreadPoolExecutor::getActiveCount)
             .tag("pool", name).register(registry);
        Gauge.builder("executor.queued", pool, p -> p.getQueue().size())
             .tag("pool", name).register(registry);
        Gauge.builder("executor.pool.size", pool, ThreadPoolExecutor::getPoolSize)
             .tag("pool", name).register(registry);
        // 关键：已完成任务数与拒绝次数，用 Counter 累计
        FunctionCounter.builder("executor.completed", pool, ThreadPoolExecutor::getCompletedTaskCount)
             .tag("pool", name).register(registry);
    });
}
```

**告警阈值的设计逻辑**（不是拍阈值，而是从饱和推导）：

```
queue.size / queue.capacity > 0.6  持续 1min      → 池子接近饱和
executor.active == pool.max        持续 30s       → 已打满，新任务将被拒绝
executor.rejected 速率 > 0                        → 每个拒绝都要有告警，因为它意味着业务降级
任务平均排队时间（自定义 Timer）> 200ms            → 队列在堆积，用户已在等
```

### 3.4 与虚拟线程共存

| 资源 | 平台线程时代 | 虚拟线程时代 |
|---|---|---|
| 线程池 | 并发上限的核心手段 | **不再是限流器**，per-task 创建 |
| 连接池 | 天然背压 | **成为唯一的背压**，必须显式限流 |
| `ThreadLocal` | 复用友好 | 每任务一线程，注意内存放大 |
| `synchronized` | 常规 | 会 pin（JDK 21/22），换 `ReentrantLock` |
| 线程池监控 | active/queue | 语义失效，改为监控**下游配额使用率** |

共存策略：**入口用虚拟线程，出口用信号量**。

```java
// 出口限流：无论上游多少虚拟线程，打到 DB 的并发永远 ≤ 50
private static final Semaphore DB = new Semaphore(50);
// 出口限流：三方支付接口配额 100 QPS，用 RateLimiter 而非信号量
private static final RateLimiter PAY = RateLimiter.create(100);
```

## 4. 边界条件与反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 池参数用默认值 | `Executors.newFixedThreadPool` 用无界队列，max 参数形同虚设 | 全部手写 `ThreadPoolExecutor`，有界队列 |
| `CompletableFuture` 不传 Executor | 污染 commonPool，全局雪崩 | 显式按下游隔离的池 |
| 在 `synchronized` / 锁内做 RPC、DB、HTTP | 临界区被 I/O 拉长，吞吐线性下降 | 锁内只做内存操作，I/O 移到锁外（先查后写 + CAS） |
| `ConcurrentHashMap` 当缓存且无淘汰 | 无界增长 OOM | Caffeine（有界 + 过期 + 统计） |
| 用 `map.size()` 判断是否为空/限流 | 弱一致，并发下不准 | 用 `isEmpty()` 或原子计数器 |
| `Thread.sleep` 做重试退避 | 占着线程不干活 | 指数退避 + 虚拟线程或调度器 |
| 拒绝策略用 `DiscardPolicy` 且不打点 | 静默丢任务，问题无感知 | 任何丢弃都必须计数 + 告警 |
| 线程池不 shutdown | 优雅停机时任务丢失或进程挂住 | `@PreDestroy` 里 `shutdown()` + `awaitTermination(30s)` |

## 5. 落地检查表

**线程池**

- [ ] 所有 `ThreadPoolExecutor` 使用**有界队列**，容量有推导依据（峰值 QPS × 可容忍排队秒数）
- [ ] 池大小有计算过程（Little's Law + 下游配额），写在类注释或 ADR 里
- [ ] 每个下游/每类任务**独立池**，弱依赖池小且超时短
- [ ] 拒绝策略非静默丢弃；`Discard*` 场景有计数器与告警
- [ ] 线程命名有前缀，便于 `jstack` 过滤
- [ ] 已暴露 active / queue / poolSize / completed / rejected 指标，并配置饱和告警
- [ ] `@PreDestroy` 中优雅关闭（`shutdown` + `awaitTermination`）

**异步编排**

- [ ] `CompletableFuture` 全部显式传入 Executor，**没有裸 `supplyAsync`**
- [ ] 每个异步调用有超时（`orTimeout` / `get(timeout)` / `completeOnTimeout`）
- [ ] 超时后能取消下游任务，或有兜底值（`exceptionally` / `handle`）
- [ ] 没有在 `thenApply` 里做阻塞 I/O（会占用上游完成线程）

**共享结构**

- [ ] `ConcurrentHashMap` 的 `compute*` / `merge` 内**没有** I/O、没有对同 map 的嵌套修改
- [ ] 缓存有容量上限与过期策略
- [ ] 没有"先 check 再 act"的非原子逻辑（用 `putIfAbsent` / `compute` 的原子语义）
- [ ] 锁内无 I/O；锁粒度尽可能小；有获取超时（`tryLock(timeout)`）

**虚拟线程共存**

- [ ] 出口限流（信号量/限流器）已建立，不依赖线程池大小
- [ ] `synchronized` 包裹阻塞调用的位置已排查（见 01 篇）
- [ ] 监控从"线程池指标"切换为"下游配额使用率 + 排队时长"

## 6. 三个追问

1. **为什么用线程池 + 信号量，而不是直接全上虚拟线程？**
   虚拟线程解决"等待时不占线程"，但不解决"下游只能承受 50 并发"。如果下游配额是瓶颈，那么无论用哪种线程模型，都必须显式限流。在已有成熟线程池参数、且没有大量阻塞 I/O 的服务里，改造收益不足以抵消风险；反之（大量扇出、长尾阻塞）虚拟线程收益显著。

2. **引入它之后，运维成本由谁承担？**
   舱壁隔离让线程总数从 200 涨到 600，内存与上下文切换成本由机器承担；监控项从 1 个池变成 N 个池，告警配置与看板维护成本由 SRE 承担。**隔离的粒度和团队运维能力必须匹配**，3 个下游可以一池一个，30 个下游就该考虑统一网关或服务网格。

3. **当它失效时，系统如何优雅退化？**
   三道闸门：队列满 → 拒绝并降级（返回缓存/兜底）；下游超时 → 熔断（见 11 篇）；整体过载 → 入口限流（Sentinel/网关）。关键是每一道闸门都有**明确的用户可感知行为**（降级返回什么），而不是"请求挂着不动"。

## 案例锚点：在 Polaris 里看代码、跑验证

### A. 看代码

| 知识点 | 代码位置 | 看什么 |
|---|---|---|
| §2.4 参数是算的，不是猜的 | `platform/platform-starter-guard/src/main/java/com/polaris/trade/guard/concurrent/ThreadPools.java` → `build()` | 唯一构造函数，四个参数全部显式传入；类注释第一句就是「队列用 `Integer.MAX_VALUE` 会让 `maximumPoolSize` 永久失效」 |
| §3.1 标准模板（有界队列 + 命名 + 拒绝策略） | 同上 | 线程名前缀 `biz-<name>-`：`jstack` 里靠它统计各池占用，见 ch02 的取证摘要 |
| §3.2 舱壁：弱依赖不拖强链路 | `platform/platform-starter-guard/src/main/java/com/polaris/trade/guard/concurrent/BulkheadExecutors.java` → `callWeakDependency()` / `callStrongDependency()` | 弱依赖吞异常返回兜底值，强依赖抛 `DegradedException`。两个 API 的**语义差别**就是隔离的本质 |
| §3.2 一个反直觉事实：超时返回 ≠ 线程释放 | 同上 → `callWeakDependency()` 内部对 `Future.cancel()` 的处理 | 代码注释专门写了 `CompletableFuture.cancel(true)` 不中断正在执行的 `Supplier`，所以改用 `Future` + 显式取消 |
| §3.3 监控要能回答「池子现在什么状态」 | `platform/platform-starter-guard/src/main/java/com/polaris/trade/guard/concurrent/PolarisThreadPool.java` | 自增 `submitted` / `rejected`；`rejectedExecution()` 重写在**处理器**上（`ThreadPoolExecutor` 本身没有这个钩子） |
| §3.3 指标命名 | `platform/platform-starter-guard/src/main/java/com/polaris/trade/guard/concurrent/ExecutorMetrics.java` | `executor.active` → `executor_active`，只把 `.` 换成 `_`，**没有** `_threads` 后缀（写错名字看板就空着） |
| §3.3 人肉可查的入口 | `platform/platform-starter-guard/src/main/java/com/polaris/trade/guard/concurrent/BulkheadEndpoint.java` | `GET /actuator/bulkpools` 返回 active / queue / rejected / completed |

### B. 跑验证：三条命令，三个结论

**验证 1 · 舱壁是否真的隔离（不需要起服务，20 秒）**

```bash
scripts/mvnw.sh -pl platform/platform-starter-guard test -Dtest=BulkheadIsolationTest
```

期望 4 项断言全绿，其中两条最能说明问题：

```
弱依赖被 3s 慢调用占满时，强依赖路径的耗时不受影响
  → stockResult = "stock-ok"，strongCostMs < 100
弱依赖超时后必须真正中断工作线程
  → 工作线程的 interrupted 标志为 true，池子 active 归零
```

**验证 2 · 服务端的池子实时状态（服务已启动时）**

```bash
curl -s http://127.0.0.1:18080/actuator/bulkpools | python -m json.tool
```

**验证 3 · 让弱依赖变成 3 秒慢调用，压出雪崩再修好**

```bash
# 问题态：优惠服务延迟 3s，不加超时
scripts/loadtest.sh --mode weak --steps 8,16,32 --duration 20

# 修复态：舱壁 + 独立超时生效后重跑
scripts/loadtest.sh --mode create --steps 8,16,32 --duration 20
```

### C. 看结果：修复前后的实测对照

| 指标 | 修复前（弱依赖 3s） | 修复后（舱壁 + 超时） | 出处 |
|---|---|---|---|
| `biz-rec` 池拒绝次数 | **713** | **0** | 两个压测目录的 `curve.md` |
| P99 | **687ms** | **335ms** | 同上 |
| 强链路池 `biz-stock` 活跃线程 | 被拖着一启动 | **0/0**（始终空闲） | `2026-10-27-1412-pool-and-gc/summary.md` |

证据目录（**修复前那个不要删**，它才是"不隔离会怎样"的证据）：

- `docs/fault/evidence/2026-10-27-1405-loadtest-create-weak-3s/` —— 问题态
- `docs/fault/evidence/2026-10-27-1411-loadtest-create-weak-3s-fixed/` —— 修复态

### D. 一句话结论

隔离的价值不是「让慢变快」，而是**让慢不外溢**：
优惠服务仍然是 3 秒，但订单主链路从 687ms 回到 335ms。
而 713 → 0 这个变化说明的另一件事是：`cancel(true)` 只给线程打中断标记，
阻塞 IO 照样占着池子 —— **超时返回不等于线程释放**。
