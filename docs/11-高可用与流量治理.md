# 11 · 高可用与流量治理

> **阶段**：高并发设计 / 容量规划
> **痛点**：限流阈值是"隔壁团队配的 1000"；熔断没配，下游挂了就一起挂；压测做了，但压出来的数字对不上生产。

---

## 1. 真实故障场景

### 场景 A：限流阈值拍脑袋，大促误杀 40% 正常流量

```java
// 某次"优化"：给下单接口配了 QPS 1000 的限流
FlowRule rule = new FlowRule("createOrder");
rule.setCount(1000);
```

大促当天实际峰值 1800 QPS，其中 800 被限流 → 用户看到"系统繁忙"。

但更糟的是：**这个接口的实际容量是 3000 QPS**（压测过，没人看）。限流阈值定得太低，等于自己制造了一次故障。

**根因**：限流阈值不是"安全值"，而是"容量 × 安全系数"。没做容量规划就配限流，等于闭着眼睛装刹车。

### 场景 B：没有熔断，一个慢下游拖垮全站

```
order-service 平均 RT 50ms
  └─ 调用 promotion-service（它因为 DB 慢，RT 从 20ms 涨到 5s）
     → order 的 Tomcat 线程全部阻塞在等 promotion
     → order 的所有接口（包括不依赖 promotion 的）都超时
     → 上游网关重试 → 压力 ×3
     → 雪崩
```

**根因**：同步调用 + 无超时 + 无熔断。一个 5% 流量的弱依赖，把 100% 的核心链路拖死。

### 场景 C：多级缓存失效，本地缓存成了"脏数据源"

```java
// 本地缓存 10 分钟，Redis 1 小时
@Cacheable(value = "sku", cacheManager = "caffeineCacheManager")
public Sku get(Long id) { ... }
```

运营改了价格 → 删了 Redis → 但 10 个实例的本地缓存还在，用户看到旧价格，客诉 200+。**多级缓存的失效传播没做，本地缓存就是"10 分钟的必然不一致"。**

### 场景 D：压测通过，生产 5 分钟就挂

压测报告：4 实例，QPS 8000，P99 120ms，通过。生产：同样配置，5 分钟后全站超时。

**根因**（三条同时存在）：

1. 压测用的是**固定参数**（同一个用户、同一个商品），缓存命中率 99%；生产是分散参数，命中率 70%；
2. 压测**没开写操作**（只压了查询），写路径的连接池与锁竞争没暴露；
3. 压测**只压了单接口**，没压混合场景（真实流量是 60% 查询 + 30% 详情 + 10% 下单）。

**没有混合场景、没有真实数据分布的压测，数字只能证明"系统能跑"，不能证明"能扛"。**

## 2. 原理剖析

### 2.1 四种限流算法与适用场景

| 算法 | 原理 | 突发流量 | 实现 | 适用 |
|---|---|---|---|---|
| 固定窗口计数 | 每秒计数，超阈值拒绝 | 临界点双倍（0.99s 和 1.01s 各放 1000） | 最简单 | 粗略保护，不推荐 |
| 滑动窗口 | 把 1 秒切成 N 格，滚动统计 | 较平滑 | 中（需存 N 个计数） | Sentinel 默认（`LeapArray`） |
| 漏桶 | 恒定速率流出，请求排队 | 完全削平（不允许突发） | 中 | 保护下游恒定处理能力 |
| 令牌桶 | 恒定速率放令牌，允许积攒 | 允许一定突发 | 中（Guava `RateLimiter`） | 大多数 API 限流 |

**Sentinel 的两种限流维度**：

| 维度 | 含义 | 适用 |
|---|---|---|
| QPS（并发请求数/秒） | 按到达速率限制 | 大多数场景 |
| 线程数（并发处理数） | 按正在处理的数量限制 | **下游慢时的正确选择**（QPS 限不住已阻塞的线程） |

> 关键判断：**下游变慢时，QPS 限流会失效**。因为 1000 QPS 的请求如果每个都卡 3 秒，会有 3000 个线程堆积。此时必须用**线程数限流**（如 `maxConcurrency=200`），它直接约束"同时在处理的请求数"。

### 2.2 熔断状态机

```
                 失败率 > 阈值
    ┌────────┐ ─────────────▶ ┌────────┐
    │ CLOSED │                │  OPEN  │  直接拒绝，不调用下游
    │ 正常放行│ ◀───────────── │ 熔断中 │
    └────────┘   探测成功      └────────┘
         ▲                          │ 等待熔断时长
         │                          ▼
         │                    ┌────────────┐
         └────────────────────│ HALF_OPEN  │  放行少量探测请求
              连续N次成功       └────────────┘
```

**Sentinel 的三种熔断策略**：

| 策略 | 触发条件 | 适用 |
|---|---|---|
| 慢调用比例 | RT > 阈值 的请求占比 > 比例，且请求数 ≥ 最小请求数 | **最常用**：下游变慢时熔断 |
| 异常比例 | 异常占比 > 阈值 | 下游大量报错 |
| 异常数 | 异常数 > 阈值（分钟级） | 低频接口 |

**参数推导示例**（不是拍脑袋）：

```
慢调用 RT 阈值 = 下游 P99 的 2 倍（如正常 P99 100ms → 阈值 300ms）
比例阈值     = 50%（一半请求都慢，说明下游真的不行了）
最小请求数   = 10（避免低流量时误熔断）
熔断时长     = 10s（下游恢复通常需要几秒到几十秒）
```

### 2.3 降级的四个层次

| 层次 | 手段 | 例子 |
|---|---|---|
| **数据降级** | 返回兜底数据 | 推荐服务挂了 → 返回热门榜单（静态） |
| **功能降级** | 关闭非核心功能 | 大促时关闭"猜你喜欢""历史浏览" |
| **链路降级** | 同步改异步 | 下单后的积分发放改为 MQ 异步 |
| **读写降级** | 只读不写 | 极端情况下关闭下单，只保留查询 |

**降级必须是"可开关、可灰度、可回滚"的**：

```java
@Component
public class DegradeSwitch {
    // 配置中心动态推送（Nacos/Apollo），无需重启
    @Value("${degrade.recommend:false}")
    private boolean recommendDown;

    public List<Item> recommend(Long uid) {
        if (recommendDown) {
            metrics.counter("degrade.recommend").increment();
            return hotListCache.get();      // 兜底：热门榜单（本地缓存，永不失效）
        }
        return recClient.list(uid);
    }
}
```

### 2.4 多级缓存的一致性传播

三层结构：

```
L1：本地缓存（Caffeine，堆内，纳秒级，TTL 1–5s）
L2：分布式缓存（Redis，毫秒级，TTL 30min）
L3：数据库
```

**L1 的失效传播有三种方案**：

| 方案 | 机制 | 延迟 | 复杂度 |
|---|---|---|---|
| 短 TTL | L1 TTL 1–5s，过期自动重载 | ≤5s | 最低（**默认推荐**） |
| 广播失效 | 数据变更时通过 Redis Pub/Sub 或 MQ 广播"删 key" | 毫秒级 | 中（需处理消息丢失） |
| 版本号 | 每个 key 带版本，L1 校验版本 | 取决于轮询 | 高 |

```java
// 广播失效的标准实现（Redis Pub/Sub）
@Configuration
public class CacheEvictConfig {
    @Bean
    RedisMessageListenerContainer container(RedisConnectionFactory f, LocalCacheEvictor evictor) {
        RedisMessageListenerContainer c = new RedisMessageListenerContainer();
        c.setConnectionFactory(f);
        c.addMessageListener(evictor, new ChannelTopic("cache:evict"));
        return c;
    }
}

@Component
@RequiredArgsConstructor
public class LocalCacheEvictor implements MessageListener {
    private final Cache<String, Object> localCache;   // Caffeine

    @Override
    public void onMessage(Message message, byte[] pattern) {
        localCache.invalidate(new String(message.getBody()));   // 本机失效
    }
}

// 变更时双重失效
public void updatePrice(Long skuId) {
    skuMapper.updatePrice(...);
    afterCommit(() -> {
        redis.delete("sku:" + skuId);
        redis.convertAndSend("cache:evict", "sku:" + skuId);    // 通知所有实例
    });
}
```

**注意 Pub/Sub 的可靠性**：Redis Pub/Sub 是"发后即忘"，实例在重启期间收不到消息 → 靠 **L1 的短 TTL 兜底**。所以"短 TTL + 广播"要同时用，不能只依赖广播。

### 2.5 容量规划：从"能压多少"到"该配多少"

**核心公式**：

```
单实例容量 = 压测得到的最大稳定 QPS（P99 满足 SLO）
实例数     = 峰值 QPS ÷ (单实例容量 × 安全水位)
安全水位   = 0.6 ~ 0.7（预留突发、故障转移、GC、发布滚动）
```

例：

```
峰值 QPS 12,000，单实例压测容量 2,500（P99 < 200ms）
实例数 = 12,000 ÷ (2,500 × 0.65) ≈ 7.4 → 8 实例
若需容忍 1 个实例故障（N+1）：9 实例
```

**为什么安全水位是 0.6–0.7**（而不是 0.9）：

| 因素 | 占用 |
|---|---|
| 单实例故障后，剩余实例要接管 | +1/N 负载 |
| GC/编译/抖动导致的短时能力下降 | 5–15% |
| 灰度发布期间新旧版本共存 | 短暂 100% 双跑 |
| 流量分布不均（客户端连接未均衡） | 5–10% |
| 突发流量（营销、爬虫） | 不可预测 |

## 3. 工程解法

### 3.1 Sentinel 规则配置（持久化到 Nacos）

```java
@Configuration
public class SentinelConfig {

    @PostConstruct
    public void init() {
        // 流控规则：QPS + 线程数双维度
        FlowRule qps = new FlowRule("createOrder");
        qps.setGrade(RuleConstant.FLOW_GRADE_QPS);
        qps.setCount(2500);                        // 来自容量规划
        qps.setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_WARM_UP);   // 预热，防冷启动打满
        qps.setWarmUpPeriodSec(30);

        FlowRule threads = new FlowRule("createOrder");
        threads.setGrade(RuleConstant.FLOW_GRADE_THREAD);
        threads.setCount(200);                     // 线程数上限，防下游慢时堆积

        // 熔断规则：慢调用比例
        DegradeRule slow = new DegradeRule("callPromotion");
        slow.setGrade(CircuitBreakerStrategy.SLOW_REQUEST_RATIO.getType());
        slow.setCount(300);                        // RT > 300ms 视为慢调用
        slow.setSlowRatioThreshold(0.5);           // 慢调用占比 > 50%
        slow.setMinRequestAmount(10);
        slow.setStatIntervalMs(10_000);
        slow.setTimeWindow(10);                    // 熔断 10s

        FlowRuleManager.loadRules(List.of(qps, threads));
        DegradeRuleManager.loadRules(List.of(slow));
    }
}
```

**规则持久化**（避免重启丢失）：

```yaml
spring:
  cloud:
    sentinel:
      datasource:
        flow:
          nacos:
            server-addr: ${NACOS_ADDR}
            data-id: ${spring.application.name}-flow-rules
            group-id: SENTINEL_GROUP
            rule-type: flow
        degrade:
          nacos:
            server-addr: ${NACOS_ADDR}
            data-id: ${spring.application.name}-degrade-rules
            group-id: SENTINEL_GROUP
            rule-type: degrade
```

> **不要用控制台直接改规则**：控制台修改默认只存在内存，重启即丢。必须持久化到 Nacos/Apollo，且规则变更有 Git 记录（可审计）。

### 3.2 超时、重试、熔断的协同（最容易配错的组合）

```
用户请求
  └─ 网关：超时 3s，不重试（幂等接口可重试 1 次）
       └─ 服务A：自身超时预算 2.5s
            └─ Feign 调用 B：连接超时 200ms，读超时 800ms，不重试
                 └─ B 调用 C：读超时 500ms
```

**三条铁律**：

| 铁律 | 理由 |
|---|---|
| 超时必须自顶向下递减 | 否则内层超时比外层还长，外层已经放弃但内层还在占资源 |
| 重试只加在**幂等 + 最内层** | 每层都重试 = 指数放大（3 层 × 3 次 = 27 倍流量） |
| 熔断阈值基于**实际 RT 分布** | 用 P99 × 2 作为慢调用阈值，而不是猜 |

```yaml
# OpenFeign 正确配置
feign:
  client:
    config:
      promotion-service:
        connectTimeout: 200
        readTimeout: 800
        loggerLevel: basic
  httpclient:
    enabled: true
    maxConnections: 200
    maxConnectionsPerRoute: 50

# 重试只对幂等 GET 生效，且只重试连接失败（不重试读超时）
resilience4j:
  retry:
    instances:
      promotion:
        maxAttempts: 2
        waitDuration: 100ms
        retryExceptions:
          - java.net.ConnectException
```

> **不要重试读超时**：读超时意味着请求可能已经在服务端执行（如下单），重试会造成重复。读超时应交给熔断与降级处理。

### 3.3 全链路压测方法论：四个阶段与输出物

| 阶段 | 目标 | 方法 | 输出物 |
|---|---|---|---|
| **① 基准测试** | 单接口的极限容量 | 单接口、固定参数、逐步加压到 P99 超 SLO | 单接口 QPS–RT 曲线、拐点容量 |
| **② 负载测试** | 目标负载下是否稳定 | 混合场景（真实比例）、真实数据分布 | 各接口 P99、错误率、资源使用率 |
| **③ 稳定性测试** | 长时间是否退化 | 70% 负载跑 8–24h | 内存/连接/线程是否单调增长、GC 频率 |
| **④ 容量规划** | 需要多少资源 | 由 ①–③ 推导 | 实例数、连接池大小、限流阈值 |

**压测设计的五个关键点**：

```
1. 数据分布要真实：不要固定 1 个用户/1 个商品（缓存全命中）
   → 准备 10 万级参数池，按 Zipf 分布分配（模拟热点）

2. 场景比例要真实：从生产网关日志统计各接口 QPS 占比
   → 压测脚本按同比例混合

3. 要压"写"：查询压不出连接池与锁竞争
   → 至少 10–20% 写操作

4. 要制造"依赖变慢"：用 ChaosBlade 给下游加 100ms 延迟
   → 验证熔断与降级是否生效（见 17 篇）

5. 压测环境要接近生产：同规格、同中间件版本、同数据量级
   → 否则数字不可用（差 3 倍很常见）
```

**压测报告必须回答的四个问题**：

```
① 当前配置能扛多少 QPS（P99 ≤ SLO）？
② 瓶颈在哪一跳（DB？连接池？某下游？GC？）
③ 资源水位如何（CPU/内存/连接数/线程数 在峰值时是多少）？
④ 限流阈值应该配多少（= 容量 × 0.7）？
```

### 3.4 热点探测与隔离

```java
// 简单热点探测：统计 key 访问频次（滑动窗口）
public class HotKeyDetector {
    private final Cache<String, LongAdder> counter = Caffeine.newBuilder()
            .expireAfterWrite(1, TimeUnit.SECONDS).maximumSize(100_000).build();

    public void record(String key) {
        counter.get(key, k -> new LongAdder()).increment();
    }

    @Scheduled(fixedRate = 1000)
    public void detect() {
        counter.asMap().forEach((k, v) -> {
            if (v.sum() > 5000) {                       // 单 key 单秒 > 5000 次
                hotKeyCache.put(k, true);               // 加入本地缓存白名单
                alert.info("hot key detected: {}", k);
            }
        });
        counter.invalidateAll();
    }
}
```

**热点的三级隔离**：

| 级别 | 手段 |
|---|---|
| 本地缓存 | 热点 key 主动加入 Caffeine（TTL 1s） |
| 副本分散 | `key:{0..9}` 随机读，把单 key 压力分散到 10 个槽 |
| 请求合并 | singleflight，同一 key 的并发请求只回源一次（见 07 篇） |

## 4. 边界条件与反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 限流阈值凭经验填 | 要么误杀，要么形同虚设 | 阈值 = 压测容量 × 0.7，并随容量变化更新 |
| 只配 QPS 限流 | 下游慢时线程堆积，QPS 限不住 | QPS + 线程数双维度 |
| 每层都加重试 | 流量指数放大（3×3×3=27） | 只在最内层、只对幂等操作重试 |
| 重试读超时 | 服务端可能已执行，造成重复 | 只重试连接失败 |
| 超时时间内外层一样长 | 内层还在跑，外层已放弃，资源浪费 | 自顶向下递减 |
| 熔断阈值用默认值 | 与业务 RT 不匹配，要么不熔断要么频繁熔断 | 基于 P99 × 2 推导 |
| 降级没有开关 | 出事时改代码重新发布，来不及 | 配置中心动态开关 |
| 本地缓存不设 TTL | 数据永久不一致 | 短 TTL（1–5s）+ 广播失效 |
| 压测用固定参数 | 缓存命中率虚高，结论不可信 | 参数池 + Zipf 分布 |
| 压测只压单接口 | 混合场景下的资源竞争未暴露 | 混合场景 + 真实比例 |
| 用单机压测结果推总量 | 忽略了网关、LB、DB 的共享瓶颈 | 全链路压测（含中间件） |

## 5. 落地检查表

**限流与熔断**

- [ ] 每个对外接口都有 QPS 限流，阈值来自压测（有文档依据）
- [ ] 关键接口同时有线程数限流
- [ ] 每个强依赖调用都有熔断规则，阈值基于 RT 分布
- [ ] 规则持久化到配置中心（非控制台内存），变更有记录
- [ ] 限流/熔断触发有指标与告警（否则等于没配）

**超时与重试**

- [ ] 每个远程调用都显式设置连接超时与读超时
- [ ] 超时预算自顶向下递减，有全局超时表
- [ ] 重试仅在最内层、仅对幂等操作、仅对连接类异常
- [ ] 重试有次数上限与退避

**降级**

- [ ] 每个弱依赖都有兜底返回（空列表/热门榜/默认值）
- [ ] 降级开关在配置中心，可动态生效
- [ ] 降级触发有计数指标（知道降级发生了多少次）
- [ ] 降级演练过（至少一次在生产验证开关生效）

**缓存**

- [ ] 本地缓存 TTL ≤ 5s，且有失效广播（或明确接受不一致窗口）
- [ ] 缓存失效与数据更新在同一事务提交后执行
- [ ] 热点 key 有探测与本地缓存兜底

**容量**

- [ ] 已完成四阶段压测（基准/负载/稳定性/容量）
- [ ] 压测使用真实数据分布与混合场景
- [ ] 实例数按"峰值 ÷ (单实例容量 × 0.65)"计算，且有 N+1 冗余
- [ ] 压测报告包含瓶颈定位与限流阈值建议

## 6. 三个追问

1. **为什么用 Sentinel 而不是自己写限流器？**
   自研限流器在单机场景很简单（Guava `RateLimiter` 就够），但**集群维度的一致性**、规则动态下发、熔断状态机、与监控的集成，都需要完整的工程实现。Sentinel 的价值不在算法（滑动窗口并不复杂），而在**规则管理 + 控制台 + 生态集成**。如果只是单机保护，`RateLimiter` + 信号量足够；需要集群级与动态规则时，用 Sentinel。

2. **引入它之后，运维成本由谁承担？**
   限流熔断的本质是"把系统能力上限显式化"。一旦配置了阈值，就意味着**必须持续维护容量模型**：流量涨了要调阈值、机器扩了要调阈值、接口改了要重新压测。这个成本由**研发 + SRE 共同承担**，且是长期的。很多团队配了规则三年没改，阈值早就与实际容量脱节，这才是最危险的状态。

3. **当它失效时，系统如何优雅退化？**
   四层退化：① 单请求超时 → 返回兜底；② 依赖熔断 → 走降级逻辑；③ 整体过载 → 入口限流（保护自己）；④ 极端情况 → 功能开关关闭非核心链路。**每一层都要有明确的用户可感知行为**（"暂时无法显示推荐" 好过 "转圈 30 秒"）。

### B. 跑验证：把弱依赖拖垮主链路，再把它按住

```bash
# 问题态：优惠服务人为延迟 3 秒（不开舱壁隔离的效果）
POLARIS_DEMO=true scripts/run-monolith.sh --bg --polaris.promotion.simulate-delay-ms=3000
scripts/loadtest.sh --mode create --steps 8,16,32 --duration 20
```

观察 `biz-rec` 线程池：`active` 会稳定停在 **8/8**（池被打满），
拒绝次数开始增长，P99 被拖到 **687ms**。

```bash
scripts/stop-monolith.sh

# 正确态：恢复正常延迟，同一套压测
POLARIS_DEMO=true scripts/run-monolith.sh --bg
scripts/loadtest.sh --mode create --steps 8,16,32 --duration 20
```

期望：拒绝 **0**，P99 **335ms**。

顺便压出单机容量天花板：

```bash
scripts/loadtest.sh --mode query --steps 8,16,32,64,128 --duration 15
```

### C. 看结果：三个数字决定"该配多少"

**① 单机拐点**（不是拍出来的，是压出来的）

| 并发 | QPS | P50 | P99 |
|---|---|---|---|
| 8 | 1724 | 3ms | 14ms |
| 32 | 3194 | 8ms | 27ms |
| **64** | **3323** | 17ms | 43ms |
| 128 | 3192 | 36ms | 105ms |

64 → 128 这一段是唯一有信息量的：**吞吐退坡 + P99 翻 2.4 倍**，
说明多出来的并发全在排队。安全水位 = 拐点 × 0.7 ≈ **2300 QPS**。

**② 舱壁隔离的效果**

| 指标 | 弱依赖 3s 且无隔离 | 舱壁 + 独立超时 |
|---|---|---|
| rec 池拒绝 | **713** | **0** |
| P99 | **687ms** | **335ms** |

**③ 超时预算的约束**

`TimeBudget` 里 3000 > 2500 > 800 > 500 > 300 全部单调递减。
违反这条，重试就会把下游压死 —— 因为外层还在等，内层已经重试了三轮。

证据：`docs/fault/evidence/2026-10-27-1402-loadtest-query/`、
`docs/fault/evidence/2026-10-27-1405-loadtest-create-weak-3s/`、
`docs/fault/evidence/2026-10-27-1411-loadtest-create-weak-3s-fixed/`

### D. 一句话结论

流量治理的所有参数（限流阈值、熔断阈值、超时、线程池大小）都应该能回答
「**这个数字是从哪来的**」。本案例的答案是同一个：**阶梯压测的拐点 × 0.7**。
拍脑袋的数字在平时看不出问题，在大促当天会以"误杀 40% 正常流量"的形式还回来。

> **诚实说明（缺口）**：Sentinel 规则目前是**进程内编程式配置**，
> 尚未持久化到 Nacos（§3.1 的做法），所以重启即失效、多实例不共享。
> 计划在 M8（流量治理）补齐 Nacos 数据源与 `limit-check.sh` 验收脚本。
