# 18 · 认证授权与数据安全

> **阶段**：贯穿全生命周期（在金融/政企场景是上线硬门槛）
> **痛点**：JWT 是无状态的，所以"用户被禁用后 token 还能用 7 天"；网关做了认证，但内部服务之间的接口裸奔；日志里躺着明文手机号和身份证号，安全评审一票否决。

---

## 1. 真实故障场景

### 场景 A：员工离职，账号禁用，但还能访问 7 天

```
HR 系统禁用账号 → 业务系统登录被拒
但该员工手上的 access_token 还有 6 天有效期
→ 他依然可以调用所有 API（JWT 自包含，服务端不查库）
```

**根因**：JWT 的核心特性是"无状态、自验证"，**这也意味着"不可撤销"**。要撤销，必须引入状态（黑名单/版本号/短 TTL）。

### 场景 B：Refresh Token 泄漏，账号被长期接管

```
access_token: 2h 有效期（泄漏后影响有限）
refresh_token: 30 天，且不轮换、不绑定设备
→ 攻击者拿一次 refresh_token，可以持续刷新 30 天
```

### 场景 C：内部接口裸奔

```
外部：https://api.example.com/api/order  → 网关校验 JWT ✅
内部：http://order-service:8080/order/all → 无鉴权，任何 Pod 都能调 ❌
```

攻击者通过 SSRF 或某个被攻陷的边缘服务，直接调用内部接口拿到全量订单数据。**"内网可信"是最危险的假设。**

### 场景 D：日志里的明文 PII

```
2026-10-24 21:03:11 INFO OrderService - create order, phone=13800138000, idCard=110101199001011234
```

日志被采集到 ELK、同步到数据仓库、被第三方运维看到。**一次日志泄漏 = 全量用户信息泄漏**，且涉及《个人信息保护法》合规问题。

### 场景 E：审计日志可被删除

某金融系统要求"所有敏感操作留痕且不可篡改"。实现方式：业务库里建 `t_audit_log` 表，用同一个 DB 账号插入。结果一次误操作 `DELETE FROM t_audit_log WHERE ...`，审计记录丢失，合规检查不通过。

## 2. 原理剖析

### 2.1 OAuth2 / OIDC 的正确姿势

```
用户 ──① 授权请求──▶ 授权服务器（Authorization Server）
     ◀──② 授权码───
     ──③ 用码换 token（带 PKCE + client_secret）──▶
     ◀──④ access_token + refresh_token + id_token──
     ──⑤ 带 access_token 调用资源服务──▶ 资源服务
                                          └─ 校验签名/过期/scope
```

| 令牌 | 用途 | 有效期 | 存放位置 |
|---|---|---|---|
| `access_token` | 调用 API | **短（5–15 分钟）** | 内存（不落 localStorage） |
| `refresh_token` | 换取新 access_token | 长（7–30 天），**必须轮换** | HttpOnly Cookie / 安全存储 |
| `id_token` | 身份声明（OIDC） | 短 | 前端 |

**PKCE 为什么必须**（对公开客户端）：

```
无 PKCE：授权码被拦截 → 攻击者用码换 token
有 PKCE：换 token 时必须提供 code_verifier（只有发起方知道），拦截者无法换取
```

**授权码模式的三个常见错误**：

| 错误 | 后果 |
|---|---|
| 隐式模式（Implicit）用于 SPA | token 暴露在 URL/浏览器历史 |
| 无 PKCE 的公开客户端 | 授权码拦截 |
| client_secret 硬编码在前端 | 等同于公开 |

### 2.2 JWT 的结构与"不该放什么"

```
eyJhbGciOiJSUzI1NiIsImtpZCI6ImsxIn0 . eyJzdWIiOiJ1ODgyMyIsImV4cCI6MTcz... . signature
└──────── header ────────┘   └────────── payload（Base64，明文可读）──────────┘
```

**payload 是 Base64 编码，不是加密**——任何人拿到 token 都能解出内容。

| 该放 | 不该放 |
|---|---|
| `sub`（用户 ID）、`exp`、`iat`、`iss`、`aud` | 手机号、身份证、邮箱（PII） |
| `scope` / `roles`（粗粒度） | 大量权限明细（token 会很大） |
| `jti`（唯一 ID，用于黑名单） | 密码、密钥、内部配置 |
| `kid`（在 header 里，用于密钥轮换） | 业务敏感数据 |

```json
// ✅ 精简且合规的 payload
{
  "sub": "u_88231",
  "iss": "https://auth.example.com",
  "aud": "order-api",
  "exp": 1730000000,
  "iat": 1729999700,
  "jti": "01J8X...",
  "scope": "order:read order:write",
  "tenant": "t_001"
}
```

### 2.3 Token 吊销的四种方案

| 方案 | 机制 | 生效延迟 | 成本 |
|---|---|---|---|
| **短 TTL**（基础） | access_token 5–15 分钟 | ≤ TTL | 无（推荐作为底座） |
| **黑名单** | Redis 存 `jti`，TTL = 剩余有效期 | 立即 | 每次请求查 Redis |
| **用户级版本号** | 用户表存 `tokenVersion`，token 带版本，不匹配即失效 | 立即 | 每次请求查缓存版本 |
| **在线自省**（introspection） | 每个请求问授权服务器 | 立即 | 高（每请求一次 RPC） |

**生产推荐组合**：

```
access_token TTL = 10 分钟（短，泄漏影响有限）
+ refresh_token 轮换（每次刷新换新的，旧的立即失效）
+ 黑名单（只存"主动注销/禁用"的 jti，量小）
+ 用户版本号（禁用账号时 version+1，所有 token 立即失效）
```

```java
// 用户级版本号：性价比最高的吊销方案
public boolean validate(String token) {
    Claims c = parser.parseSignedClaims(token).getPayload();
    if (c.getExpiration().before(new Date())) return false;

    Long ver = cache.get("user:ver:" + c.getSubject(), () -> userMapper.selectVersion(c.getSubject()));
    if (!Objects.equals(ver, c.get("ver", Long.class))) return false;   // 版本不匹配 → 已吊销

    if (blacklist.contains(c.getId())) return false;                    // 主动注销
    return true;
}
```

### 2.4 微服务的鉴权边界

```
┌─────────┐   ①认证（验签/查黑名单）   ┌──────────────┐
│  网关    │ ───────────────────────▶ │ 业务服务      │
│ Gateway │   ②透传身份（签名头）       │ ③细粒度鉴权   │
└─────────┘                            └──────────────┘
```

**关键设计：网关与服务的职责分离**

| 层 | 职责 | 不该做的事 |
|---|---|---|
| 网关 | 认证（token 有效性）、限流、路由、注入可信身份头 | 业务权限判断（不知道业务规则） |
| 服务 | 授权（RBAC/ABAC，数据级权限） | 重复做认证（但要校验身份头来源可信） |

```java
// 网关校验后，注入签名头（防止内部伪造）
// X-User-Id: u_88231
// X-User-Sig: HMAC-SHA256(X-User-Id + timestamp, gatewaySecret)
// X-User-Ts: 1730000000

@Component
public class TrustedHeaderFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String uid = req.getHeader("X-User-Id");
        String sig = req.getHeader("X-User-Sig");
        String ts  = req.getHeader("X-User-Ts");

        // 内部调用必须携带有效签名，否则视为未认证（防绕过网关）
        if (uid != null) {
            if (!SignatureUtils.verify(uid, ts, sig, gatewaySecret)
                    || Math.abs(now() - Long.parseLong(ts)) > 60) {
                res.setStatus(401);
                res.getWriter().write("{\"code\":401,\"msg\":\"untrusted identity header\"}");
                return;
            }
            SecurityContext.set(new Principal(uid));
        }
        chain.doFilter(req, res);
    }
}
```

**内部服务的三种保护方式**：

| 方式 | 强度 | 成本 | 适用 |
|---|---|---|---|
| 网络隔离（NetworkPolicy / 安全组） | 中 | 低 | 基础防护，必须做 |
| Service Token / mTLS | 高 | 中 | 敏感服务（支付、用户） |
| 服务网格 mTLS | 高 | 高 | 规模大、合规要求高（见 10 篇） |

### 2.5 PII 的三层脱敏

**第一层：传输**

```
外部：TLS 1.2+（推荐 1.3），HSTS，证书有效
内部：mTLS 或至少 TLS（不要以为内网就安全）
```

**第二层：存储**

| 数据类型 | 处理方式 | 示例 |
|---|---|---|
| 密码 | **不可逆哈希 + 加盐**（bcrypt/argon2id） | `$2a$12$...` |
| 手机号 | 加密（AES-GCM）或掩码存储 | `138****8000`（展示用）+ 密文（查询用） |
| 身份证 | 加密 + 单独字段存哈希（用于精确查询） | 密文 + `SHA256(idCard + salt)` |
| 银行卡 | **禁止存储完整卡号**（PCI-DSS），只存后四位 + token | `**** **** **** 1234` |
| 地址 | 加密 | — |

```java
// 字段级加密（MyBatis TypeHandler，对业务透明）
@MappedTypes(String.class)
public class EncryptTypeHandler extends BaseTypeHandler<String> {
    @Override
    public void setNonNullParameter(PreparedStatement ps, int i, String p, JdbcType t) throws SQLException {
        ps.setString(i, AesGcm.encrypt(p, keyProvider.current()));   // 支持密钥轮换
    }
    @Override
    public String getNullableResult(ResultSet rs, String col) throws SQLException {
        return AesGcm.decrypt(rs.getString(col), keyProvider::byVersion);
    }
}
```

**第三层：日志**

```java
// Logback 脱敏 converter（在输出前统一处理，业务代码无感）
public class DesensitizeConverter extends ClassicConverter {
    private static final List<Pattern> RULES = List.of(
        Pattern.compile("(1[3-9]\\d)\\d{4}(\\d{4})"),                    // 手机号
        Pattern.compile("(\\d{6})\\d{8}(\\d{4}[0-9Xx])"),                 // 身份证
        Pattern.compile("(\\d{4})\\d{10,12}(\\d{4})")                     // 银行卡
    );

    @Override
    public String convert(ILoggingEvent event) {
        String msg = event.getFormattedMessage();
        msg = RULES.get(0).matcher(msg).replaceAll("$1****$2");
        msg = RULES.get(1).matcher(msg).replaceAll("$1********$2");
        msg = RULES.get(2).matcher(msg).replaceAll("$1**********$2");
        return msg;
    }
}
```

```xml
<conversionRule conversionWord="msg" converterClass="com.example.log.DesensitizeConverter"/>
```

> **两层防护是必要的**：① 日志脱敏 converter（兜底）；② 业务代码规范（不打印整个对象、`toString` 里排除敏感字段）。只靠后者，一定会漏。

### 2.6 审计留痕的"不可篡改"

| 要求 | 实现 |
|---|---|
| 独立存储（不与业务库同库同账号） | 独立 DB / 对象存储 / 日志服务 |
| 只追加（append-only） | 应用只有 INSERT 权限；DB 层禁止 UPDATE/DELETE |
| 不可篡改 | 哈希链（每条记录含前一条的 hash）或 WORM 存储 |
| 可追溯查询 | 按时间/用户/会话/资源建索引 |
| 保留期 | 按合规要求（金融常见 5–7 年） |

```sql
CREATE TABLE t_audit_log (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    ts          DATETIME(3) NOT NULL,
    actor_id    VARCHAR(64)  NOT NULL,
    actor_ip    VARCHAR(64),
    action      VARCHAR(64)  NOT NULL,   -- ORDER_CANCEL / USER_DISABLE
    resource    VARCHAR(128) NOT NULL,
    detail      JSON,                     -- 变更前后（脱敏后）
    trace_id    VARCHAR(64),
    prev_hash   CHAR(64),                 -- 上一条的 hash
    hash        CHAR(64) NOT NULL,        -- SHA256(本条内容 + prev_hash)
    KEY idx_actor_ts (actor_id, ts),
    KEY idx_resource (resource, ts)
);
-- 应用账号只有 INSERT 权限
GRANT INSERT ON app.t_audit_log TO 'app_user'@'%';
```

```java
// 哈希链：任一记录被改，后续 hash 全部对不上（可校验）
String hash = sha256(ts + actorId + action + resource + detailJson + prevHash);
```

**审计的常见缺口**：

| 缺口 | 后果 |
|---|---|
| 只记录"成功"操作 | 越权尝试、暴力破解无痕迹 |
| 不记录"查了什么" | 数据被批量拉走无法追溯 |
| 记录里含 PII 明文 | 审计表本身成了泄漏源 |
| 没有校验机制 | "不可篡改"只是口头承诺 |

## 3. 工程解法

### 3.1 认证授权的落地清单

```yaml
# 关键配置（Spring Authorization Server 示例）
spring:
  security:
    oauth2:
      authorizationserver:
        client:
          web-app:
            registration:
              client-authentication-methods: [client_secret_basic]
            token:
              access-token-time-to-live: 10m      # 短 TTL
              refresh-token-time-to-live: 7d
              reuse-refresh-tokens: false          # ⚠️ 必须 false：refresh 轮换
```

```java
// 资源服务器校验（含版本号吊销检查）
@Bean
SecurityFilterChain filterChain(HttpSecurity http, TokenValidator validator) throws Exception {
    http.oauth2ResourceServer(oauth2 -> oauth2
            .jwt(jwt -> jwt.decoder(NimbusJwtDecoder.withPublicKey(pubKey)
                    .build())
                 .jwtAuthenticationConverter(converter())))
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/actuator/health/**").permitAll()
            .requestMatchers("/api/admin/**").hasRole("ADMIN")      // 授权在这里
            .anyRequest().authenticated())
        .addFilterBefore(new TokenVersionFilter(validator), BearerTokenAuthenticationFilter.class);
    return http.build();
}
```

### 3.2 数据分级与处理矩阵

| 级别 | 例子 | 传输 | 存储 | 日志 | 展示 |
|---|---|---|---|---|---|
| L1 公开 | 商品名、价格 | TLS | 明文 | 可打印 | 明文 |
| L2 内部 | 订单号、库存 | TLS | 明文 | 可打印 | 明文 |
| L3 敏感 | 手机号、地址 | TLS | 加密 | **脱敏** | 掩码 |
| L4 高敏 | 身份证、银行卡、密码 | TLS + 字段加密 | 加密/哈希 | **禁止打印** | 掩码/不展示 |

**落地方式**：给每个实体字段打标签（注解），用 TypeHandler + Converter 统一处理，而不是每个业务方法手写脱敏。

```java
public record UserProfile(
    String userId,
    @Sensitive(level = L3, mask = PHONE) String phone,
    @Sensitive(level = L4, mask = ID_CARD) String idCard,
    @Sensitive(level = L4, encrypt = true) String bankCard
) {}
```

### 3.3 安全评审的自查清单（可提交给评审方）

```
身份与访问
  ✓ 所有对外接口都有认证（除显式白名单）
  ✓ 内部接口有网络隔离或服务间认证
  ✓ 权限校验在服务端（前端隐藏按钮不算）
  ✓ 数据级权限（只能查自己的数据）已验证（水平越权测试）
  ✓ 管理员操作有二次确认或 MFA

令牌
  ✓ access_token TTL ≤ 15min
  ✓ refresh_token 轮换，且绑定设备指纹
  ✓ 支持主动注销（黑名单/版本号）
  ✓ JWT 不含 PII

数据
  ✓ PII 字段已分级并加密/脱敏
  ✓ 日志无明文 PII（已用真实请求验证）
  ✓ 密码使用 bcrypt/argon2（非 MD5/SHA1）
  ✓ 数据库备份加密

审计
  ✓ 敏感操作全部留痕（含失败）
  ✓ 审计独立存储，应用无 UPDATE/DELETE 权限
  ✓ 有哈希链或 WORM 保证不可篡改
```

## 4. 边界条件与反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| JWT 存 localStorage | XSS 可直接窃取 | HttpOnly Cookie（refresh）+ 内存（access） |
| access_token 有效期 7 天 | 泄漏后无法挽回 | ≤15 分钟 + refresh 轮换 |
| 只靠 JWT 无状态、不做吊销 | 禁用账号后仍可用 | 版本号/黑名单 |
| JWT payload 放手机号、角色明细 | Base64 明文可读 + token 过大 | 只放 ID 与粗粒度 scope |
| 网关认证后内部接口不校验 | SSRF/横向移动可直达 | 签名头校验 + 网络隔离 |
| 认为"内网可信" | 内网横向移动是主流攻击路径 | 零信任：每个服务都校验 |
| 密码用 MD5/SHA1 加盐 | 彩虹表/GPU 破解 | bcrypt(cost≥12) / argon2id |
| 手机号明文存 | 一次拖库全量泄漏 | 加密存储 + 掩码展示 |
| 日志打印整个对象 | `toString` 带出 PII | 脱敏 converter + 白名单字段 |
| 审计表与业务同库同账号 | 可被删除/篡改 | 独立存储 + 只 INSERT + 哈希链 |
| 只记录成功操作 | 越权尝试无痕迹 | 成功与失败都记录 |
| 前端做权限控制 | 改前端即可越权 | 服务端强制校验 |

## 5. 落地检查表

**认证**

- [ ] 使用标准协议（OAuth2/OIDC），未自研令牌格式
- [ ] access_token TTL ≤ 15 分钟，refresh_token 轮换
- [ ] 支持主动吊销（版本号或黑名单），且验证过生效
- [ ] JWT 不含 PII，且使用非对称签名（RS256/ES256）
- [ ] 签名密钥支持轮换（`kid`），私钥在 KMS/Vault

**授权**

- [ ] 所有接口在服务端校验权限（含数据级权限）
- [ ] 水平越权测试通过（用户 A 无法访问用户 B 的数据）
- [ ] 网关注入的身份头有签名校验，无法伪造
- [ ] 内部服务有网络隔离（NetworkPolicy/安全组）
- [ ] 管理端操作有审计 + 敏感操作二次确认

**数据**

- [ ] PII 字段已分级（L1–L4），有处理矩阵
- [ ] 密码用 bcrypt(cost ≥ 12)/argon2id，未用 MD5/SHA1
- [ ] 敏感字段加密存储（AES-GCM），密钥支持轮换
- [ ] 日志脱敏 converter 已生效（用真实请求验证过）
- [ ] 数据库备份加密，备份访问受控
- [ ] 数据导出有权限控制与审计（防批量拖库）

**审计**

- [ ] 敏感操作全部留痕（含失败与查询类）
- [ ] 审计独立存储，应用账号只有 INSERT
- [ ] 有哈希链或 WORM 保证不可篡改
- [ ] 可按时间/用户/会话/资源检索
- [ ] 保留期符合合规要求

## 6. 三个追问

1. **为什么用 JWT + 短 TTL，而不是服务端 Session？**
   Session 天然可撤销（删了就失效），但需要共享存储（Redis）且每次请求查一次。JWT 无状态、可水平扩展、适合跨服务传递身份，代价是**不可撤销**。工程上的答案是"两者结合"：用 JWT 传递身份（性能），用版本号/黑名单恢复可撤销性（安全），用短 TTL 限制窗口。**在单体应用里，Session 反而更简单、更安全。**

2. **引入它之后，运维成本由谁承担？**
   安全机制的成本是持续的：密钥轮换（证书/签名密钥/加密密钥）、令牌黑名单的存储、审计日志的容量（金融场景每年 TB 级）、合规审计的配合。这些通常由**安全团队 + SRE** 共同承担，且必须在上线前分配预算与 owner。**"加密存储"意味着"密钥丢了数据就没了"**，密钥管理（KMS、备份、轮换流程）是必须提前设计的。

3. **当它失效时，系统如何优雅退化？**
   认证服务不可用 → 用本地公钥验签（JWT 自包含，不依赖授权服务器在线），这是 JWT 的核心优势；黑名单 Redis 不可用 → 降级为"只校验签名与过期"（放宽但可用），并告警；审计存储不可用 → **不能阻塞业务**（异步写 + 本地缓冲 + 失败重试），但要告警（审计缺失是合规风险）。

## 案例锚点：在 Polaris 里看代码、跑验证

### A. 看代码

| 知识点 | 代码位置 | 看什么 |
|---|---|---|
| §2.2 JWT 校验 | `platform/platform-starter-security/src/main/java/com/polaris/trade/security/JwtVerifier.java` | 校验签名、过期、签发者；**不校验业务权限**（那是网关与接口层的事） |
| §2.3 Token 吊销的"版本号 + 黑名单"组合 | `platform/platform-starter-security/src/main/java/com/polaris/trade/security/TokenVersionFilter.java` | 用户改密码/被踢下线时，令牌未到期也要立刻失效 |
| §2.4 内部服务身份 | `platform/platform-starter-security/src/main/java/com/polaris/trade/security/TrustedHeaderFilter.java` | 验签 `X-Internal-*` 头；没有它，`/internal/**` 就是"改个 header 就能进" |
| §2.5 日志脱敏（第一层） | `platform/platform-starter-security/src/main/java/com/polaris/trade/security/DesensitizeConverter.java` | 在日志**写出之前**抹掉 PII，而不是事后清洗 |
| §2.5 字段级加密（第三层） | `platform/platform-starter-data/src/main/java/com/polaris/trade/data/crypto/EncryptTypeHandler.java`、`platform/platform-starter-data/src/main/java/com/polaris/trade/data/crypto/AesGcmCipher.java` | 实体里是明文、库里是密文，业务代码无感；AES-256-GCM 带完整性校验 |
| §3.2 数据分级与脱敏规则 | `platform/platform-common/src/main/java/com/polaris/trade/common/security/MaskType.java`、`platform/platform-common/src/main/java/com/polaris/trade/common/security/SensitiveLevel.java` | 一次定义、三处复用（序列化 / 日志 / 导出） |

| 安全配置里的两道口子 | `platform/platform-starter-security/src/main/java/com/polaris/trade/security/PolarisSecurityAutoConfiguration.java` 第 83–87 行 | `dev-mode` 下 `/api/**`、`/internal/**` 全放开；关闭后 `/internal/**` 要求 `ROLE_INTERNAL` |

### B. 跑验证：把 dev-mode 关掉，看接口还进不进得去

```bash
scripts/up.sh min

# ① 演示模式（默认）：一条 curl 就能调内部接口
POLARIS_DEMO=true scripts/run-monolith.sh --bg
curl -s -o /dev/null -w "dev-mode 下 /internal/stock/90001 -> HTTP %{http_code}\n" \
  http://127.0.0.1:18080/internal/stock/90001
# 期望：HTTP 200

scripts/stop-monolith.sh

# ② 关掉 dev-mode：同一个请求被拦
POLARIS_SECURITY_DEV_MODE=false POLARIS_DEMO=true scripts/run-monolith.sh --bg
curl -s -o /dev/null -w "生产模式 /internal/stock/90001 -> HTTP %{http_code}\n" \
  http://127.0.0.1:18080/internal/stock/90001
# 期望：HTTP 401 或 403（而不是 404 —— 404 才说明端点没注册）
```

这个对比正是 §1 场景 C「内部接口裸奔」的最小复现：
差别只在 `polaris.security.dev-mode` 这一个开关，
而它默认是 `true`，且启动时只打一条 ERROR 日志提醒。

脱敏的验证：

```bash
grep -E "1[3-9][0-9]{9}" logs/monolith.log | head -3
# 期望：没有结果。如果打出了完整手机号，说明 DesensitizeConverter 没生效
```

### C. 看结果

| 层 | 手段 | 拦得住什么 | 拦不住什么 |
|---|---|---|---|
| 传输 | HTTPS | 链路窃听 | 端点内的越权 |
| 认证 | `JwtVerifier` | 无令牌 / 过期 / 伪造 | 已签发但应吊销的令牌 |
| 吊销 | `TokenVersionFilter` | 改密后旧令牌 | 版本号存储不可用时的降级 |
| 服务间 | `TrustedHeaderFilter` | 外部伪造内部身份 | 内网已被攻陷 |
| 存储 | `EncryptTypeHandler` + AES-GCM | 库文件泄漏、备份泄漏 | 应用被拿到密钥 |
| 输出 | `DesensitizeConverter` + `MaskType` | 日志/导出泄漏 PII | 业务代码自己 `log.info(dto)` 绕过 |

最后一列是这一篇最有价值的部分：**每一层都有它拦不住的东西**。
把这张表填满，才算真的做过安全评审。

### D. 一句话结论

安全这件事没有"做完了"的状态，只有"这一层挡住了什么、挡不住什么"的清单。
本案例的清单从最土的一条开始：`/internal/**` 不应该默认对公网可用 ——
它现在是靠一个默认 `true` 的 `dev-mode` 开关放开的，
**这个默认值本身就是一笔技术债**，上线前必须改成 `false`。
