# 15 · 可观测性三支柱的落地

> **阶段**：线上运行 / 故障响应
> **痛点**：监控大盘有 60 个图表，但出事时没人能回答"哪个接口、哪个下游、哪台机器"；日志打了 500GB/天，搜一条请求的完整链路要拼 8 个服务的日志。

---

## 1. 真实故障场景

### 场景 A：CPU 从 30% 涨到 95%，但不知道是哪个接口

大盘上 CPU、内存、QPS、RT 都在，唯独没有"按接口维度的延迟/错误率"。SRE 只能：

```
看 CPU 高 → 猜是流量涨了 → 查 QPS 没涨 → 猜是某个 SQL 慢了 → 登机器 jstack
```

**花了 40 分钟才定位到一个刚上线的报表接口。**

**根因**：指标只覆盖了"资源层"，缺少"应用层/业务层"（RED 指标）。资源指标能告诉你"生病了"，应用指标才能告诉你"哪里病了"。

### 场景 B：日志有 8 个服务的记录，但串不起来

用户投诉"下单失败"，traceId 在网关日志里有，但下游服务的日志格式是：

```
2026-10-24 21:03:11.482 INFO OrderService - create order success
```

**没有 traceId、没有用户 ID、没有订单号**。要在 8 个服务的几百万行日志里找这一次请求，等于大海捞针。

### 场景 C：100% 采样，链路存储费 3 万/月

接入 SkyWalking 后默认 100% 采样，日均 2 亿 span，ES 存储 15 天，账单 3 万/月。团队为了省钱，改成 **1% 采样**，结果：

- 出问题时，有问题的那个请求大概率没被采样；
- 只能"复现"，无法回溯。

**根因**：采样策略选错。**头采样（head-based）在入口随机决定采不采，与请求是否有价值无关**。正确做法是**尾部采样（tail-based）：先收集所有 span，在链路上报时根据"是否有错误/是否慢"决定是否保留**。

### 场景 D：告警一天 300 条，全是噪音

```
[告警] order-service CPU > 80%     （持续 30s，其实只是 GC）
[告警] order-service 5xx 率 > 1%   （持续 1min，其实是压测）
[告警] Redis 连接数 > 500          （阈值设的，离上限还有 3000）
```

值班同学第三天就把群免打扰了。**等到真故障时，告警被淹没。**

## 2. 原理剖析

### 2.1 三支柱的分工（不要混用）

| 支柱 | 回答的问题 | 数据特征 | 成本 |
|---|---|---|---|
| **Metrics** | "现在是否正常？趋势如何？" | 聚合数值、低基数、可长期存储 | 低（按时间序列计） |
| **Logging** | "这次请求发生了什么？" | 离散事件、高基数、全文 | 高（按量计） |
| **Tracing** | "请求经过了哪些服务？慢在哪一跳？" | 调用链、上下文传播、采样 | 中高（按 span 计） |

**判断用哪个**：

```
"整体 P99 涨了吗？"            → Metrics（直方图分位）
"哪个接口涨了？"               → Metrics（按 uri 维度）
"这一次请求为什么慢？"          → Tracing（看 span 耗时分布）
"这次请求为什么报错？"          → Logging（看异常栈与上下文）
```

### 2.2 黄金指标：必须落地的四个维度

**RED（面向服务）**：

| 指标 | 定义 | 落地方式 |
|---|---|---|
| **Rate** | 请求速率（QPS） | `http_server_requests_seconds_count` |
| **Errors** | 错误率 | 按 status 分组：`status=~"5.."` |
| **Duration** | 延迟分布 | Histogram → `histogram_quantile(0.99, ...)` |

**USE（面向资源）**：

| 指标 | 定义 |
|---|---|
| **Utilization** | 使用率（CPU、内存、连接池 active/max） |
| **Saturation** | 饱和度（队列长度、`hikaricp.connections.pending`、线程池 queue） |
| **Errors** | 资源层错误（OOM、连接超时、磁盘满） |

> **Saturation 是最容易被忽略、也最有预警价值的指标**：CPU 80% 可能正常，但连接池 `pending > 0` 意味着用户已经在等了。

### 2.3 Micrometer 的指标模型

```
MeterRegistry（聚合入口）
 ├─ Counter        只增不减（请求数、错误数、消息消费数）
 ├─ Gauge         瞬时值（队列长度、连接数、缓存大小）
 ├─ Timer         计时 + 分布（请求耗时 → count/sum/max + histogram）
 └─ DistributionSummary  非时间的分布（响应体大小、批量条数）
```

命名与标签规范（决定可用性）：

```java
// ✅ 好：标签是"可枚举的低基数维度"
Timer.builder("http.server.requests")
     .tag("uri", "/api/order/{id}")        // 模板化 uri，不是具体值
     .tag("method", "GET")
     .tag("status", "200")
     .register(registry)
     .record(duration);

// ❌ 坏：把用户 ID / 订单号当标签 → 基数爆炸（Prometheus 会挂）
Counter.builder("order.created").tag("orderNo", orderNo).register(registry);
```

**基数（cardinality）是指标系统最致命的成本**：

```
1 个指标 × 1000 个 orderNo = 1000 条时间序列
× 10 个实例 × 每 15s 一个点 × 保留 90 天 ≈ 5 亿个数据点
```

**规则**：标签基数总和 < 10 万。业务 ID 只能进日志和 trace，不能进 metric 标签。

### 2.4 直方图与分位数：为什么不能算平均值

```
请求耗时：1ms, 1ms, 1ms, 1ms, 1000ms
平均 = 200.8ms      ← 看起来还行，但有个用户等了 1 秒
P99  = 1000ms       ← 这才是用户实际感受
```

**Prometheus 的分位数必须在服务端算（histogram）**，不能对平均值再平均：

```java
// Micrometer：开启 percentile histogram（服务端可聚合的分桶）
management.metrics.distribution.percentiles-histogram.http.server.requests=true
management.metrics.distribution.slo.http.server.requests=50ms,100ms,200ms,500ms,1s
```

```promql
# ✅ 正确：用 bucket 计算全局 P99
histogram_quantile(0.99,
  sum by (le, uri) (rate(http_server_requests_seconds_bucket{job="order"}[5m])))

# ❌ 错误：对客户端算好的 p99 再取平均
avg(http_server_requests_seconds{quantile="0.99"})
```

### 2.5 链路追踪：上下文传播与采样

**W3C Trace Context** 是标准格式（跨语言、跨厂商）：

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                │
             │  └ trace-id（全局唯一，32 hex）    └ span-id        └ flags（01=采样）
             └ version
```

**Java 侧的接入方式**（Spring Boot 3）：

```yaml
management:
  tracing:
    sampling:
      probability: 0.1        # 10% 头采样（生产基线）
  zipkin:
    tracing:
      endpoint: http://zipkin:9411/api/v2/spans
```

```java
// 手动埋点（框架未覆盖的关键路径）
@Observed(name = "order.create", contextualName = "create-order")
public Order create(OrderCmd cmd) { ... }
```

**采样策略对比**：

| 策略 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| 头采样（head） | 入口决定，后续全部跟随 | 实现简单、开销低 | 可能漏掉错误请求 |
| 尾采样（tail） | 收集所有 span，链路上报时再决定 | **能保留所有错误/慢请求** | 需要 Collector 聚合（内存开销） |
| 自适应 | 按 QPS 动态调整比例 | 流量大时仍可控 | 实现复杂 |

**推荐组合**：

```
基线：头采样 10%（覆盖常规流量，成本可控）
+
兜底：尾部采样规则（trace 中有 error=true 或 duration>1s → 100% 保留）
+
SLO 关键接口：强制 100%（如支付、下单）
```

## 3. 工程解法

### 3.1 应用侧完整配置（Spring Boot 3 + Micrometer + OTel）

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
  metrics:
    tags:
      application: ${spring.application.name}
      env: ${ENV:dev}
    distribution:
      percentiles-histogram:
        http.server.requests: true
      slo:
        http.server.requests: 50ms,100ms,200ms,500ms,1s,3s
  tracing:
    sampling:
      probability: ${TRACE_SAMPLE:0.1}
  otlp:
    tracing:
      endpoint: http://otel-collector:4318/v1/traces
  observations:
    key-values:
      env: ${ENV:dev}
```

```java
// 业务指标：围绕"业务健康"，而不只是技术指标
@Component
@RequiredArgsConstructor
public class OrderMetrics {
    private final MeterRegistry registry;

    // 下单量（按结果分标签，可直接算成功率）
    public void orderCreated(String channel, boolean success) {
        registry.counter("biz.order.created",
                "channel", channel, "result", success ? "ok" : "fail").increment();
    }

    // 业务延迟：下单到支付完成的耗时（用 Timer 记录分布）
    public void payLatency(Duration d) {
        registry.timer("biz.order.pay.latency").record(d);
    }

    // 关键业务状态量（Gauge 绑定到已有对象，不要每次 new）
    @Bean
    public Gauge pendingOrders(OrderMapper mapper) {
        return Gauge.builder("biz.order.pending", mapper, m -> m.countByStatus("PAYING"))
                .description("处于中间态的订单数")
                .register(registry);
    }
}
```

**必须存在的业务指标清单**（每类系统都适用）：

| 指标 | 用途 |
|---|---|
| 核心业务动作成功率（下单/支付/发货） | 比 5xx 更早发现业务故障 |
| 中间态数量（待支付、待发货超时） | 发现"卡住"的订单 |
| 消息端到端延迟（生产→消费） | 发现异步链路问题 |
| 关键第三方调用成功率与延迟 | 区分"我挂了"还是"别人挂了" |

### 3.2 日志规范：结构化 + traceId + 脱敏

```xml
<!-- logback-spring.xml：JSON 输出 + MDC 注入 -->
<appender name="JSON" class="ch.qos.logback.core.ConsoleAppender">
  <encoder class="net.logstash.logback.encoder.LogstashEncoder">
    <includeMdcKeyName>traceId</includeMdcKeyName>
    <includeMdcKeyName>spanId</includeMdcKeyName>
    <includeMdcKeyName>userId</includeMdcKeyName>
  </encoder>
</appender>
```

```json
// 实际输出（一行一条，便于采集与检索）
{"@timestamp":"2026-10-24T21:03:11.482+08:00","level":"INFO",
 "logger":"c.e.order.OrderService","message":"order created",
 "traceId":"4bf92f3577b34da6a3ce929d0e0e4736","spanId":"00f067aa0ba902b7",
 "userId":"u_88231","orderNo":"202610240001","costMs":42}
```

**日志的五个规范**：

| 规范 | 说明 |
|---|---|
| 结构化（JSON） | 便于采集、检索、聚合；不要用字符串拼接 |
| 一行一条 | 多行堆栈会打散采集，改用 JSON 的 `stack_trace` 字段 |
| 必带 traceId | 由框架自动注入 MDC，业务代码不用手写 |
| 关键业务 ID 进 MDC | `userId`、`orderNo`、`tenantId`（便于按业务维度检索） |
| **禁止 PII 明文** | 手机号、身份证、银行卡必须脱敏（见 18 篇） |

```java
// MDC 的正确注入方式（在入口过滤器/拦截器里）
@Component
public class MdcFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        try {
            String uid = JwtUtils.userIdOrNull(req);          // 可能为空（未登录）
            if (uid != null) MDC.put("userId", uid);
            chain.doFilter(req, res);
        } finally {
            MDC.clear();                                      // ⚠️ 必须清理，否则线程复用时串号
        }
    }
}
```

> **MDC 不清理的后果**：Tomcat 线程复用，下一个请求的日志会带上一个请求的 userId/traceId。这个 bug 极难发现（日志看起来"串了"），但会让所有排障结论失效。

### 3.3 告警设计：从"阈值告警"到"症状告警"

**三类告警，优先级从高到低**：

| 类型 | 例子 | 特点 |
|---|---|---|
| **症状告警**（用户视角） | 下单成功率 < 99%、支付 P99 > 1s | **最该告警**，直接对应业务损失 |
| **原因告警**（组件视角） | 连接池 pending > 0、消费积压 > 10 万 | 辅助定位 |
| **资源告警**（机器视角） | CPU > 90%、磁盘 > 85% | 噪音最多，仅作参考 |

**SLO 燃尽率告警**（比固定阈值更科学）：

```promql
# 错误预算燃尽率：1 小时内消耗了 5% 的月度预算 → 相当于 6 小时就会耗尽
# 30 天 SLO 99.9%，1 小时窗口
(
  sum(rate(http_server_requests_seconds_count{status=~"5.."}[1h]))
  / sum(rate(http_server_requests_seconds_count[1h]))
) / (1 - 0.999)
```

```yaml
# 多窗口燃尽率告警（既能快速发现，又能避免抖动）
- alert: HighErrorBudgetBurn
  expr: |
    (job:slo_errors_ratio:rate1h > (14.4 * 0.001)) and
    (job:slo_errors_ratio:rate5m > (14.4 * 0.001))
  for: 2m
  labels: { severity: critical }
  annotations:
    summary: "错误预算快速燃尽，预计 2 天内耗尽月度预算"
```

**告警的四条纪律**：

1. **每条告警都必须有 runbook**（处理步骤、影响面、联系谁）；
2. **每条告警都必须有人负责**（owner），无人负责的告警直接删除；
3. **告警必须可执行**——"CPU 高"不是告警，"CPU 高且 P99 > SLO"才是；
4. **定期清理**：连续 30 天未触发的告警，要么阈值错了，要么指标没意义。

### 3.4 存储成本控制

| 数据 | 保留策略 | 降本手段 |
|---|---|---|
| Metrics | 原始 15s 粒度 15 天 → 1min 粒度 90 天 → 5min 粒度 1 年 | 降采样（recording rules）、删除无用指标、控制标签基数 |
| Logs | 热存 7 天（可全文检索）→ 冷存 90 天（压缩归档） | 分级存储、采样（DEBUG 日志关闭）、只保留结构化字段 |
| Traces | 错误/慢请求 100%，正常请求 1–10% | 尾部采样、缩短保留期（7–15 天） |

**成本估算示例**（10 个服务、日均 5000 万请求）：

```
Traces 100% 采样：5000 万 × 3 span × 1KB ≈ 150GB/天  → 15 天 = 2.2TB
Traces 5% + 全量错误：约 8GB/天                       → 15 天 = 120GB
差价：约 18 倍
```

## 4. 边界条件与反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 只监控资源指标 | 知道生病，不知道哪里病 | RED + USE 双维度 |
| 把业务 ID 当 metric 标签 | 基数爆炸，Prometheus 崩 | 业务 ID 进日志/trace |
| 用平均值看延迟 | 掩盖长尾 | P50/P90/P99 直方图 |
| 100% 采样 trace | 成本失控 | 10% 头采样 + 错误/慢请求全保留 |
| 1% 采样且无尾部策略 | 出问题时没有样本 | 尾部采样或 SLO 接口 100% |
| 日志打大对象/整段 JSON | 存储爆炸、检索变慢 | 只打关键字段 + 摘要 |
| 日志无 traceId | 无法串联 | MDC 自动注入 |
| MDC 不清理 | 日志串号，排障结论错误 | `finally { MDC.clear(); }` |
| 告警只设固定阈值 | 误报多、漏报多 | SLO 燃尽率 + 症状告警 |
| 告警无 runbook | 值班同学不知道干什么 | 每条告警配处理步骤 |
| 采样率固定不变 | 大促时成本飙升 / 故障时样本不足 | 动态采样（按 QPS 与错误率调整） |

## 5. 落地检查表

**Metrics**

- [ ] 所有 HTTP 接口有 `http.server.requests`（含 uri 模板、status、method 标签）
- [ ] 开启 percentile histogram，SLO 分桶已配置
- [ ] 有业务指标（成功率、中间态数量、第三方调用）
- [ ] 标签基数总和 < 10 万，无业务 ID 作标签
- [ ] 连接池、线程池、缓存、消息积压都有 saturation 指标

**Logging**

- [ ] 输出 JSON 结构化日志，一行一条
- [ ] traceId / spanId / userId 自动注入 MDC，且 `finally` 清理
- [ ] 无 PII 明文（手机号/身份证/银行卡已脱敏）
- [ ] 日志分级别，生产 INFO 起步，DEBUG 可动态开启
- [ ] 有冷热分级存储与保留策略

**Tracing**

- [ ] 入口生成/透传 W3C `traceparent`
- [ ] 采样率可配置，且有错误/慢请求 100% 保留策略
- [ ] 关键下游调用（DB、Redis、MQ、HTTP）自动埋点
- [ ] trace 与日志、指标可互相跳转（traceId 关联）

**告警**

- [ ] 以症状告警为主（业务成功率、SLO 燃尽），资源告警为辅
- [ ] 每条告警有 owner 与 runbook
- [ ] 告警有分级（P0/P1/P2）与对应响应时限
- [ ] 每季度清理一次无效告警（30 天未触发即复审）
- [ ] 有值班轮值与升级路径

## 6. 三个追问

1. **为什么用 Prometheus + Grafana，而不是只用云厂商 APM？**
   云 APM 开箱即用、免运维，但**成本随数据量线性增长**，且指标模型封闭（难以自定义业务指标）。自建 Prometheus 的边际成本低（指标按序列计费，聚合后存储小），适合"大量自定义业务指标 + 长期保留"的需求。实践中的组合：**Metrics 自建（Prometheus），Tracing/Logging 用托管**（这两类数据量大、运维复杂）。

2. **引入它之后，运维成本由谁承担？**
   可观测性系统本身就是一个需要运维的分布式系统：Prometheus 的存储与高可用、Collector 的吞吐、Grafana 的看板维护、告警规则的调优。**看板腐化是最常见的问题**（三个月后没人看得懂）。治理手段：每个看板有 owner、每季度评审一次、删除无人访问的面板。

3. **当它失效时，系统如何优雅退化？**
   可观测性系统挂了，不能影响业务（**必须与业务链路隔离**，异步上报、失败丢弃）。此时退化到：① 基础指标（主机层监控仍在）；② 日志（本地文件可查）；③ `jstack`/`jcmd` 直连进程。**所以"本地留一份 GC 日志和应用日志"是最后的底线**（见 02 篇）。

|---|---|---|
| §2.5 traceId 的入口 | `platform/platform-starter-web/src/main/java/com/polaris/trade/web/trace/TraceIdFilter.java` | 解析 W3C `traceparent`，没有就生成一个；**32 位小写 hex**，格式不对的必须丢弃重生成 |
| traceId 的统一出口 | `platform/platform-common/src/main/java/com/polaris/trade/common/trace/TraceIds.java` | `SAMPLE = 4bf92f3577b34da6a3ce929d0e0e4736`：文档、脚本、压测共用同一个样例 ID，保证"你按文档敲的命令和我当时跑的是同一个 trace" |
| 网关层的第一跳 | `services/gateway-service/src/main/java/com/polaris/trade/gateway/filter/TraceIdGlobalFilter.java` | 全链路 traceId 在网关生成，下游只透传 |
| 最容易漏的一环：异步传播 | `platform/platform-starter-observability/src/main/java/com/polaris/trade/observability/MdcTaskDecorator.java` | 线程池提交任务时把 MDC 复制过去。**不装这个装饰器，异步链路的日志就会丢 traceId** |
| §3.1 技术指标之外的那一层 | `platform/platform-starter-observability/src/main/java/com/polaris/trade/observability/BizMetrics.java` | 下单 QPS / 失败率 / 待支付订单数 —— 业务健康度，技术指标回答不了 |
| §3.4 采样率的可见性 | `platform/platform-starter-observability/src/main/java/com/polaris/trade/observability/ObservationSamplingLogger.java` | 启动时把"当前生效的采样率"打出来。采样率配错时，人只会以为"链路丢了" |
| 告警规则 | `deploy/prometheus/rules/jvm.yml` | 6 条：堆使用率、**堆外占比**、GC 停顿比、队列饱和度、拒绝次数、弱依赖降级 |
| 看板 | `deploy/grafana/dashboards/overview.json`、`deploy/grafana/dashboards/jvm.json` | 「Polaris · 总览」含下单 QPS / 失败率 / 待支付订单（业务三指标） |

### B. 跑验证：把一根 traceId 从入口追到日志

```bash
scripts/up.sh obs            # + prometheus + grafana（≈5.4GB，做完就 down）
POLARIS_DEMO=true scripts/run-monolith.sh --bg

# 1) 带着固定 traceId 发一笔请求
curl -s -X POST http://127.0.0.1:18080/api/order \
  -H 'Content-Type: application/json' \
  -H 'traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01' \
  -d '{"userId":"u_88231","merchantId":8821,"skuId":90001,"quantity":1}'

# 2) 在日志里把这根链路捞出来
grep 4bf92f3577b34da6a3ce929d0e0e4736 logs/monolith.log
```

期望：同一个 traceId 会出现在**多个层面**的日志行里 —— HTTP 入口、应用服务、
TCC 冻结、outbox 写入。如果只有入口那一行有 traceId，说明 MDC 没传播到下游
（`MdcTaskDecorator` 没装上，或日志 pattern 没带 `%X{traceId}`）。

```bash
# 3) 看指标
curl -s http://127.0.0.1:18080/actuator/prometheus | grep -E "^executor_rejected_total|^biz_order"

# 4) 看板
# Prometheus: http://127.0.0.1:19090
# Grafana:    http://127.0.0.1:13000  → 看板「Polaris · 总览」/「Polaris · JVM」
```

### C. 看结果：三支柱各自能回答什么

| 支柱 | 回答的问题 | 本案例的落点 | 成本 |
|---|---|---|---|
| Metrics | 「现在还正常吗」 | `BizMetrics` + `ExecutorMetrics` + 6 条告警 | 低（聚合后存储） |
| Logging | 「刚才发生了什么」 | `TraceIdFilter` + `MdcTaskDecorator` + pattern 带 `%X{traceId}` | 中（量最大） |
| Tracing | 「这条链路卡在哪一跳」 | `TraceIdGlobalFilter` + 跨服务透传 | 高（全量采样扛不住） |

> 一个反复出现的教训：**指标名写错，看板就静默空白**。
> `executor.active` 被 Micrometer 转成 `executor_active`（只换 `.`，**没有** `_threads` 后缀）。
> 命名对不上时，表现不是报错，是图画不出来 —— 所以 `ExecutorMetrics` 里的名字是照着
> 实际输出核过的，不是照文档猜的。

### D. 一句话结论

可观测性的验收标准不是"有没有三件套"，而是**能不能在不知道问题是什么的情况下，
用 3 分钟定位到是哪一跳出的问题**。本案例的答案依赖一个很土的东西：
所有日志都带同一个 traceId，包括异步线程里的那些。
技术选型换了多少轮，这一条都没变过。
