# 14 · 代码质量与安全左移

> **阶段**：日常开发 / 代码评审
> **痛点**：SonarQube 接了，扫出 2 万个 issue，没人看；依赖漏洞报告 300 个 CVE，全是 Critical，结果真正危险的那个被淹没了；上线前安全评审，才发现日志里躺着明文身份证号。

---

## 1. 真实故障场景

### 场景 A：2 万个 issue 的"质量平台"

某团队接入 SonarQube 默认规则（"Sonar way"），首扫结果：

```
Bugs: 1,247    Vulnerabilities: 386    Code Smells: 18,432
Duplications: 12.4%    Coverage: 31%
```

三个月后，issue 数量变成 2.1 万——因为**没人处理，新代码继续累积**。质量平台变成了"一个大家都知道存在但没人打开的网站"。

**根因**：默认规则集是为"通用最佳实践"设计的，与企业实际风险不匹配。一个 `TODO` 注释和一个 SQL 注入被列为不同等级，但**数量和噪音把真正的问题埋了**。

### 场景 B：CVE 优先级判错的代价

依赖扫描报告了 340 个 CVE，其中 42 个 CRITICAL。团队按 CVSS 分数排序，花了两周升级了 40 个包（大部分用不到那个漏洞函数），结果**真正有风险的没修**：

```
jackson-databind 2.13.0  CVE-2020-36518  CVSS 7.5（HIGH，不是 CRITICAL）
  → 实际可被触发：接口接收 JSON，攻击者可构造深层嵌套导致栈溢出（DoS）
  → 该接口暴露在公网

commons-fileupload 1.4  CVE-2023-24998  CVSS 7.5
  → 代码里根本没有使用文件上传
  → 修复优先级应为 P3
```

**根因**：CVSS 衡量的是"漏洞本身的严重程度"，不是"你的系统被利用的可能性"。**优先级 = CVSS × 可达性 × 暴露面**。

### 场景 C：密钥泄漏在 Git 历史里

半年后做安全检查，`gitleaks` 扫出：

```
Found leaked AWS Access Key in commit a3f2c1d (2025-03-12)
  file: src/main/resources/application-prod.yml
```

虽然当前文件已删除密钥，但**历史 commit 里还在**，仓库有 200 个协作者。最终处置：轮换密钥（影响 3 个系统）+ 重写历史（所有协作者要重新 clone）。

### 场景 D：Code Review 漏掉的 `${}` 注入

一个 PR 里新增了 `ORDER BY ${sortField}`，reviewer 看的是"业务逻辑对不对"，没注意拼写方式。上线 2 个月后被外部渗透测试发现。

**根因**：**人会疲劳，规则不会**。这类问题应该由 SAST 自定义规则在 CI 里拦截，而不是靠人眼。

## 2. 原理剖析

### 2.1 静态分析的三种技术路线

| 技术 | 原理 | 能发现 | 误报率 |
|---|---|---|---|
| **模式匹配**（Checkstyle/PMD） | 正则/AST 模式 | 命名规范、空 catch、`==` 比较字符串 | 低 |
| **数据流分析**（SpotBugs） | 追踪变量从赋值到使用 | 空指针、资源未关闭、并发问题 | 中 |
| **污点分析**（Semgrep/CodeQL） | 从"源"（用户输入）追踪到"汇"（SQL 执行） | **SQL 注入、XSS、命令注入** | 中高（需调规则） |

**污点分析的价值**——它是唯一能自动发现"注入类"问题的技术：

```yaml
# Semgrep 自定义规则：禁止 MyBatis XML 中用 ${} 接收参数
rules:
  - id: mybatis-dollar-injection
    languages: [generic]
    severity: ERROR
    message: "禁止使用 ${} 拼接参数（SQL 注入风险），改用 #{}；标识符必须白名单校验"
    paths:
      include: ["**/mapper/**/*.xml"]
    pattern-regex: '\$\{[^}]+\}'
```

```yaml
# 禁止把用户输入直接拼进 SQL 字符串
  - id: java-sql-string-concat
    languages: [java]
    severity: ERROR
    message: "检测到 SQL 字符串拼接，改用参数化查询（PreparedStatement / Mapper #{}）"
    patterns:
      - pattern-either:
          - pattern: $X.execute($A + $B)
          - pattern: $X.executeQuery("..." + $B)
          - pattern: |
              String $SQL = "..." + $B;
              ...
              $X.execute($SQL);
```

### 2.2 质量门禁：为什么门禁要针对"新增代码"

**"Clean as you code"** 原则：不要求一次性还清历史债，但**新代码必须是干净的**。

```yaml
# SonarQube Quality Gate 配置
条件（针对 New Code，即最近一次合并后的变更）：
  - Coverage on New Code          ≥ 80%
  - Duplicated Lines on New Code  ≤ 3%
  - Blocker Issues                = 0
  - Critical Issues               = 0
  - Security Hotspots Reviewed    = 100%
  - Maintainability Rating        = A
```

**为什么不对全量代码设门禁**：

| 策略 | 结果 |
|---|---|
| 全量覆盖率 ≥ 80% | 老系统永远达不到 → 门禁被关闭 → 等于没有 |
| 全量 0 Blocker | 历史 issue 清不完 → 团队放弃 |
| **新增代码 0 Blocker + 80% 覆盖** | 债务不再增加，老代码逐步改善 → 可持续 |

### 2.3 依赖漏洞的优先级模型

```
风险 = CVSS × 可达性 × 暴露面 × 数据敏感度
```

| 因子 | 判断方法 | 权重 |
|---|---|---|
| **CVSS 分数** | 官方评分（0–10） | 基础分 |
| **是否可达** | 代码里是否调用了受影响的方法/类（`mvn dependency:tree` + 代码搜索 / SCA 工具的可达性分析） | ×3（不可达直接降为 P3） |
| **暴露面** | 触发路径是否来自公网/不可信输入 | ×2 |
| **数据敏感度** | 影响的是资金/PII 还是日志模块 | ×2 |
| **是否有 PoC/在野利用** | CISA KEV 清单、EPSS 分数 | ×2 |

```bash
# 1. 看依赖树：这个包是谁引入的？能否升级？
mvn dependency:tree -Dincludes=com.fasterxml.jackson.core:jackson-databind

# 2. 看是否有代码使用受影响类
grep -rn "ObjectMapper" src/main/java | head

# 3. 看 EPSS（利用概率）与 KEV（在野利用）
curl -s "https://api.first.org/data/v1/epss?cve=CVE-2020-36518"
```

**分级响应 SLA**（写进团队规范）：

| 级别 | 条件 | 修复时限 |
|---|---|---|
| P0 | 公网可达 + 有 PoC/在野利用 + 影响认证/资金 | 24 小时（或立即下线相关接口） |
| P1 | 可达 + CVSS ≥ 9 + 暴露于不可信输入 | 7 天 |
| P2 | 可达 + CVSS 7–8.9 | 30 天 |
| P3 | 不可达 / 仅本地 / 需要管理员权限 | 90 天或随版本升级 |
| 例外 | 无法升级（如依赖锁死） | 记录 VEX 声明 + 补偿控制（WAF 规则、网络隔离） |

> **VEX（Vulnerability Exploitability eXchange）** 是"声明这个漏洞对我不可利用"的标准格式，很多安全评审开始接受它作为例外依据。比"写个 Excel 说我们不修"专业得多。

### 2.4 SBOM：供应链可见性

```
SBOM（Software Bill of Materials）= 制品里所有组件的清单
格式：SPDX / CycloneDX
内容：组件名、版本、许可证、哈希、依赖关系
```

```bash
# 生成 SBOM（构建时）
syft $IMAGE -o cyclonedx-json > sbom.json

# 或 Maven 插件
mvn org.cyclonedx:cyclonedx-maven-plugin:makeAggregateBom
```

**SBOM 的三个用途**：

1. **漏洞爆发时快速定位影响面**（"Log4Shell 出了，我们哪些服务用了 log4j-core？"→ 查 SBOM，5 分钟出结果，而不是逐个服务排查）；
2. **许可证合规**（GPL 传染性、商用限制）；
3. **审计要求**（金融/政企的供应链安全审查已开始强制要求）。

## 3. 工程解法

### 3.1 SonarQube 规则集的裁剪策略

**四步裁剪法**：

```
① 保留（必须开启）
   - 所有 Blocker / Critical 级别的 Bug 与 Vulnerability
   - 安全热点（Security Hotspot）全部开启（人工确认制）
   - 团队自定义规则（如"禁止 System.out"、"禁止 new Date()"）

② 调整等级
   - 与团队规范冲突的规则 → 降级或关闭（如强制 javadoc 在内部服务里是噪音）
   - "代码味道"类规则 → 只对新增代码生效

③ 关闭（噪音源）
   - 与框架冲突的（如 Spring 的字段注入警告，团队已统一用构造器注入）
   - 过度严格的重构建议（方法行数、类行数）
   - 对生成代码（DTO/MapStruct）的规则

④ 例外管理
   - 确需豁免的 → 代码里 @SuppressWarnings + 注释原因（可追溯）
   - 不允许在平台里"批量标记为 false positive"
```

**推荐的规则关注点**（Java 场景）：

| 类别 | 具体规则 | 理由 |
|---|---|---|
| 安全 | SQL 注入、命令注入、路径穿越、XXE、不安全反序列化 | 直接导致入侵 |
| 安全 | 硬编码凭证、弱加密算法（MD5/DES）、`Random` 用于令牌 | 高频真实事故 |
| 可靠性 | 空指针解引用、资源未关闭、`catch` 空块 | 直接导致线上错误 |
| 可靠性 | `SimpleDateFormat` 静态共享、`HashMap` 并发访问 | 偶发、难排查 |
| 可维护性 | 重复代码块（阈值 3%） | 变更成本 |

```java
// 自定义规则示例：禁止在生产代码中使用 System.out / printStackTrace
// （用 ArchUnit 或 Checkstyle 也能实现，关键是"能被 CI 阻断"）
@ArchTest
static final ArchRule no_system_out =
    noClasses().should().callMethod(System.class, "out")
        .orShould().callMethod(Throwable.class, "printStackTrace");
```

### 3.2 依赖治理流水线

```yaml
# ① PR 阶段：只扫描变更引入的依赖（快）
dependency-check-pr:
  stage: scan
  script:
    - mvn -B org.owasp:dependency-check-maven:check \
        -DfailBuildOnCVSS=9 \
        -DsuppressionFiles=security/owasp-suppressions.xml

# ② 每日定时：全量扫描 + SBOM 生成
dependency-check-nightly:
  stage: scan
  rules: [{ if: '$CI_PIPELINE_SOURCE == "schedule"' }]
  script:
    - mvn -B org.cyclonedx:cyclonedx-maven-plugin:makeAggregateBom
    - trivy sbom target/bom.json --severity HIGH,CRITICAL --exit-code 0   # 只报告，不阻断
```

**例外管理文件**（suppressions，必须有人签字）：

```xml
<!-- security/owasp-suppressions.xml -->
<suppress>
  <notes><![CDATA[
    CVE-2023-24998: commons-fileupload。
    影响面：本项目不使用文件上传功能（已全仓库搜索确认）。
    负责人：张三  复核日期：2026-10-01  下次复核：2027-01-01
  ]]></notes>
  <packageUrl regex="true">^pkg:maven/commons-fileupload/commons-fileupload@.*$</packageUrl>
  <cve>CVE-2023-24998</cve>
</suppress>
```

**依赖升级的自动化**（Renovate / Dependabot）：

```json
// renovate.json —— 自动开 PR，但按风险分级合并
{
  "extends": ["config:base"],
  "packageRules": [
    { "matchUpdateTypes": ["patch"], "automerge": true },
    { "matchUpdateTypes": ["minor"], "automerge": false, "groupName": "minor updates" },
    { "matchUpdateTypes": ["major"], "dependencyDashboardApproval": true },
    { "matchPackagePatterns": ["^org.springframework"], "groupName": "spring" }
  ],
  "vulnerabilityAlerts": { "labels": ["security"] }
}
```

> **自动合并 patch 版本**是被验证有效的做法（前提：有足够的测试覆盖）。它把"依赖升级"从"季度专项"变成"持续小步"，显著降低大版本升级的痛苦。

### 3.3 密钥与敏感数据的左移防护

**三道防线**：

```
① 提交前（本地 hook）：gitleaks protect --staged
   → 在 commit 时拦截，成本最低

② CI 中：gitleaks detect --no-git（扫全仓库历史）
   → 拦截已推送的泄漏

③ 运行时：镜像扫描 + 配置审计（禁止明文密钥进镜像）
```

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0
    hooks:
      - id: gitleaks
```

```bash
# 已泄漏的处置流程（顺序不能错）
1. 立即轮换密钥（先止血，不要先改代码）
2. 评估影响面（这个 key 能访问什么？日志里有没有异常调用？）
3. 清理当前代码
4. 决定是否重写历史（涉及协作者数量、仓库是否公开）
5. 补充检测规则（这类密钥为什么没被 gitleaks 拦住？）
```

**重写历史**（仅当仓库范围可控时）：

```bash
# 用 git-filter-repo（比 filter-branch 快且安全）
git filter-repo --path application-prod.yml --invert-paths
# 之后：强制推送 + 通知所有协作者重新 clone
```

### 3.4 安全左移的落地节奏

| 阶段 | 措施 | 谁做 |
|---|---|---|
| 编码时 | IDE 插件（SonarLint、Semgrep）实时提示 | 开发者 |
| 提交时 | pre-commit hook（格式、密钥、危险 API） | 开发者（工具强制） |
| PR 时 | SAST + 依赖扫描 + 门禁 | CI |
| 构建时 | SBOM + 镜像扫描 + 签名 | CI |
| 部署前 | DAST（对预发环境跑 ZAP 扫描） | 安全/QA |
| 运行时 | RASP / WAF / 异常行为告警 | SRE |

**关键原则：越靠左，修复成本越低。**

```
编码时发现：5 分钟
PR 时发现：30 分钟
测试时发现：4 小时
上线后发现：2 天（含应急、复盘、客诉处理）
数据泄漏后：不可估量
```

## 4. 边界条件与反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 接入 Sonar 默认规则全开 | 噪音淹没真问题，团队放弃 | 四步裁剪 + new code 门禁 |
| 覆盖率门禁设全量 80% | 老系统永远达不到 → 门禁被关 | 只对新增代码设门禁 |
| 按 CVSS 排序修 CVE | 修了不可达的，漏了可达的 | CVSS × 可达性 × 暴露面 |
| 扫描报告只"生成"不"处置" | 报告变成摆设 | 有 SLA、有 owner、有例外审批 |
| 依赖锁死永不升级 | 一次升级跨越 5 个大版本，风险更高 | Renovate 持续小步 + patch 自动合并 |
| 密钥泄漏只删代码不轮换 | 历史与日志里仍有，随时可用 | **先轮换，再清理** |
| 用 `@SuppressWarnings` 批量消警告 | 掩盖真实问题 | 每个豁免必须有注释原因 + 复核日期 |
| DAST 放到上线后 | 发现问题已来不及 | 对预发环境扫描 |
| 安全评审只是"填表" | 走形式，无实质检查 | 评审清单化（见 18 篇）+ 自动化证据 |

## 6. 三个追问

1. **为什么用 Sonar 自建，而不是只用 IDE 插件？**
   IDE 插件是"个人自律"，Sonar 是"组织护栏"。前者依赖每个开发者的自觉（且无法阻止"我本地就是不改"），后者能在合并前强制拦截。代价是维护一套平台（服务器、规则、升级）。**小团队（<5 人）可以只用 IDE 插件 + PR 模板；超过 10 人，平台化的门禁几乎必需。**

2. **引入它之后，运维成本由谁承担？**
   质量平台的成本不是"装一次"，而是**规则维护 + 例外审批 + 漏洞跟踪 + 升级**。规则过严团队会绕过，过松等于没有，这个平衡需要持续调。通常由**技术负责人 + 安全团队**共同承担，且要有固定的评审节奏（每季度一次）。

3. **当它失效时，系统如何优雅退化？**
   扫描器误报导致流水线卡住 → 有例外审批通道（不阻塞发布）；新的 CVE 爆发且无法立即修复 → 用 WAF/网络隔离等补偿控制 + VEX 声明；密钥泄漏 → 先轮换（止血）再清理。**安全左移不能变成"安全阻塞一切"**——它必须有降级路径，否则团队会整体绕过它。

## 案例锚点：在 Polaris 里看代码、跑验证

### A. 看代码

| 知识点 | 代码位置 | 看什么 |
|---|---|---|
| 编译期就拦下的那类问题 | `pom.xml` → `maven-compiler-plugin` | `-Xlint:all,-processing,-serial`：忽略告警清单是**枚举出来的**，不是"全关" |
| 用测试锁住"反直觉的约定" | `platform/platform-starter-guard/src/test/java/com/polaris/trade/guard/concurrent/BulkheadIsolationTest.java` | 4 项断言，其中一条锁的是「超时返回 ≠ 线程释放」——这种反直觉的事实只能靠测试守住 |
| 用测试锁住值语义 | `platform/platform-common/src/test/java/com/polaris/trade/common/money/MoneyTest.java` | 5 个用例，含"99.0 与 99.00 是同一笔钱" |
| 单飞合并的边界 | `platform/platform-starter-data/src/test/java/com/polaris/trade/data/cache/SingleFlightTest.java` | 并发下"只回源一次"是可断言的 |
| 安全左移的一个具体落点 | `services/order-service/src/main/resources/mapper/OrderQueryMapper.xml` → `pageUnsafe` | 反面教材**留在仓库里**并注释了攻击 payload。评审时"看到 `${}` 就问一句"这个反射，只能靠对照建立 |
| 文档也会腐烂，所以也要校验 | `tools/check_docs.py` | 把"文档里写的路径是否还存在"变成可执行检查。这是本仓库对"质量左移"的自举：文档失效也是缺陷 |

### B. 跑验证：三道已经存在的闸门


### C. 看结果

| 质量手段 | 本仓库现状 | 拦得住什么 |
|---|---|---|
| 编译期 `-Xlint:all` | **已启用** | 未使用变量、不安全转换、缺失 `finally` 等 |
| 单元测试 | **25 个**，覆盖金额/状态机/单飞/舱壁/缓存键 | 反直觉行为的回归 |
| 文档锚点校验 | **已启用**（`check_docs.py`） | 文档指向不存在的文件 |
| SonarQube / SpotBugs | **未接入**，M9 | 复杂度、重复度、空指针模式 |
| 依赖漏洞扫描（OWASP DC / Trivy） | **部分**：`pom.xml` 里的 `bannedDependencies` 禁已知 CVE 版本区间 | 已知漏洞的旧依赖 |
| SAST（Semgrep / CodeQL） | **未接入**，M9 | `${}` 注入这类模式 |

> 关于"只禁漏洞区间"这个选择：`pom.xml` 里禁的是
> `commons-collections:commons-collections:[,3.2.2)`，而不是整个 artifact。
> 一刀切会让整条依赖链无法解析，团队转头就去删规则 —— **规则一旦被删就再也不会回来**。
> 这是依赖治理最常见的失败模式，也是"安全左移"最容易做成"安全表演"的地方。

### D. 一句话结论

质量左移的判据不是"接了几个扫描工具"，而是**有多少问题在合并前就被拦下来了**。
本案例能拿出的数字是：25 个单测 + 1 个文档校验器 + 1 条依赖禁入规则，
每一项都对应一个真实踩过的坑（金额精度、单飞边界、舱壁释放、文档腐烂）。
**测试写的是"我曾经错过什么"，不是"代码覆盖率"。**
