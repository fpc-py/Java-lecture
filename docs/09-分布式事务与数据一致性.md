# 09 · 分布式事务与数据一致性

> **阶段**：跨服务业务设计 / 数据一致性治理
> **痛点**：一个业务动作横跨三个服务，A 扣款成功、B 加款失败，账对不上；引入了 Seata 之后，性能掉了 40%，而且"全局回滚"本身也会失败。

---

## 1. 真实故障场景

### 场景 A：转账 100 元，钱凭空消失

```
account-service:  A 账户 -100（本地事务提交 ✅）
points-service:   A 积分 +100（RPC 超时，实际未执行 ❌）
```

用户看到"转账成功"提示，但积分没到。人工补积分时又因为"没记录"而被当作重复发放拦截。

**根因**：两个服务各自本地事务，没有跨服务的原子性。而 RPC 超时这个"结果未知"状态，是最难处理的——它既不是成功也不是失败。

### 场景 B：TCC 的 Cancel 把已成功的业务取消了

```java
// Try：冻结 100 元
// Confirm：扣减冻结
// Cancel：解冻
```

故障时序：

```
t0  Try 执行成功（冻结 100）
t1  协调者调用 Confirm 超时（网络抖动，实际 Confirm 已成功）
t2  协调者重试 Confirm，业务侧已扣减，返回"幂等成功" —— 正常
---
另一种情况：
t0  Try 请求超时，但实际到达并执行成功（悬挂）
t1  协调者认为 Try 失败，发起 Cancel → 解冻了一笔"本该冻结"的钱
t2  真正的 Try 请求此时才被处理 → 又冻结一次
```

TCC 有**三个必须自己处理的坑**：

| 坑 | 现象 | 解法 |
|---|---|---|
| **空回滚** | Try 未执行（或未到达），Cancel 先到 → 解冻了不存在的数据 | Cancel 判断"是否存在 Try 记录"，无记录则插入一条"已取消"的占位记录 |
| **悬挂** | Cancel 先于 Try 执行，之后 Try 才到 → 数据被冻结但永不释放 | Try 执行前检查是否有"已取消"的占位记录，有则直接返回成功不执行 |
| **幂等** | Confirm/Cancel 重复调用 | 每个阶段都要幂等（状态机 + 唯一键） |

### 场景 C：本地消息表发了消息，但业务回滚了

```java
@Transactional
public void createOrder(OrderCmd cmd) {
    orderMapper.insert(order);
    mqTemplate.send("order-created", order.getId());   // ⚠️ 消息先发出去了
    // 后面抛异常 → 事务回滚，订单不存在，但消息已发出
}
```

消费方收到"订单已创建"事件，回查订单却是 404。这是**消息发送与本地事务的原子性问题**，不是 MQ 的问题。

## 2. 原理剖析

### 2.1 先问"能不能不要分布式事务"

这是本篇最重要的一节。**90% 的"分布式事务需求"，本质是服务边界画错了。**

```
需求：一个业务动作要保证 3 个服务的数据一致
  │
  ├─ 这 3 份数据真的属于不同的"聚合根/限界上下文"吗？
  │    ├─ 否 → 服务拆错了，合并回一个服务，用本地事务（最优解，成本为 0）
  │    └─ 是 ↓
  │
  ├─ 业务真的要求"强一致"（秒级、零容忍）吗？
  │    ├─ 否（大多数场景：允许 1–5 秒最终一致）→ 最终一致方案（本地消息表 / 事务消息 / 对账）
  │    └─ 是 ↓
  │
  ├─ 能接受 2PC 的性能与可用性代价吗？（同步阻塞、协调者单点、全局锁）
  │    ├─ 能（内部低并发核心系统）→ Seata AT / XA
  │    └─ 否 → TCC / Saga（业务侵入大，但性能好）
  │
  └─ 无论选哪种，"最终兜底"永远是：对账 + 补偿 + 人工介入
```

**真实的工程优先级**：

```
避免分布式事务  >  最终一致（异步）  >  TCC / Saga  >  AT / XA 2PC
   （重构）        （本地消息表）      （业务侵入）    （性能最差）
```

### 2.2 五种方案的本质对比

| 方案 | 一致性 | 性能 | 业务侵入 | 隔离性 | 适用 |
|---|---|---|---|---|---|
| **2PC / XA** | 强一致 | 差（同步阻塞，持锁到全局提交） | 无 | 强（全局锁） | 内部系统、低并发、跨库操作 |
| **Seata AT** | 强一致（读未提交级别） | 中（一阶段本地提交 + undo log，二阶段异步） | 无（注解） | **弱**（全局锁只锁行，期间可能读到中间态） | 大多数"不想改代码"的场景 |
| **TCC** | 强一致（业务补偿） | 好（无长事务锁） | **高**（每个操作写 3 个方法） | 中（靠资源预留实现隔离） | 资金、库存等核心资源 |
| **Saga** | 最终一致 | 好 | 中高（每个正向操作配补偿） | 无 | 长流程（订单履约、跨系统编排） |
| **本地消息表 / 事务消息** | 最终一致 | 最好 | 低 | 无 | 异步解耦的绝大多数场景 |

### 2.3 Seata AT 的工作机制与代价

```
一阶段（业务 SQL 执行时）：
  ① 解析 SQL，生成前后镜像（beforeImage / afterImage）
  ② 写 undo_log（与业务 SQL 同库同事务）
  ③ 注册分支事务，向 TC 申请全局锁（锁的是行主键）
  ④ 本地事务直接提交  ← 这是它比 XA 快的原因

二阶段：
  提交 → 异步删除 undo_log（很快，无锁）
  回滚 → 用 beforeImage 生成反向 SQL 补偿（需要再次获取全局锁校验）
```

**AT 模式的三个隐性成本**：

| 成本 | 说明 |
|---|---|
| **全局锁竞争** | 同一行数据被全局事务锁住期间，其他全局事务必须等待 → 热点行（如库存）QPS 骤降 |
| **读未提交** | 一阶段已提交，其他事务能读到"中间态"；只有全局事务参与者之间通过全局锁隔离 |
| **undo_log 膨胀** | 大事务（批量更新 10 万行）会写出巨大的 undo_log，回滚极慢甚至失败 |

```yaml
# Seata 关键配置
seata:
  enabled: true
  application-id: order-service
  tx-service-group: my_tx_group
  service:
    vgroup-mapping:
      my_tx_group: default
  client:
    rm:
      lock:
        retry-interval: 10        # 全局锁重试间隔（ms）
        retry-times: 30           # 重试 30 次 = 300ms，热点行要调大
      report-success-enable: false
```

> **AT 的适用边界**：单次全局事务涉及的表不超过 3 张、更新行数不超过 1000、无热点行竞争。超出这个范围，性能会断崖式下跌。

### 2.4 TCC 的"三个坑"与标准实现

```java
public interface AccountTccAction {
    @TwoPhaseBusinessAction(name = "deduct", commitMethod = "confirm", rollbackMethod = "cancel")
    boolean tryDeduct(BusinessActionContext ctx, @BusinessActionContextParameter(paramName = "userId") Long userId,
                      @BusinessActionContextParameter(paramName = "amount") BigDecimal amount);
    boolean confirm(BusinessActionContext ctx);
    boolean cancel(BusinessActionContext ctx);
}
```

**防悬挂 + 防空回滚的标准写法**（用一张 TCC 事务记录表）：

```sql
CREATE TABLE t_tcc_record (
    xid        VARCHAR(128) NOT NULL,
    branch_id  BIGINT       NOT NULL,
    status     TINYINT      NOT NULL COMMENT '1=TRY, 2=CONFIRM, 3=CANCEL',
    amount     DECIMAL(18,2),
    PRIMARY KEY (xid, branch_id)
);
```

```java
// Try
@Transactional
public boolean tryDeduct(String xid, long branchId, Long userId, BigDecimal amount) {
    // 防悬挂：若已存在 CANCEL 记录，说明 Cancel 先到了，Try 必须拒绝执行
    TccRecord exist = recordMapper.selectById(xid, branchId);
    if (exist != null && exist.getStatus() == CANCEL) {
        return true;    // 视作成功但不做任何事
    }
    accountMapper.freeze(userId, amount);      // 冻结（不是扣减）
    recordMapper.insert(xid, branchId, TRY, amount);
    return true;
}

// Cancel（幂等 + 防空回滚）
@Transactional
public boolean cancel(String xid, long branchId) {
    // 空回滚：没有 Try 记录 → 插入占位记录，防止后续 Try 再执行
    recordMapper.insertIgnore(xid, branchId, CANCEL, null);

    TccRecord rec = recordMapper.selectById(xid, branchId);
    if (rec.getStatus() == CANCEL && rec.getAmount() == null) {
        return true;    // 空回滚，无需解冻
    }
    if (rec.getStatus() == CANCEL) {
        return true;    // 已取消，幂等返回
    }
    accountMapper.unfreeze(rec.getUserId(), rec.getAmount());
    recordMapper.updateStatus(xid, branchId, CANCEL);
    return true;
}
```

**TCC 的设计铁律**：

1. Try 只做**资源预留**（冻结、预占、锁定），不做真实扣减；
2. Confirm / Cancel 必须**幂等**且**可重试**；
3. 三者的资源校验必须能应对"跨天重试"（预留资源不能有 TTL 短于最大重试窗口）；
4. **每个 TCC 接口都要有补偿失败的告警**——TCC 补偿失败意味着"钱被冻结但永不释放"，必须人工介入。

### 2.5 本地消息表：最实用的最终一致方案

**核心思想**：把"发消息"变成"插一条本地记录"，与业务操作同事务；再由独立任务把记录投递出去。

```
① 业务事务：更新业务表 + 插入本地消息（同一本地事务，原子）
② 独立投递任务：扫未发送的消息 → 发 MQ → 标记已发送（失败则重试）
③ 消费方：幂等消费（见 08 篇）
④ 兜底：定时对账，比对两边状态
```

```sql
CREATE TABLE t_local_message (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    msg_id      VARCHAR(64)  NOT NULL UNIQUE,   -- 幂等键
    topic       VARCHAR(128) NOT NULL,
    payload     TEXT         NOT NULL,
    status      TINYINT      NOT NULL DEFAULT 0, -- 0=待发送 1=已发送 2=已消费 3=失败
    retry_count INT          NOT NULL DEFAULT 0,
    next_retry_at DATETIME   NOT NULL,
    created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    KEY idx_status_retry (status, next_retry_at)
);
```

```java
@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderMapper orderMapper;
    private final LocalMessageMapper msgMapper;

    @Transactional   // ← 关键：业务与消息在同一事务
    public void createOrder(OrderCmd cmd) {
        Order o = cmd.toOrder();
        orderMapper.insert(o);
        msgMapper.insert(LocalMessage.of("order-created", o.getId(), toJson(new OrderCreatedEvent(o))));
    }
}

@Component
@RequiredArgsConstructor
public class MessageRelay {
    private final LocalMessageMapper msgMapper;
    private final RocketMQTemplate mq;

    // 每 1s 扫一批待发送；多实例部署时用 SELECT ... FOR UPDATE SKIP LOCKED 或分布式锁分片
    @Scheduled(fixedDelay = 1000)
    public void relay() {
        List<LocalMessage> batch = msgMapper.selectPending(
                LocalDateTime.now(), 200);
        if (batch.isEmpty()) return;

        for (LocalMessage m : batch) {
            try {
                mq.syncSend(m.getTopic(), m.getPayload(), 3000);
                msgMapper.markSent(m.getId());            // status=1
            } catch (Exception e) {
                msgMapper.markRetry(m.getId(), backoff(m.getRetryCount()));   // 指数退避
            }
        }
    }
}
```

**投递任务的四个工程细节**：

| 细节 | 做法 |
|---|---|
| 多实例并发扫描 | `SELECT ... WHERE status=0 AND next_retry_at <= now() ORDER BY id LIMIT 200 FOR UPDATE SKIP LOCKED` |
| 消息重复投递 | 允许（消费方幂等），但 relay 侧用 `msg_id` 去重可降低概率 |
| 消息永久失败 | `retry_count > 10` → `status=3` + 告警（人工介入） |
| 消息表膨胀 | 定期归档已发送且超过 7 天的记录（按 `created_at`） |

### 2.6 RocketMQ 事务消息：省掉消息表

```
① 发送 half message（对消费者不可见）
② 执行本地事务
③ 根据本地事务结果 commit / rollback half message
④ 若 ③ 失败（进程崩溃），Broker 回查生产者的本地事务状态
```

```java
@RocketMQTransactionListener
public class OrderTxListener implements RocketMQLocalTransactionListener {

    @Override
    public RocketMQLocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            orderService.createOrderInTx((OrderCmd) arg);     // 本地事务
            return RocketMQLocalTransactionState.COMMIT;
        } catch (Exception e) {
            return RocketMQLocalTransactionState.ROLLBACK;
        }
    }

    @Override
    public RocketMQLocalTransactionState checkLocalTransaction(Message msg) {
        // 回查：查本地事务是否成功（必须有可查的状态，如订单是否存在）
        String orderNo = (String) msg.getHeaders().get("orderNo");
        return orderMapper.existsByNo(orderNo)
                ? RocketMQLocalTransactionState.COMMIT
                : RocketMQLocalTransactionState.ROLLBACK;
    }
}
```

**代价与边界**：`checkLocalTransaction` 必须有可靠的查询依据；回查次数有限（默认 15 次），超过后消息被丢弃；只支持 RocketMQ。

## 3. 工程解法：最终一致性的"可观测性"

> 提纲里那句话值得展开：**如何证明"最终"真的到了，而不是永远在路上。**

### 3.1 三个必建指标

| 指标 | 定义 | 告警 |
|---|---|---|
| **端到端时延** | `消费时间 − 业务发生时间` 的 P50/P99 | P99 > 业务容忍窗口（如 5s）→ 告警 |
| **未完成单据数** | 处于"中间态"（如 `PAYING`）超过 N 分钟的单量 | 持续 > 0 → 告警 |
| **对账差异数** | 每日对账的不一致条数 | > 0 → 立即告警（资金类必须为 0） |

```java
// 在消息里带上业务发生时间，消费端上报端到端时延
public record OrderCreatedEvent(String orderNo, long occurredAt, String traceId) {}

// 消费端
metrics.timer("mq.e2e.latency", "topic", "order-created")
       .record(System.currentTimeMillis() - e.occurredAt(), MILLISECONDS);
```

### 3.2 对账任务的设计

```
T+1 全量对账（资金类必须）
  ├─ 数据源 A：订单库的已支付订单
  ├─ 数据源 B：支付流水库的成功流水
  ├─ 差异分类：
  │    ├─ 有订单无流水 → 补流水 / 关单
  │    ├─ 有流水无订单 → 人工核实（可能重复扣款，最高优先级）
  │    └─ 金额不一致   → 立即冻结 + 人工
  └─ 输出：差异明细表 + 告警 + 处理工单

准实时对账（可选，5 分钟粒度）
  └─ 扫描"中间态超过 5 分钟"的单据 → 主动查询下游真实状态 → 修正
```

**对账的工程要点**：

- **必须能重跑**（幂等），且能指定时间窗口；
- 差异明细要可下钻（能点进具体单据）；
- **数量对账 + 金额对账都要做**（只对条数会漏"金额错但笔数对"）；
- 对账任务本身要有监控（跑了没？耗时多久？差异多少？）。

### 3.3 补偿的设计原则

| 原则 | 说明 |
|---|---|
| 补偿必须幂等 | 会被重复调用 |
| 补偿必须可重试 | 网络问题会持续一段时间 |
| 补偿要有上限 | 重试 N 次后转人工，不要无限重试（会掩盖问题） |
| 补偿要有记录 | 每次补偿写日志表，便于复盘 |
| 补偿不能"反向破坏" | 如退款补偿失败后重试，不能退两次（用唯一退款单号约束） |

```java
// 补偿任务的骨架
@Scheduled(cron = "0 */1 * * * ?")
public void compensate() {
    List<Order> stuck = orderMapper.selectStuck(PAYING, Duration.ofMinutes(5));
    for (Order o : stuck) {
        try {
            PayStatus real = payClient.query(o.getOrderNo());     // 主动查询真实状态
            switch (real) {
                case SUCCESS -> orderMapper.casStatus(o.getId(), PAYING, PAID);
                case FAILED  -> orderMapper.casStatus(o.getId(), PAYING, CLOSED);
                case UNKNOWN -> { /* 继续等待，累计次数 */ }
            }
        } catch (Exception e) {
            log.warn("compensate failed, order={}", o.getOrderNo(), e);
        }
    }
}
```

> **CAS 更新（`WHERE status = PAYING`）是补偿的核心**：它保证补偿与正常流程并发时不会互相覆盖。

## 4. 边界条件与反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 一有跨服务就上 Seata AT | 性能损失 30–50%，热点行全局锁排队 | 先判断能否用最终一致 |
| TCC 的 Try 里做真实扣减 | 无法回滚（钱已经出去了） | Try 只做预留，Confirm 才扣减 |
| TCC 不处理空回滚/悬挂 | 资金冻结永不释放或重复冻结 | 事务记录表 + 状态机 |
| 本地消息表与业务不在同一事务 | 消息与业务不一致 | 同一本地事务；或独立表 + 定时扫描补偿 |
| 补偿任务无上限重试 | 掩盖真实问题，资源被耗尽 | 重试 N 次后转人工 + 告警 |
| 对账任务不幂等 | 重跑时重复补偿 | 用唯一键 + CAS 状态更新 |
| 用 MQ 的"至少一次"当"恰好一次" | 重复消费导致资损 | 业务幂等（见 08 篇） |
| 分布式事务内做 RPC/长耗时操作 | 全局锁持有时间过长 | 拆分成多个小事务 + Saga 编排 |
| 没有中间态监控 | 单据永远停在"处理中" | 端到端时延 + 中间态数量指标 |

## 5. 落地检查表

**设计阶段**

- [ ] 已明确回答"能否不做分布式事务"（合并服务 / 单库事务 / 最终一致）
- [ ] 方案选择有理由（一致性要求、性能预算、业务侵入成本）
- [ ] 每个跨服务流程都有"中间态"定义与超时策略
- [ ] 补偿逻辑与正向逻辑同时设计（不是事后补）

**实现阶段**

- [ ] 本地消息表与业务操作在同一本地事务
- [ ] relay 任务支持多实例安全扫描（`SKIP LOCKED` 或分片）
- [ ] 消费端幂等（唯一键 / 状态机 / 唯一约束）
- [ ] TCC 三阶段均幂等，且处理了空回滚与悬挂
- [ ] 所有状态更新使用 CAS（`WHERE status = 旧值`）
- [ ] 补偿有次数上限与人工介入通道

**可观测**

- [ ] 端到端时延有 P50/P99 指标与告警
- [ ] 中间态单据数量有监控（超时未完成即告警）
- [ ] T+1 对账任务已上线，且差异告警可达人
- [ ] 补偿执行有日志，可追溯到具体单据

## 6. 三个追问

1. **为什么用最终一致而不是 TCC/AT？**
   因为绝大多数业务的一致性要求是"用户刷新两次能看到"，而不是"毫秒级强一致"。最终一致的实现成本（一张消息表 + 一个定时任务 + 幂等 + 对账）远低于 TCC（每个操作写三份逻辑 + 处理三个坑），且性能不受影响。**只有在"资源必须预留"的场景（库存、额度、资金冻结）才值得上 TCC。**

2. **引入它之后，运维成本由谁承担？**
   分布式事务把"数据一致性"从数据库的职责转移到了**应用 + 运维**：要跑 relay 任务、要对账、要处理补偿失败、要监控中间态。这些是长期运行的负担，**每增加一个跨服务流程，就多一套需要维护的补偿与对账逻辑**。所以在架构评审时，第一个问题永远是"能不能不拆"。

3. **当它失效时，系统如何优雅退化？**
   最终一致的失效模式是"永远不一致"。所以必须有：① 中间态超时告警（发现"卡住"）；② 主动查询补偿（修正"卡住"）；③ T+1 对账（兜底所有漏网之鱼）；④ 人工工单（处理无法自动修复的）。**没有对账的最终一致，等于没有一致性。**

### A. 看代码

### B. 跑验证：把 TCC 的三个坑逐个踩一遍

```bash
scripts/up.sh min
POLARIS_DEMO=true scripts/run-monolith.sh --bg

# 准备：库存 100
curl -s -X POST "http://127.0.0.1:18080/internal/stock/demo/reset?skuId=92001&quantity=100"
```

**坑 1 · 幂等（Try 重复到达）**

```bash
for i in 1 2; do
  curl -s -X POST http://127.0.0.1:18080/internal/stock/try \
    -H 'Content-Type: application/json' \
    -d '{"orderNo":"TCC-IDEM","skuId":92001,"quantity":3}'
  echo
done
```

期望：两次都返回 `true`，但库存只冻结 **3** 件（`t_stock_tcc_record` 里只有一条记录，
`uk_xid_branch` 挡掉了第二次插入）。

**坑 2 · 空回滚（Cancel 早于 Try）**

```bash
curl -s -X POST http://127.0.0.1:18080/internal/stock/cancel \
  -H 'Content-Type: application/json' \
  -d '{"orderNo":"TCC-EMPTY","skuId":92001}'

docker exec -it polaris-mysql mysql -uroot -proot polaris_stock -e "
SELECT xid, branch_id, status FROM t_stock_tcc_record WHERE xid='TCC-EMPTY'\G"
```

期望：`status = 3`（CANCEL 占位记录被插入）。**这条记录的唯一作用就是挡住迟到的 Try**。

**坑 3 · 悬挂（Cancel 之后 Try 才到）**

```bash
curl -s -X POST http://127.0.0.1:18080/internal/stock/try \
  -H 'Content-Type: application/json' \
  -d '{"orderNo":"TCC-EMPTY","skuId":92001,"quantity":3}'
```

期望：**失败**，错误码 `STOCK_FROZEN_CONFLICT`，日志里出现

```
WARN 检测到 TCC 悬挂，拒绝 Try xid=TCC-EMPTY skuId=92001
```

三件事合起来说明：TCC 的正确性**不靠调用顺序**，靠状态机 + 唯一键把乱序变成可判定的情况。

### C. 看结果

| 坑 | 现象 | 代码里的对策 |
|---|---|---|
| 幂等 | Try 重发导致重复冻结 | `uk_xid_branch` 唯一键 + `existing != null → return true` |
| 空回滚 | Cancel 先到，没有 Try 记录 | 插入 CANCEL 占位记录 |
| 悬挂 | 占位记录存在时 Try 又到了 | 检测到 `STATUS_CANCEL` → 抛异常拒绝 |

真实链路验证（不需要手工调 TCC 端点）：

```bash
scripts/smoke-m3.sh    # 下单 → 支付 → 关单，18 条断言，含库存冻结量校验
```

### D. 一句话结论

分布式事务这一篇最反直觉的结论是 §2.1 那句「先问能不能不要分布式事务」。
本案例的顺序就是证据：先把库存冻结与订单落库放在同一个本地事务里（能不做就不做），
跨服务的部分用**本地消息表 + 消费端幂等 + 定时对账**兜住，
只有真的需要「要么全成功要么全失败」的地方才上 TCC。
TCC 不是更"高级"，它是**更贵**——三个坑每一个都要额外写代码来填。
