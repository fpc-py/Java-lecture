## 1. 背景与约束

Polaris 交易中台要同时满足两个互相拉扯的目标：

1. **教学场景**：要让读者在一台笔记本上把"下单 → 支付 → 关单"跑通，并观察
   缓存击穿、超卖、消息积压、弱依赖雪崩这些现象。多进程部署会让每个实验都先花
   半小时配环境。
2. **工程真实性**：要能演示真实的拆分代价 —— 进程内调用变成远程调用之后的
   超时、重试、部分成功、分布式事务。

当时的硬约束：

- 单机可跑（8GB 内存，容器 + 应用 + IDE 同时开）；
- 服务边界必须是**真的**边界（否则拆分那一讲无从讲起）；
- 不能维护两套业务代码（两套必然发散，讲的内容就和跑的内容对不上）。

## 2. 备选方案

| 方案 | 优点 | 放弃原因 |
|---|---|---|
| A. 只做单体 | 简单，机器压力小 | **拆分的代价讲不了** —— 没有远程调用就没有超时、重试、部分成功 |
| B. 只做微服务 | 边界真实 | 单个实验要起 7 个进程 + 4 个中间件，大多数人的机器跑不动；调一次代码要重启 7 次 |
| C. 微服务为主，另写一套单体演示版 | 两边都能演示 | **两套业务代码必然发散**，改一边忘一边，最终没人信 |
| **D. 一套代码 + 两种装配** | 业务代码只有一份；边界在 `services/*` 里是真的 | 构建配置更容易配错（见 §4） |

## 3. 决定

采用 **D：一套代码、两种装配**。

- 业务代码只存在于 `services/*`（7 个服务）与 `contract`（跨服务契约）；
- `apps/polaris-monolith` **不含一行业务代码**，只做装配：
  把 6 个服务的**普通 jar** 依赖进来，用一个 Spring Boot 启动器装进同一个 JVM
  （不含 gateway，它是 WebFlux 的，线程模型不同，混装会把两种运行时叠在一起）；
- 装配模式由 `polaris.mode` 决定：`local`（单体）/ `micro`（微服务）；
- 服务边界通过**契约层**表达：`InventoryClient`、`PayClient`、`MemberClient`、`CouponClient`
  只有接口与 DTO，实现分别落在服务方的 `Local*Client` 与调用方的 `Http*Client`。

## 4. 后果

### 4.1 好的后果

1. **同一份业务代码，两条链路**：切 `polaris.mode` 就从进程内直调变成 HTTP 调用，
   业务代码一个字不改 —— 拆分的代价因此变得可观察、可对比。
2. **实验成本低**：单体模式一个 JVM 就能跑全部 12 讲的实验。
3. **边界仍然是硬的**：没人能在 order-service 里直接 `@Autowired` 一个
   `stock` 的 Mapper，因为模块之间只依赖 `contract`。

### 4.2 代价与必须配套的三条约束

| 代价 | 配套约束 | 不遵守的后果 |
|---|---|---|
| 各服务的主产物必须是**普通 jar** | 各服务 `spring-boot-maven-plugin` 加 `<classifier>exec</classifier>`，fat jar 变副产物 | 主产物被 repackage 成 fat jar，单体依赖不进来 → `NoClassDefFoundError` |
| 六份 Flyway 脚本会在同一次迁移里撞车 | 版本号**分段**：V1xx 订单 / V2xx 库存 / V3xx 支付 / V4xx 会员 / V5xx 促销 / V6xx 通知 | 第二个 `V1__` 执行时 `FlywayException: Found more than one migration with version 1` |
| 单体下"反正同一个事务"的写法会悄悄出现 | ArchUnit 规则 `no-cross-domain-transaction`（待落地，M7） | 拆分时跨域事务全部要重写 —— 这是最大的返工来源 |

还有一条容易忽略的：**`@MapperScan` 必须显式限定注解**。
`@MapperScan(basePackages="com.polaris.trade", annotationClass=Mapper.class)` ——
只给包名会把 `contract` 里的 `InventoryClient` 这类接口也注册成 Mapper，
启动时报 `Invalid bound statement`，而且报的是别的地方。

## 5. 什么情况下应该推翻这个决定

写 ADR 最有用的一节，是提前写清"什么时候它就不再成立"：

1. **单体启动时间超过 60 秒**：说明装配已经复杂到失去教学价值；
2. **某个服务的依赖（如 gateway 的 WebFlux）无法与其余服务共存**：现在只有一个 gateway，
   再加第二个就会逼出"两套装配"；
3. **需要演示跨 JVM 的真实故障（网络分区、时钟漂移）**：单体内做不到，只能起多进程；
4. **读者机器普遍能跑 7 个进程**：约束 1 消失，B 方案重新变得合理。
