# 16 · 线上故障排查的"武器库"

> **阶段**：线上运行 / 故障响应（P1/P0）
> **痛点**：出事时第一反应是重启，重启完问题消失但根因未知，一周后复发；工具都知道名字，但真到了机器前面，不知道第一条命令敲什么。

---

## 1. 真实故障场景

### 场景 A：CPU 100%，重启后 30 分钟又 100%

```
$ top
  PID USER  %CPU  %MEM   COMMAND
 8821 app   798.3  32.1  java ...

$ jstack 8821 | grep -c "RUNNABLE"      →  187
```

重启后半小时复发。**重启只是把"正在崩溃"变成"即将崩溃"，没有解决任何问题。**

### 场景 B：接口偶发超时，日志里什么都没有

某查询接口 P99 从 80ms 涨到 3s，但错误日志为 0，慢 SQL 日志也没有。最终靠 Arthas `trace` 定位到：一个 `synchronized` 方法内部做了 HTTP 调用，锁竞争导致排队。

### 场景 C：Full GC 每 10 分钟一次，堆 dump 打不开

导出 8GB 的 hprof，MAT 加载需要 16GB 内存，打开要 20 分钟。运维同学的笔记本直接崩了。

## 2. 排查总纲：先止血，还是先定位？

这是故障响应的第一个决策，且**经常做错**。

```
故障发生
  │
  ├─ 影响面在扩大（全站不可用、资损、数据损坏）？
  │    └─ 是 → 先止血（重启/回滚/降级/限流），保留现场（dump、日志、线程栈）
  │              止血后再定位根因，不要让"找根因"耽误止血
  │
  └─ 影响面可控（局部功能、单实例）？
       └─ 是 → 先定位（现场只有一次，重启就没了）
```

**"保留现场"的最小动作**（30 秒内能做完的三件事）：

```bash
# ① 三次线程栈（间隔 5s，用于对比哪条线程卡住不动）
for i in 1 2 3; do jstack -l <pid> > /tmp/js-$i.txt; sleep 5; done

# ② GC 状态快照
jstat -gcutil <pid> 1000 10 > /tmp/gc.txt

# ③ 堆直方图（很快，看什么对象最多）
jcmd <pid> GC.class_histogram > /tmp/histo.txt
```

```bash
# 容器环境注意：进程 PID 常为 1
docker exec -it <container> jcmd 1 Thread.print > /tmp/threads.txt
kubectl exec <pod> -- jcmd 1 Thread.print > threads.txt
```

## 3. Arthas：线上诊断的主力工具

> 核心价值：**不用重启、不用加日志、不用改代码**，就能观察运行中的方法调用。

### 3.1 启动与基础命令

```bash
# 下载并启动（attach 到目标进程；容器内需同镜像同 JDK）
curl -O https://arthas.aliyun.com/arthas-boot.jar
java -jar arthas-boot.jar          # 交互式选择进程
# 或直接指定
java -jar arthas-boot.jar <pid>
```

| 命令 | 用途 | 典型场景 |
|---|---|---|
| `dashboard` | 实时面板（线程、内存、GC、最忙线程） | 首选的"看一眼" |
| `thread` | 线程状态与栈 | CPU 高、死锁、线程池打满 |
| `trace` | 追踪方法调用路径与耗时 | **定位慢方法（最高频）** |
| `watch` | 观察方法入参/返回值/异常 | 数据不对、返回值异常 |
| `profiler` | 生成火焰图 | CPU 热点 |
| `jad` | 反编译已加载的类 | 确认线上跑的是哪个版本 |
| `sc` / `sm` | 查类/方法是否加载 | 类冲突、方法未生效 |
| `ognl` | 执行表达式、读静态字段 | 读配置、调静态方法 |
| `vmtool` | 从堆里捞对象 | 查看某个 Bean 的状态 |
| `logger` | 动态改日志级别 | 临时开 DEBUG |
| `heapdump` | 导出堆 | 内存问题 |
| `monitor` | 统计方法调用次数/成功率/RT | 粗粒度监控 |

### 3.2 `thread`：CPU 高 / 死锁 / 线程池的第一现场

```bash
# 找出最忙的 5 个线程（CPU 排序）
[arthas@8821]$ thread -n 5
"http-nio-8080-exec-23" Id=45 cpuUsage=78% RUNNABLE
    at java.util.regex.Pattern$Loop.match(Pattern.java:4785)
    at com.example.validator.RegexValidator.validate(RegexValidator.java:31)
    at com.example.order.OrderService.create(OrderService.java:88)

# 查看线程池状态（按名称过滤）
[arthas@8821]$ thread --state WAITING | grep "pool-"
[arthas@8821]$ thread -n 3 -i 5000          # 每 5s 采样一次，看是否持续

# 检测死锁（JVM 级别的，synchronized/ReentrantLock）
[arthas@8821]$ thread -b
"thread-2" Id=32 BLOCKED on java.lang.Object@6f1fba17 owned by "thread-1" Id=31
```

**三次采样对比的意义**：

```bash
# 连续三次 dump，如果某线程的栈帧始终停在同一行 → 它卡住了
jstack <pid> > 1.txt; sleep 3; jstack <pid> > 2.txt; sleep 3; jstack <pid> > 3.txt
# 统计出现 3 次相同的栈顶
grep -A3 "java.lang.Thread.State" 1.txt 2.txt 3.txt | sort | uniq -c | sort -rn | head
```

### 3.3 `trace`：定位慢方法（最高频场景）

```bash
# 追踪 OrderService.create 的调用链，只显示耗时 > 50ms 的
[arthas@8821]$ trace com.example.order.OrderService create '#cost > 50'
Press Q or Ctrl+C to abort.
Affect(class count: 1 , method count: 1) cost in 88 ms
`---ts=2026-10-24 21:03:11.482;thread_name=http-nio-8080-exec-5;id=2e;
    `---[1284.33ms] com.example.order.OrderService:create()
        +---[0.12ms] OrderCmd:validate()
        +---[1180.55ms] OrderMapper:insert()          ← 罪魁祸首
        |   `---[1178.20ms] com.zaxxer.hikari.HikariDataSource:getConnection()
        +---[2.11ms] InventoryClient:deduct()
```

**一次就看清：慢在获取数据库连接上（1.18s），而不是 SQL 本身。**

常用变体：

```bash
# 只追踪特定层级的调用（减少噪音）
trace com.example.order.OrderService create -n 5 --skipJDKMethod false

# 统计方法耗时分布（不打印每次调用）
monitor -c 10 com.example.order.OrderService create

# 追踪耗时 + 记录入参（注意：会打印参数，慎用于含 PII 的方法）
trace com.example.order.OrderService create '#cost > 100' -v
```

### 3.4 `watch`：数据不对时的杀手锏

```bash
# 看入参和返回值
[arthas@8821]$ watch com.example.order.OrderService getById '{params, returnObj}' -x 2
ts=2026-10-24 21:03:11; [cost=3.2ms] result=@ArrayList[
    @Long[88231],
    @Order[
        orderNo=@String[202610240001],
        status=@Integer[3],
        amount=@BigDecimal[99.00],
    ],
]

# 只在抛异常时观察（排查"偶发异常"）
watch com.example.order.OrderService create '{params, throwExp}' -e -x 2

# 条件观察：只关心某个参数值的调用
watch com.example.order.OrderService create '{params[0], returnObj}' 'params[0].amount > 1000' -x 2

# 观察静态字段/常量（确认配置是否生效）
getstatic com.example.config.AppConfig INSTANCE
```

### 3.5 `profiler`：CPU 火焰图

```bash
[arthas@8821]$ profiler start --event cpu --duration 30
Profiling started... (will stop after 30s)
[arthas@8821]$ profiler stop --format html --file /tmp/cpu.html
```

打开 HTML 看火焰图：

```
横向看宽度  → 占 CPU 的比例
纵向看深度  → 调用栈深度
找最宽的"平顶"  → 那就是热点函数
```

**火焰图最常见的三个热点**：

| 热点形态 | 含义 |
|---|---|
| `Pattern.matcher` 很宽 | 正则回溯（正则写错了，或输入超长） |
| `String.concat` / `StringBuilder.append` 很宽 | 字符串拼接（日志、报文） |
| `HashMap.get` / `ConcurrentHashMap.get` 很宽 | 锁竞争或 GC 压力（表面是 get，实际是 GC） |

### 3.6 `jad` / `sc`：确认线上跑的是什么

```bash
# 反编译，确认线上版本（比"猜部署有没有成功"可靠）
[arthas@8821]$ jad com.example.order.OrderService | head -40

# 类是否被加载、从哪个 jar 加载（排查类冲突）
[arthas@8821]$ sc -d com.example.order.OrderService | grep -E "classLoader|codeSource"

# 方法是否存在（注解未生效时，确认方法签名是否匹配）
[arthas@8821]$ sm com.example.order.OrderService
```

## 4. 四条标准化排查路径

### 4.1 CPU 飙高

```bash
① top -Hp <pid>                       # 找出最耗 CPU 的线程（十进制 tid）
② printf '%x\n' <tid>                 # 转十六进制
③ jstack <pid> | grep -A 30 "nid=0x<hex>"   # 找到对应栈
④ 看栈顶是什么：
   ├─ 业务代码（循环/正则/序列化）→ 用 profiler 定位热点函数
   ├─ GC 线程（"GC task thread"）→ 转 4.2 内存路径
   └─ 无 Java 线程匹配 → native 线程（JNI/Netty 直接内存）
```

**常见根因与处置**：

| 栈特征 | 根因 | 处置 |
|---|---|---|
| `Pattern$Loop.match` | 正则回溯（如 `(a+)+b` 匹配超长字符串） | 改正则、限制输入长度 |
| `BigDecimal.divide` | 无限小数未指定精度（抛异常前的计算） | 指定 `RoundingMode` |
| `String.format` / `ObjectMapper.writeValue` | 大对象序列化 | 减少打印、限制体积 |
| `GC task thread` | GC 压力 | 见 4.2 |
| `Unsafe.park` + 大量 RUNNABLE | 自旋（如 `while` 轮询） | 加 sleep 或改事件驱动 |

### 4.2 Full GC / 内存泄漏

```
① 确认是 GC 问题还是真实泄漏
   jstat -gcutil <pid> 1000 20
   → Old 区持续上涨且 Full GC 后不降 → 真实泄漏
   → Old 区高但 Full GC 后能降 → 内存分配过快/堆太小

② 看什么对象占内存（heap histogram，很快，几乎无影响）
   jcmd <pid> GC.class_histogram | head -20
   → 若 byte[] / char[] / 业务对象占 80%，进一步 dump

③ 堆 dump（有 STW，业务高峰期慎用）
   jcmd <pid> GC.heap_dump /dump/heap.hprof
   # 或 Arthas：heapdump --live /tmp/heap.hprof

④ 分析（MAT）
   Leak Suspects → Dominator Tree → Path to GC Roots
   重点看"为什么回收不掉"：
   ├─ 静态集合（static Map/List 无限增长）
   ├─ ThreadLocal（线程池复用导致不释放）
   ├─ 未关闭的连接/流
   └─ 缓存无上限（Caffeine 未设 maximumSize）
```

**大 dump 文件处理技巧**：

```bash
# 1. 先看直方图，很多时候不用 dump 就能定位
jcmd <pid> GC.class_histogram

# 2. dump 时只导出存活对象（体积小 30–50%）
jcmd <pid> GC.heap_dump -all /tmp/live.hprof

# 3. 用命令行工具做初步分析（不需要 16GB 内存的笔记本）
jhat -J-Xmx4g /tmp/live.hprof        # 轻量但慢
# 或 MAT 的 ParseHeapDump + 命令行报告
mat/ParseHeapDump.sh /tmp/live.hprof org.eclipse.mat.api:suspects
```

**泄漏的六种典型模式**：

| 模式 | 特征 | 修复 |
|---|---|---|
| 静态集合只增不删 | `static Map` 大小单调增长 | 换 Caffeine（有界 + 过期） |
| ThreadLocal 未 remove | 线程池复用，对象跟随线程 | `finally { tl.remove(); }` |
| 监听器未反注册 | 每次创建都注册，永不注销 | 用弱引用或显式注销 |
| 连接/流未关闭 | `Socket`、`InputStream` 堆积 | try-with-resources |
| 缓存 Key 无界 | `orderNo` 当 key 无限增长 | 限制 key 空间 + TTL |
| 类加载器泄漏 | Metaspace 增长（动态代理/热部署） | 缓存代理类、避免重复生成 |

### 4.3 线程池打满 / 接口全超时

```bash
① 看线程数与状态分布
   jstack <pid> | grep "java.lang.Thread.State" | sort | uniq -c
   → 大量 WAITING/TIMED_WAITING 在同一个栈 → 卡在某个资源上

② 统计"卡在哪一行"（最有效的一步）
   jstack <pid> | grep -A 5 "pool-" | grep "at com.example" | sort | uniq -c | sort -rn | head
   → 输出形如：
     187     at com.example.client.PriceClient.get(PriceClient.java:45)

③ 顺着栈看是哪个下游
   → 该下游的超时/熔断是否配置？连接池是否够？
```

**四种典型卡点与处置**：

| 卡点 | 栈特征 | 止血 | 根治 |
|---|---|---|---|
| 等 DB 连接 | `HikariPool.getConnection` | 扩容实例/限流 | 优化慢 SQL、调池大小（见 05 篇） |
| 等下游 HTTP | `SocketInputStream.socketRead0` | 熔断该下游 | 加超时、降级（见 11 篇） |
| 等锁 | `ReentrantLock.lock` / `Object.wait` | 关闭相关功能 | 缩小锁范围（见 03 篇） |
| 队列堆积 | 线程 RUNNABLE 且 `queue.size` 巨大 | 扩容消费者 | 有界队列 + 拒绝策略 |

### 4.4 数据库：死锁 / 慢查询 / 连接耗尽

```sql
-- ① 当前正在执行的 SQL（谁在跑）
SELECT id, user, time, state, LEFT(info, 120) AS sql_text
FROM information_schema.processlist
WHERE command != 'Sleep' ORDER BY time DESC LIMIT 10;

-- ② 谁在等锁（MySQL 8.0）
SELECT * FROM performance_schema.data_lock_waits;
SELECT * FROM performance_schema.data_locks;

-- ③ 最近一次死锁
SHOW ENGINE INNODB STATUS\G   -- 看 LATEST DETECTED DEADLOCK 段

-- ④ 长事务（阻塞源头）
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS seconds,
       trx_mysql_thread_id, trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started LIMIT 5;
```

**止血顺序**（从伤害最小开始）：

```
① 杀掉长事务/阻塞源（KILL <thread_id>）—— 会回滚，注意影响
② 应用侧限流（Sentinel 降级该接口）
③ 只读降级（关闭写操作，保护读）
④ 切从库（如果是读压力）
⑤ 重启应用（最后手段，且必须配合限流，否则重启后立刻再挂）
```

## 5. 排查 SOP 速查表（可打印贴在工位上）

| 症状 | 第一条命令 | 常见根因 |
|---|---|---|
| CPU 高 | `top -Hp <pid>` → `jstack` 定位 | 正则回溯、序列化、GC |
| 内存涨 | `jcmd <pid> GC.class_histogram` | 静态集合、ThreadLocal、缓存无界 |
| Full GC 频繁 | `jstat -gcutil <pid> 1000 20` | 堆太小、大对象、泄漏 |
| 接口慢 | Arthas `trace <class> <method> '#cost > 100'` | 下游、DB、锁 |
| 接口 500 | `grep ERROR` 日志 + traceId | 空指针、依赖异常、数据问题 |
| 线程打满 | `jstack` 统计栈顶 | 下游超时、锁、连接池 |
| 连接池耗尽 | `hikaricp.connections.pending` 指标 | 慢 SQL、泄漏、池太小 |
| 死锁 | `SHOW ENGINE INNODB STATUS` | 加锁顺序不一致、Next-Key Lock |
| 消息积压 | 消费 lag 指标 | 分区不足、消费慢、rebalance |
| 502/504 | 网关日志 + Pod 状态 | 优雅停机、探针、后端超时 |
| 容器 OOMKilled | `kubectl describe pod` + NMT | 堆外内存（直接内存/元空间/栈） |

## 6. 边界条件与反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 出事第一反应重启 | 现场丢失，根因未知，必然复发 | 先保留现场（3 次 jstack + histogram），再决定止血 |
| 生产直接开 `-XX:+HeapDumpBeforeFullGC` | 磁盘秒满，IO 打满 | 用 `jcmd GC.heap_dump` 按需 dump |
| Arthas `watch` 观察含 PII 的方法 | 参数打进屏幕/日志，造成泄漏 | 只观察非敏感字段，或用 `-x 1` 限制深度 |
| 高峰期 `trace` 高频方法 | `trace` 有性能开销（增强字节码），可能放大故障 | 加 `#cost > N` 条件、限制次数 `-n` |
| 无限重试下游 | 把下游打得更死 | 熔断 + 有限重试（见 11 篇） |
| `jstack` 只看一次 | 无法区分"正在跑"和"卡住了" | 间隔 3–5s 采 3 次对比 |
| 用 `kill -9` 杀进程 | 连接不释放、事务不回滚、dump 不生成 | `SIGTERM` + 优雅停机（见 06 篇） |
| 只排查应用不排查依赖 | 根因常在 DB/Redis/网络 | 用 trace 看耗时分布，先定位"哪一跳" |
| 故障后不写复盘 | 同样的坑反复踩 | 复盘必须有：时间线、根因、改进项、owner、deadline |

## 7. 落地检查表

**准备（平时就要做）**

- [ ] 生产镜像内包含 `jcmd`、`jstack`、`jmap`（JRE 精简镜像可能没有，需显式安装）
- [ ] Arthas 已预置在镜像或可快速下载（离线环境有私有仓库）
- [ ] `-XX:+HeapDumpOnOutOfMemoryError` + dump 目录有足够空间（≥ 堆大小 × 1.5）
- [ ] 有统一的"故障排查手册"（含本文的 SOP 表）
- [ ] 关键服务做过一次"故障演练"，验证工具可用

**工具使用规范**

- [ ] `trace`/`watch` 只在必要时使用，且带条件与次数限制
- [ ] 观察含敏感数据的方法时，明确排除 PII 字段
- [ ] `heap_dump` 在低峰执行，或明确接受 STW
- [ ] 所有生产操作有记录（谁、何时、执行了什么）

**事后**

- [ ] 每次 P1 故障有复盘文档（时间线 → 根因 → 改进项）
- [ ] 改进项有 owner 与 deadline，且在下次故障前完成
- [ ] 复盘结论沉淀为监控/告警/检查表（不只是一份文档）

## 8. 三个追问

1. **为什么用 Arthas 而不是加日志重新发布？**
   加日志需要：改代码 → 走流水线 → 发布 → 复现 → 看日志，至少 30 分钟，且故障现场可能已经消失（重启后不复现）。Arthas 能在**不重启、不改代码**的情况下观察方法调用，把"30 分钟的定位"压缩到"2 分钟"。代价是它有性能开销（字节码增强），不能长期开启。

2. **引入它之后，运维成本由谁承担？**
   工具本身零成本，但**"会用"是长期投入**：值班同学需要培训（否则出事时现查文档来不及）、需要演练（在预发环境模拟故障并实操）、需要版本适配（新 JDK 可能需要新版 Arthas）。这部分成本通常由 SRE 团队承担，且应纳入 on-call 培训体系。

3. **当它失效时，系统如何优雅退化？**
   Arthas attach 失败（JDK 版本不兼容、容器权限不足）时，退化到：`jcmd`/`jstack`（JDK 自带，最可靠）→ `async-profiler`（独立 agent，兼容性好）→ 日志与指标。**所以最基本的 `jstack` + `jstat` + 日志，必须永远可用**——它们是底线工具。

## 案例锚点：在 Polaris 里看代码、跑验证

### A. 看代码与工具

| 知识点 | 代码位置 | 看什么 |
|---|---|---|
| §3.2 `thread` 的第一现场 | `platform/platform-starter-guard/src/main/java/com/polaris/trade/guard/concurrent/BulkheadEndpoint.java` | `GET /actuator/bulkpools`：不用 Arthas 也能一眼看到各池 active/queue/rejected。**先看这个，再决定要不要 attach** |
| §4.4 慢查询的自动发现 | `platform/platform-starter-data/src/main/java/com/polaris/trade/data/mybatis/SlowSqlInterceptor.java` | 300ms 阈值 + SQL 指纹归一化。排障时按指纹聚合，而不是逐条看 |
| §4.2 / §4.3 的取证脚本 | `scripts/capture-evidence.sh` | 三份 jstack（间隔 3s）+ NMT diff + GC 采样 + 类直方图，**一次采集一个目录** |

### B. 跑验证：按症状选命令

**症状 1 · 线程池打满 / 接口全超时（§4.3）**

```bash
curl -s http://127.0.0.1:18080/actuator/bulkpools | python -m json.tool
# 期望看到某个池 active == max、queue 增长、rejected 递增
```

**症状 2 · Full GC / 怀疑堆外泄漏（§4.2）**

```bash
# 压测中同步取证：压测跑着，另一边采快照
scripts/loadtest.sh --mode create --steps 32 --duration 40 &
scripts/capture-evidence.sh --tag gc-storm --rounds 3 --interval 3
```

**症状 3 · CPU 高，但不知道是谁**

```bash
scripts/capture-evidence.sh --tag cpu-high
# 产物里的 summary.md 已按线程名前缀统计各池占用，先看这一屏
```

scripts 采集不到的部分（Arthas 交互式命令）只能看文档 §3；本仓库没有内置 Arthas
（它是 attach 工具，不适合写进自动化脚本）。

### C. 看结果：一次真实取证长什么样

`docs/fault/evidence/2026-10-27-1412-pool-and-gc/summary.md`：

```
线程状态：112 TIMED_WAITING / 82 WAITING / 51 RUNNABLE

前缀        第1轮 第2轮 第3轮
biz-price         0     0     0
biz-stock         0     0     0
biz-rec           8     8     8      ← 池满且三轮不降 = 真卡住
```

配合 NMT：

```
Total: reserved=1406MB, committed=860MB
-  Java Heap (committed=512MB)
-  Thread    (committed= 19MB)
-  Code      (committed= 63MB)
-  GC        (committed= 65MB)
```

两个数字合起来回答了 §4.3 那个问题：**堆没满，但进程 committed 860MB** ——
所以"堆只用了 40% 却被 OOMKilled"不是玄学，是 `-Xmx` 之外的 348MB。

### D. 一句话结论

排障最大的成本不是"没有数据"，而是**数据里 90% 是噪音**：
116 个空闲 IO 线程、几百行无关堆栈、几十个不相关的指标。
所以武器库的核心不是命令清单，而是**降噪的判断** ——
哪几个线程名该看、哪个指标的量级对得上、三份 jstack 里哪一行是三次都出现的。
先降噪，再定位；顺序反了，工具越多越慢。
