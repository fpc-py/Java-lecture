# 19 · 供应链安全与密码学演进

> **阶段**：技术选型 / 构建发布 / 长期演进
> **痛点**：`SNAPSHOT` 依赖混进了生产，同一个版本号两次构建出的产物不一样；内部包名被公共仓库抢注，一次依赖解析就把恶意代码拉进了构建；密码用的还是 MD5，且"以后换"已经说了三年。

---

## 1. 真实故障场景

### 场景 A：SNAPSHOT 上线，线上跑的是"没人知道哪个版本"

```xml
<dependency>
  <groupId>com.example</groupId>
  <artifactId>common-utils</artifactId>
  <version>2.3.0-SNAPSHOT</version>    <!-- 每次构建都可能拉到不同内容 -->
</dependency>
```

后果：

- 周一构建的镜像和周三构建的镜像，代码不同但版本号一样；
- 线上出问题，`common-utils` 的 owner 说"我昨天改了个 bug 已经发 SNAPSHOT 了"——但不知道线上是改前还是改后；
- 回滚镜像时，SNAPSHOT 依赖可能已经被覆盖，**回滚也回不到原来的行为**。

**可重现构建是供应链安全的起点**。没有它，其他一切（SBOM、签名、审计）都建立在流沙上。

### 场景 B：依赖混淆攻击（Dependency Confusion）

某公司内部包：

```xml
<groupId>com.company</groupId>
<artifactId>internal-auth-client</artifactId>
<version>1.4.2</version>
```

开发者在公共 Maven Central 注册了同名（或私有仓库优先级配置错误），发布了一个版本号更高的同名包（如 `1.4.3`）。构建时，Maven 按"版本最高"或"仓库优先级"解析，拉到了公共仓库的**恶意包**——它会在构建时执行后门代码，把环境变量（含密钥）发到外部。

**同类攻击：typosquatting**（`spring-boot-starter-web` → `spring-boot-stater-web`）、**恶意维护者劫持**（包作者账号被盗后发布后门版本）、**构建工具投毒**（CI 插件被替换）。

### 场景 C：刚刚发布的版本带了后门

某开源库被植入后门版本发布到公共仓库，2 小时后被发现并下架。但你的流水线在这 2 小时内构建了一次，**已经把它打进了镜像**。

**根因**：私有仓库代理没有"冷却期"，新版本发布后立刻被拉取。**"新版本不等于安全版本"**——社区发现与响应需要时间。

### 场景 D：密码哈希用了 MD5，被拖库后 3 天全破

```
MD5("123456") = e10adc3949ba59abbe56e057f20f883e
```

GPU 每秒可计算数百亿次 MD5。加盐也只能防彩虹表，防不住暴力破解。

### 场景 E：量子计算的"先存后解"

攻击者现在抓取并存储加密流量（TLS 会话），等量子计算机成熟后再解密。这对**长期敏感数据**（身份证、医疗记录、合同）构成"追溯性"威胁。**迁移必须在威胁到来之前完成**，而不是之后。

## 2. 原理剖析

### 2.1 供应链的四个攻击面

```
① 依赖来源      公共仓库被投毒、抢注、作者账号被盗
② 构建过程      CI 插件被替换、构建机被入侵、缓存被污染
③ 制品          镜像仓库被篡改、tag 被重新指向
④ 分发          更新通道被劫持（自动更新、热更新）
```

**每一层的防护手段不同**：

| 层 | 防护 |
|---|---|
| 依赖来源 | 私有仓库代理 + 白名单 + 冷却期 + 依赖锁定 |
| 构建过程 | 可重现构建、构建环境隔离、SLSA provenance |
| 制品 | 签名（cosign）+ 部署时验签 + digest 引用 |
| 分发 | 签名验证 + 离线校验 |

### 2.2 SLSA：供应链完整性等级

| 等级 | 要求 | 能防什么 |
|---|---|---|
| SLSA 1 | 构建过程有文档、有 provenance（构建来源证明） | 无（仅记录） |
| SLSA 2 | 构建由托管 CI 完成，provenance 由 CI 生成 | 本地构建被篡改 |
| SLSA 3 | 构建环境隔离、不可伪造的 provenance 签名 | 构建系统被入侵 |
| SLSA 4 | 双人 review + 可重现构建 | 源代码被内部人篡改 |

**大多数团队的现实目标是 SLSA 2–3**：托管 CI + 生成 provenance + 镜像签名。

```bash
# 用 cosign 做无密钥签名（Sigstore，基于 OIDC 身份）
cosign sign --yes $IMAGE@$DIGEST

# 部署时验签（K8s admission controller：Kyverno / policy-controller）
cosign verify $IMAGE@$DIGEST \
  --certificate-identity=ci@example.com \
  --certificate-oidc-issuer=https://token.actions.githubusercontent.com
```

### 2.3 依赖锁定与可重现构建

| 生态 | 锁定机制 |
|---|---|
| Maven | 本身无 lock 文件 → 用 `dependencyManagement` + BOM 锁定版本；`mvn dependency:tree` 审计 |
| Gradle | `gradle.lockfile` + `--write-locks` |
| npm | `package-lock.json` |
| Go | `go.sum` |

**Maven 的"隐性版本漂移"**（最容易被忽略）：

```xml
<!-- pom 里只写了 1.2.0，但实际解析到 1.2.3，因为"最近者优先"或范围传递 -->
<dependency>
  <artifactId>some-lib</artifactId>
  <version>1.2.0</version>
</dependency>
```

```bash
# 确认最终解析版本（而不是 pom 里写的版本）
mvn dependency:tree -Dverbose | grep some-lib
mvn help:effective-pom | grep -A2 "some-lib"
```

**治理手段**：用 `dependencyManagement` 集中管理所有版本（BOM 模式），禁止子模块自行指定版本。

### 2.4 私有仓库的四条规则

```
规则1：所有依赖必须经过私有仓库代理（不直连公网）
规则2：新版本发布后有"冷却期"（如 7 天）才允许拉取
规则3：内部包名使用保留域名反写（com.company.*），且在私有仓库中设置"不允许回退到公共仓库"
规则4：公共仓库镜像采用白名单（只代理已知安全的 group）
```

```xml
<!-- Nexus / Artifactory 的仓库配置要点（概念示意） -->
<!-- ① hosted（内部发布）优先级最高 -->
<!-- ② proxy（公共代理）带冷却期 -->
<!-- ③ group 中 hosted 在前，proxy 在后；且禁用"公共仓库优先" -->
```

> **依赖混淆的根本原因**：Maven 会**遍历所有配置的仓库**寻找 artifact，若私有仓库没有对应版本，就回退到公共仓库。解法是在私有仓库中对内部 group 配置"**不代理到公网**"（block 规则），让内部包永远无法从公共仓库解析。

### 2.5 密码学敏捷性（Crypto Agility）

**定义**：系统能够在不重构业务代码的前提下，替换密码算法/密钥长度/协议版本。

```
不敏捷的写法：
  byte[] hash = MessageDigest.getInstance("MD5").digest(pwd.getBytes());
  → 算法硬编码在 300 个地方，换算法要改 300 处 + 数据迁移

敏捷的写法：
  PasswordEncoder encoder = encoderProvider.current();   // 由配置决定
  → 换算法只改配置 + 渐进式重哈希（用户下次登录时升级）
```

**渐进式重哈希**（迁移密码算法的正确方式）：

```java
public boolean matches(String raw, String stored) {
    PasswordEncoder encoder = encoderFor(stored);       // 从存储格式识别算法（$2a$ = bcrypt, $argon2id$ = argon2）
    if (!encoder.matches(raw, stored)) return false;

    if (encoder != currentEncoder) {                    // 老算法 → 登录成功后升级
        userMapper.updatePasswordHash(userId, currentEncoder.encode(raw));
    }
    return true;
}
```

**这个模式同样适用于**：对称加密（AES-GCM 密钥版本）、签名（RS256 → ES256 → ML-DSA）、TLS 版本。

### 2.6 后量子密码（PQC）的现状与迁移

**NIST 2024 标准化的算法**：

| 用途 | 算法 | 标准 | 说明 |
|---|---|---|---|
| 密钥交换（KEM） | **ML-KEM**（CRYSTALS-Kyber） | FIPS 203 | 替代 ECDH/RSA 密钥交换 |
| 数字签名 | **ML-DSA**（CRYSTALS-Dilithium） | FIPS 204 | 替代 RSA/ECDSA 签名 |
| 数字签名（备选） | **SLH-DSA**（SPHINCS+） | FIPS 205 | 基于哈希，签名大但假设最少 |

**TLS 1.3 的混合密钥交换**（过渡期的最佳实践）：

```
X25519MLKEM768 = X25519（经典） + ML-KEM-768（抗量子）
两个都破解才能攻破 → 兼顾"现在安全"与"未来安全"
```

```bash
# 检查你的服务是否支持混合密钥交换（OpenSSL 3.5+ / BoringSSL）
openssl s_client -connect example.com:443 -groups X25519MLKEM768

# 输出中应看到 Negotiated TLS1.3 group: X25519MLKEM768
```

**迁移路线图（分四步，按数据敏感度排序）**：

```
① 盘点（Inventory）
   梳理所有使用密码学的位置：TLS 端点、证书、签名、加密字段、密钥管理
   标注：算法、密钥长度、数据保留期、谁能访问

② 敏捷化（Agility）
   把算法/密钥从硬编码提取为配置；建立密钥版本机制（kid）
   这一步与 PQC 无关，但对任何算法迁移都是必需的

③ 混合过渡（Hybrid）
   TLS 1.3 启用 X25519MLKEM768（客户端与服务端都要支持）
   代码签名/内部通信开始评估 ML-DSA
   保留经典算法作为回退（互操作性）

④ 纯 PQC（Pure）
   仅在高安全场景（长期机密数据）逐步切到纯 PQC
   注意：签名体积增大（ML-DSA 签名 ~2.4KB vs ECDSA ~64B），会影响协议设计
```

**优先级判断**（"先存后解"威胁模型）：

| 数据类型 | 保留期 | 迁移优先级 |
|---|---|---|
| 长期机密（身份证、医疗、合同、源代码） | > 10 年 | **最高**（现在抓、以后解） |
| 会话数据、临时令牌 | < 1 年 | 低（到期时已无价值） |
| 内部通信 | 视情况 | 中 |

## 3. 工程解法

### 3.1 Maven 层面的强制约束

```xml
<!-- ① 禁止 SNAPSHOT 进入 release 构建 -->
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-enforcer-plugin</artifactId>
  <executions>
    <execution>
      <id>enforce-no-snapshot</id>
      <goals><goal>enforce</goal></goals>
      <configuration>
        <rules>
          <requireReleaseDeps>
            <message>生产构建禁止使用 SNAPSHOT 依赖</message>
            <onlyWhenRelease>true</onlyWhenRelease>
          </requireReleaseDeps>
          <requireUpperBoundDeps/>          <!-- 依赖版本冲突检测 -->
          <banDuplicatePomDependencyVersions/>
          <bannedDependencies>
            <excludes>
              <exclude>commons-collections:commons-collections</exclude>  <!-- 历史高危 -->
              <exclude>log4j:log4j</exclude>                              <!-- 1.x 已停止维护 -->
            </excludes>
          </bannedDependencies>
        </rules>
        <fail>true</fail>
      </configuration>
    </execution>
  </executions>
</plugin>
```

```xml
<!-- ② 集中版本管理（BOM），子模块不得指定版本 -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>3.3.4</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
    <!-- 内部 BOM，统一管理内部包版本 -->
    <dependency>
      <groupId>com.company</groupId>
      <artifactId>platform-bom</artifactId>
      <version>2.8.0</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
```

### 3.2 私有仓库的冷却期与白名单

```bash
# 概念配置：Nexus 的 "Content Max Age" / Artifactory 的 "Metadata Retrieval Cache Period"
# 目标：公共仓库的新版本在发布后 N 天内不可被解析

# 具体实现（Artifactory 示例：给远程仓库加 "Blackout Period"）
# 或用 CI 前置检查脚本：
```

```java
// CI 中的"新版本拦截"脚本（伪代码思路）
// 拉取候选依赖的发布时间，若 < 7 天则告警/阻断
public void checkFreshness(Dependency dep) {
    Instant published = mavenCentralApi.publishedAt(dep);
    if (Duration.between(published, Instant.now()).toDays() < 7) {
        throw new BuildException("依赖 " + dep + " 发布时间过新（" 
            + published + "），需安全评估");
    }
}
```

**白名单策略**（依赖 = 代码，需要审批）：

| 策略 | 说明 |
|---|---|
| 新增依赖需 PR 审批 | CODEOWNERS 指派架构/安全组 |
| 依赖清单固化 | 只有清单内的 group/artifact 允许引入 |
| 定期清理 | 每季度审计未使用的依赖（`mvn dependency:analyze`） |

### 3.3 制品签名与验证

```bash
# 构建阶段：签名镜像（commit 后自动）
cosign sign --yes --key env://COSIGN_KEY $IMAGE@$DIGEST

# 生成 provenance（SLSA）
slsa-github-generator / cosign attest --predicate provenance.json $IMAGE

# 部署阶段：K8s 准入控制强制验签（Kyverno 策略）
```

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-image-signature
spec:
  validationFailureAction: Enforce        # 验签失败则拒绝部署
  rules:
    - name: verify-signature
      match:
        any:
          - resources: { kinds: [Pod] }
      verifyImages:
        - imageReferences: ["registry.example.com/*"]
          attestors:
            - entries:
                - keyless:
                    subject: "ci@example.com"
                    issuer: "https://token.actions.githubusercontent.com"
```

### 3.4 密码哈希的迁移

```java
// 目标：Argon2id（内存硬，抗 GPU）
@Bean
public PasswordEncoder passwordEncoder() {
    return new Argon2PasswordEncoder(16, 32, 1, 1 << 16, 3);   // salt 16B, hash 32B, 64MB, 3 轮
    // 或 bcrypt(cost = 12)：兼容性好，实现简单
}
```

| 算法 | 推荐度 | 说明 |
|---|---|---|
| MD5 / SHA1（加盐） | ❌ 禁止 | GPU 可破 |
| SHA256 单次 | ❌ 禁止 | 同上 |
| PBKDF2 | △ 可用 | 迭代次数需 ≥ 60 万（OWASP 2023） |
| bcrypt | ✅ 推荐 | cost ≥ 12；密码长度限制 72 字节 |
| **Argon2id** | ✅ **首选** | 内存硬，抗 GPU/ASIC；需调参 |

**迁移计划**：

```
① 存量：登录时识别算法 → 验证通过后重哈希为新算法（渐进式，无需强制改密）
② 新增：一律用新算法
③ 监控：统计"仍使用旧算法"的用户比例，低于阈值后清理旧算法代码
```

### 3.5 证书与密钥的生命周期

| 项 | 要求 |
|---|---|
| TLS 证书 | 有效期 ≤ 90 天（自动化续期，ACME），到期前 30 天告警 |
| 签名密钥 | 每年轮换，支持多版本并存（`kid`） |
| 加密密钥（数据） | 每年轮换，旧密钥保留用于解密历史数据（版本化） |
| 密钥存储 | KMS / Vault / HSM，**不进代码、不进配置、不进镜像** |
| 最小权限 | 每个服务只能拿到自己需要的密钥 |

```java
// 密钥版本化：加密时记录版本，解密时按版本取
public record Ciphertext(String keyId, byte[] iv, byte[] data) {}

String encrypt(String plain, String keyId) {
    return keyId + ":" + Base64.getEncoder().encodeToString(gcm.encrypt(plain, kms.get(keyId)));
}
```

## 4. 边界条件与反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 允许 SNAPSHOT 进生产 | 不可重现、无法回滚 | enforcer 阻断 |
| 子模块各自指定依赖版本 | 版本漂移、冲突难查 | 统一 BOM + dependencyManagement |
| 直连公网 Maven Central | 无冷却期、无审计、无缓存 | 私有仓库代理 |
| 公共仓库优先于私有仓库 | 依赖混淆 | hosted 优先 + 内部 group 禁止回退 |
| 新版本发布当天就升级 | 恶意/有缺陷版本窗口 | 冷却期 ≥ 7 天，安全补丁例外 |
| 只扫依赖不验签名 | 镜像/制品被篡改无法发现 | cosign 签名 + 部署时验签 |
| 密码用 MD5/SHA1 | 拖库即明文 | Argon2id / bcrypt |
| 算法硬编码在业务代码 | 无法迁移（Crypto Agility = 0） | 算法可配置 + 密钥版本化 |
| 认为"PQC 还很远" | 长期数据已被"先存后解" | 按数据保留期排序，先迁移高敏 |
| 一次性全量切 PQC | 互操作性与性能风险 | 混合模式（Hybrid）过渡 |
| 密钥写在配置文件/环境变量明文 | 泄漏面大 | KMS/Vault + 短期凭证 |

## 6. 三个追问

1. **为什么用私有仓库 + 冷却期，而不是直接信任 Maven Central？**
   信任是"概率"而不是"保证"：开源包可能被投毒、作者账号可能被盗、新版本可能有恶意代码。冷却期的价值是**用时间换取社区的发现与响应**（后门版本通常在数小时内被发现）。代价是新依赖的引入变慢——对安全补丁需要开例外通道。**这是"可用性 vs 安全性"的显式权衡，而不是教条。**

2. **引入它之后，运维成本由谁承担？**
   供应链安全的成本是**持续且分散**的：私有仓库的运维（容量、代理、清理）、依赖审批（每次新增依赖要走流程）、漏洞跟踪（每周新增 CVE）、密钥轮换（每年数十个密钥）、PQC 迁移（数年项目）。这些通常由**平台/安全团队**牵头，但审批与升级的压力会落在每个业务团队身上。**没有 owner 的治理，三个月后一定腐化。**

3. **当它失效时，系统如何优雅退化？**
   私有仓库不可用 → 本地缓存/离线仓库（保证构建可继续）；签名验证服务不可用 → 缓存已验证的 digest 白名单（限制爆炸半径）；算法迁移出问题 → 保留旧算法解密能力（**双算法并存期不可省**）；密钥轮换出错 → 旧密钥保留 ≥ 数据保留期。**密码学迁移的第一原则是"永远能解开老数据"。**

## 案例锚点：在 Polaris 里看代码、跑验证

### A. 看代码与配置

| 知识点 | 代码位置 | 看什么 |
|---|---|---|
| 依赖门禁：禁 SNAPSHOT | `pom.xml` → `maven-enforcer-plugin` | `requireReleaseDeps` 的 `<onlyWhenRelease>true</onlyWhenRelease>`：日常开发允许，**发布必须全是 release 版** |
| 依赖门禁：禁已知 CVE 版本区间 | 同上 → `bannedDependencies` | `commons-collections:commons-collections:[,3.2.2)`。**只禁漏洞区间而不是禁整个 artifact** —— 一刀切会让团队转头去删规则 |
| §3.4 摘要与签名的统一入口 | `platform/platform-common/src/main/java/com/polaris/trade/common/lang/Hashes.java` | 签名算法选择集中在一处，不允许各处 `MessageDigest.getInstance("MD5")` |
| §2.5 加密算法演进 | `platform/platform-starter-data/src/main/java/com/polaris/trade/data/crypto/AesGcmCipher.java` | AES-256-**GCM**（带完整性校验），不是 ECB/CBC |
| §3.5 密钥生命周期 | `platform/platform-starter-data/src/main/java/com/polaris/trade/data/crypto/KeyProvider.java` | 密钥从哪来、怎么轮换、旧密钥怎么保留解密能力 |
| 构建信息可追溯 | `platform/platform-starter-observability/src/main/java/com/polaris/trade/observability/BuildInfoContributor.java` | `/actuator/info` 的 `build.commit` 是"这个镜像到底装了哪份代码"的唯一答案 |

### B. 跑验证：触发一次依赖门禁

```bash
# 日常构建（允许 SNAPSHOT 依赖）
scripts/mvnw.sh -DskipTests install

# 发布构建（禁止任何 SNAPSHOT）
scripts/mvnw.sh -Drelease=true -DskipTests validate
```

期望：当前**通过**（所有依赖都是 release 版）。
若某模块引入 SNAPSHOT 依赖，这一步会失败：

```
发布构建禁止任何 SNAPSHOT 依赖：版本号必须可追溯
```

这就是"门禁"与"建议"的区别 —— 建议可以忽略，门禁会红。

```bash
# 看某个依赖是从哪条路径进来的（CVE 排查的第一步）
scripts/mvnw.sh -pl services/order-service dependency:tree -Dincludes=commons-collections
```

### C. 看结果

| 供应链控制点 | 本仓库现状 | 说明 |
|---|---|---|
| 依赖版本统一管理 | **已做到**：父 POM 集中 `dependencyManagement` | 版本冲突先在这里解决 |
| 禁止 SNAPSHOT 发布 | **已做到**：`-Drelease=true` 触发 enforcer | — |
| 禁止已知 CVE 版本 | **部分**：手写 banned 区间 | 覆盖面和维护成本都是问题 |
| SBOM（CycloneDX）生成 | **未落地**，M9 | 出事时"我到底用了哪些包"现在只能 `dependency:tree` |
| 依赖漏洞自动扫描 | **未落地**，M9 | 计划 OWASP DC / Trivy |
| 镜像签名与来源校验 | **未落地**（无 Dockerfile） | M9 |
| 密钥托管（KMS / Vault） | **未落地**：`KeyProvider` 是本地实现 | 生产必须换 |
| 后量子迁移评估 | **仅文档**（§2.5 / §3.5） | 无可执行部分 |

> 关于"后量子"这一节：它是**判断类内容**，本案例不给代码是对的。
> 现在写一个"抗量子加密工具类"既没有真实算法库支撑，也会给人"已经迁移完了"的错觉。
> 这一节的价值在 §4 的边界条件 —— 什么时候该开始评估、评估什么。

### D. 一句话结论

供应链安全最容易做成"装一个扫描器然后不管了"。
真正起作用的是两条：**版本必须可追溯**（禁 SNAPSHOT、构建信息注入 commit）、
**漏洞区间必须能收窄**（禁区间而不是禁 artifact）。
前者决定出事时能不能定位到代码，后者决定规则能不能活过三个月。
