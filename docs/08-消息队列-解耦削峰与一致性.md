# 08 · 消息队列：解耦、削峰与一致性

> **阶段**：系统扩展 / 异步化改造
> **痛点**：MQ 一引入，"消息丢了"和"消息重了"就同时出现了；积压告警天天响，但没人能说清消费能力上限是多少。

---

## 1. 真实故障场景

### 场景 A：订单消息丢了 12 单，财务对不上

```java
// 生产端：发完就不管了
kafkaTemplate.send("order-created", orderNo, payload);
```

Broker 侧 `acks` 用的是默认值，leader 写入成功即返回；leader 在同步给 follower 之前宕机，消息丢失。加上应用没做发送重试与失败落库，12 单订单"创建成功但下游没收到"。

**消息丢失的三个环节，每一个都要单独保证**：

```
生产者 ──①网络/未确认──▶ Broker ──②未刷盘/未同步──▶ 磁盘 ──③消费位点提前提交──▶ 消费者
```

### 场景 B：重复消费导致重复扣款 3 次

消费端逻辑：

```java
@KafkaListener(topics = "pay-success")
public void onMessage(String msg) {
    PayEvent e = parse(msg);
    accountMapper.deduct(e.userId(), e.amount());   // 无幂等
}
```

触发重复的三条路径（都会真实发生）：

1. 消费成功但**提交位点前**进程被 kill → 重启后重投；
2. 消费超时（`max.poll.interval.ms` 默认 5 分钟）→ 触发 rebalance，分区被分配给其他实例，消息被重复投递；
3. 生产端重试（网络超时但实际已写入）→ 消息本身重复。

**Kafka 的"至少一次"语义意味着重复是常态，不是异常**。幂等必须由业务自己保证。

### 场景 C：状态机被乱序消息打回旧状态

订单状态消息按 `CREATED → PAID → SHIPPED` 发送，消费者收到 `SHIPPED` 后又收到 `PAID`（因为两条消息落在不同分区、并行消费），状态从"已发货"退回"已支付"，用户看到订单"倒退"。

**根因**：Kafka **只保证单分区内有序**，跨分区无序。生产端若未指定 key（或 key 分布导致同一订单进不同分区），顺序无法保证。

### 场景 D：积压 800 万条，扩容消费者无效

大促后订单履约 Topic 积压 800 万条。运维把消费者从 4 个实例扩到 16 个，**积压不降反升**，且频繁 rebalance。

**根因**：Topic 只有 4 个分区。**Kafka 的消费并行度上限 = 分区数**，多出来的消费者实例空转，还会因为不断加入组而触发 rebalance（Stop-The-World 式重平衡）。同时消费者是"拉一批、处理完再拉"，单条处理 200ms，单实例吞吐 = `500 / 0.2s = 2500 条/s`，4 实例 1 万条/s，800 万需要 800s——理论上能降，但 rebalance 打断了这个进程。

## 2. 原理剖析

### 2.1 三大 MQ 的选型维度

| 维度 | Kafka | RocketMQ | RabbitMQ |
|---|---|---|---|
| 吞吐 | 最高（百万级/s，顺序写 + 零拷贝） | 高（十万级/s） | 中（万级/s） |
| 延迟 | ms 级 | ms 级（更低，长轮询） | μs–ms 级（最低） |
| 顺序消息 | 分区内有序 | **支持分区顺序 + 全局顺序** | 队列内有序 |
| 事务消息 | 支持（需配合幂等 producer） | **原生 half message + 回查**（最完整） | 不支持（只有 publisher confirm） |
| 延迟消息 | 不支持（需外部方案） | **原生支持任意延迟级别** | 需插件（rabbitmq_delayed_message_exchange） |
| 消息回溯 | **支持（按 offset/时间重置）** | 支持（按时间） | 不支持（消费即删） |
| 路由能力 | 弱（topic + key） | 中（tag 过滤） | **强（exchange + routing key）** |
| 运维复杂度 | 中高（依赖 ZK/KRaft、分区规划） | 中 | 低（单机即可） |
| 典型场景 | 日志、埋点、大数据管道、高吞吐事件流 | 电商交易、订单履约、金融 | 业务解耦、RPC 异步化、复杂路由 |

**选型口诀**：

```
吞吐优先、可回溯、允许最终一致      → Kafka
交易场景、需要事务消息/延迟消息/顺序  → RocketMQ
路由复杂、消息量中等、想快速落地      → RabbitMQ
```
> 只选一个时：**国内电商/金融业务默认 RocketMQ**（事务消息与延迟消息是刚需）；**数据管道默认 Kafka**。

### 2.2 消息不丢：三层保障

| 层 | Kafka | RocketMQ | RabbitMQ |
|---|---|---|---|
| 生产端 | `acks=all` + `retries>0` + `enable.idempotence=true` | 同步发送 + 重试（3 次）+ `sendStatus` 校验 | publisher confirms + 返回值校验 |
| Broker | `replication.factor>=3` + `min.insync.replicas>=2` + `unclean.leader.election=false` | 同步刷盘 `SYNC_FLUSH` + 主从同步复制 `SYNC_MASTER` | `delivery_mode=2`（持久化）+ 镜像/quorum 队列 |
| 消费端 | **手动提交 offset**（处理成功后提交） | 处理成功返回 `CONSUME_SUCCESS` | 手动 ack（`basicAck`） |

**Kafka 生产端标准配置**：

```java
Properties p = new Properties();
p.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "broker:9092");
p.put(ProducerConfig.ACKS_CONFIG, "all");                          // 所有 ISR 确认
p.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);             // 幂等 producer（去重）
p.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);           // 配合幂等，安全重试
p.put(ProducerConfig.MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, 5);    // 幂等开启时 ≤5 保证顺序
p.put(ProducerConfig.DELIVERY_TIMEOUT_MS_CONFIG, 120_000);
p.put(ProducerConfig.REQUEST_TIMEOUT_MS_CONFIG, 30_000);
p.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "lz4");
```

`enable.idempotence=true` 解决的是**生产者重试导致的重复**（Broker 侧按 `PID + 序列号` 去重），**不解决业务级重复**。

**同步发送 + 失败落库**（关键业务必须）：

```java
public void sendReliably(String topic, String key, String payload) {
    try {
        SendResult r = rocketMQTemplate.syncSend(topic + ":" + key, payload, 3000);
        if (r.getSendStatus() != SendStatus.SEND_OK) {
            throw new MqSendException("status=" + r.getSendStatus());
        }
    } catch (Exception e) {
        // 落本地消息表，由定时任务补偿（见 09 篇）
        localMessageMapper.insert(LocalMessage.pending(topic, key, payload));
        log.error("send failed, saved to local table", e);
    }
}
```

### 2.3 消费端幂等：四种实现与适用边界

| 方案 | 实现 | 优点 | 边界 |
|---|---|---|---|
| **唯一键 + 去重表** | 消息 ID 或业务唯一键建唯一索引，插入冲突即视为重复 | 强可靠、可审计 | 每次消费多一次 DB 写；需清理历史 |
| **业务状态机** | 状态只能单向流转（`PAID → SHIPPED`，已是 `SHIPPED` 就跳过） | 无额外存储，天然幂等 | 要求业务本身有状态语义 |
| **Redis SETNX** | `SET msg:{id} 1 NX EX 86400` | 快 | Redis 故障/过期后失效；**非强一致** |
| **数据库唯一约束** | 直接在业务表上建唯一索引（如 `order_no + type`） | 最简单、最可靠 | 仅适用于"天然唯一"的业务 |

**推荐组合**：`业务状态机（主） + 唯一键去重表（兜底）`。Redis 方案只用于"可容忍极小概率重复"的场景（如埋点统计）。

```java
@RocketMQMessageListener(topic = "order-paid", consumerGroup = "g-order-paid")
public class OrderPaidConsumer implements RocketMQListener<OrderPaidEvent> {

    @Override
    public void onMessage(OrderPaidEvent e) {
        // ① 幂等：唯一键插入（msgId 由生产端保证唯一）
        try {
            dedupMapper.insert(new DedupRecord(e.msgId(), "order-paid"));
        } catch (DuplicateKeyException dup) {
            log.info("duplicate msg, skip: {}", e.msgId());
            return;                       // 直接 ACK
        }

        // ② 状态机校验：不允许状态回退
        Order o = orderMapper.selectById(e.orderId());
        if (o.getStatus() >= OrderStatus.PAID.getCode()) {
            log.info("already paid, skip: {}", e.orderId());
            return;
        }

        // ③ 业务处理（与去重记录在同一事务）
        orderMapper.updateStatus(e.orderId(), PAID);
        accountMapper.addFlow(e.orderId(), e.amount());
    }
}
```

> `dedupMapper.insert` 与业务更新必须在**同一事务**里，否则"去重记录写入成功但业务失败"会导致消息被跳过、业务永久丢失。

### 2.4 顺序消息：分区与消费模型的约束

**Kafka 的顺序保证链条**：

```
生产端：相同 key → 相同分区（hash(key) % partitions）
Broker：分区内 append-only，天然有序
消费端：一个分区只能被组内一个消费者消费；单分区内单线程处理
```

因此顺序消费必须做到：

1. 生产端**显式指定 key**（用业务主键，如 `orderNo`）；
2. 消费端**不要用线程池并发处理同一分区的消息**（`concurrency` 可以设 >1，但每个线程处理不同分区）；
3. 生产端 `max.in.flight.requests.per.connection=1`（或开启幂等且 ≤5）。

**RocketMQ 的顺序消费**：

```java
// 生产端：用 orderNo 做队列选择器，保证同一订单进同一队列
rocketMQTemplate.syncSendOrderly("order-status", payload, orderNo);

// 消费端：顺序消费（单队列单线程，失败会阻塞该队列）
@RocketMQMessageListener(topic = "order-status", consumerGroup = "g-status",
        consumeMode = ConsumeMode.ORDERLY)
public class StatusConsumer implements RocketMQListener<String> { ... }
```

**顺序消费的代价**：单队列串行处理，吞吐受限于单线程处理速度；一条消息卡住（重试）会阻塞整个队列。**只在真正需要顺序的业务上用**（状态流转、账户流水），不要全局滥用。

## 3. 工程解法

### 3.1 堆积治理：从"能降"到"降得动"

**先算清楚消费能力**：

```
单实例吞吐 = 单批条数 fetch.max.bytes / 单条大小 ÷ 单批处理耗时
           ≈ 并发线程数 ÷ 单条平均耗时
总吞吐     = min(实例数, 分区数) × 单实例吞吐
积压消化时间 = 积压量 ÷ (总吞吐 − 生产速率)
```

例：800 万积压、生产速率 2000/s、单条 5ms、4 分区 4 实例 → 总吞吐 800/s，**永远降不下来**。

**四种处置手段**（按优先级）：

| 手段 | 效果 | 代价 |
|---|---|---|
| ① 提升消费并行度（分区足够时扩实例） | 线性提升 | 分区不足时无效；注意 rebalance |
| ② 提升单条处理速度（批量化、去掉同步 RPC） | 2–5 倍 | 改代码，可能影响幂等 |
| ③ 扩分区（`kafka-topics --alter --partitions`） | 提升并行上限 | **会破坏 key→分区的映射**，顺序性受影响；不可逆 |
| ④ 临时"丢弃/转移"（写一个临时消费者把消息搬到新 Topic 并扩容） | 快速止血 | 需要额外 Topic 与运维操作 |

**注意 rebalance 风暴**：消费者实例数变化、`max.poll.interval.ms` 超时、心跳丢失都会触发 rebalance。Kafka 2.4+ 用**增量协作式重平衡**（`CooperativeStickyAssignor`）可大幅缓解：

```java
props.put(ConsumerConfig.PARTITION_ASSIGNMENT_STRATEGY_CONFIG,
          "org.apache.kafka.clients.consumer.CooperativeStickyAssignor");
props.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, 200);         // 减小单批，避免处理超时
props.put(ConsumerConfig.MAX_POLL_INTERVAL_MS_CONFIG, 300_000); // 大于单批最长处理时间
```

### 3.2 重试与死信：不能让一条坏消息堵住整个队列

```
消费失败
  ├─ 可重试异常（网络抖动、DB 死锁）→ 重试 3 次，指数退避（1s / 5s / 15s）
  ├─ 不可重试异常（数据格式错误、业务规则拒绝）→ 直接进死信，不重试
  └─ 重试耗尽 → 进死信队列 → 告警 + 人工/定时任务处理
```

**RocketMQ 的延迟级别重试**（`%RETRY%` Topic，默认 16 级：1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h）：

```java
@RocketMQMessageListener(topic = "order-paid", consumerGroup = "g-order-paid",
        maxReconsumeTimes = 3)
public class OrderPaidConsumer implements RocketMQListener<OrderPaidEvent> {
    @Override
    public void onMessage(OrderPaidEvent e) {
        try {
            handle(e);
        } catch (BizRejectException ex) {
            // 业务拒绝：不再重试，直接落死信表并 ACK
            deadLetterService.save(e, ex.getMessage());
        }
        // 其他异常直接抛出 → RocketMQ 按延迟级别重试
    }
}
```

**Kafka 没有原生重试/死信**，标准做法是自建：

```java
// 重试 Topic + 延迟队列（用 timeout 或独立调度器）
// 超过 N 次 → dead-letter Topic，且必须有人消费它，否则等于静默丢弃
@KafkaListener(topics = "order-paid.DLT", groupId = "g-dlt")
public void onDeadLetter(String msg) {
    deadLetterMapper.insert(msg);
    alert.warn("DLT message", msg);     // 必须有告警
}
```

> **死信队列最常见的失误**：建了 DLT 但没人消费、没告警。死信成了"消息坟墓"，问题从"消费失败"变成"数据永久丢失且无人知晓"。

### 3.3 延迟消息：订单超时关单的标准模式

| 方案 | 精度 | 可靠性 | 说明 |
|---|---|---|---|
| RocketMQ 延迟消息 | 固定 18 级（4.x）/ 任意时间（5.x） | 高 | 首选 |
| RabbitMQ 延迟插件 | ms 级 | 高 | 需安装插件 |
| 定时任务扫表 | 秒/分钟级 | 高 | 简单可靠，适合小数据量（`WHERE status=UNPAID AND create_time < now-30m`） |
| Redis ZSet + 定时轮询 | 秒级 | 中 | 轻量方案 |
| Kafka + 时间轮（自研） | 秒级 | 中 | 复杂度高，不建议 |

```java
// 下单时投递延迟消息（RocketMQ 5.x 支持任意时间戳）
rocketMQTemplate.syncSendDelayTimeMills("order-timeout",
        new OrderTimeoutEvent(orderNo), Duration.ofMinutes(30).toMillis());

// 消费时二次校验：可能用户已经支付
public void onMessage(OrderTimeoutEvent e) {
    Order o = orderMapper.selectByNo(e.orderNo());
    if (o == null || o.getStatus() != UNPAID) return;      // 已支付/已取消 → 幂等跳过
    orderMapper.closeIfUnpaid(e.orderNo());                 // CAS：UPDATE ... WHERE status = UNPAID
}
```

**为什么必须二次校验**：延迟消息不保证"恰好 30 分钟送达"（可能延迟 30 分 2 秒，也可能重试导致重复投递），且用户可能在第 29 分 59 秒支付。**唯一可靠的判断依据是数据库当前状态**，不是消息本身。

### 3.4 削峰填谷的容量设计

```
峰值写入 20,000/s，消费能力 5,000/s，峰值持续 60s
→ 需堆积 20,000 × 60 − 5,000 × 60 = 900,000 条
→ 按 1KB/条 = 900MB，需保证 Broker 保留策略覆盖（retention ≥ 峰值后消化时间 + 缓冲）
→ 消化时间 = 900,000 / 5,000 = 180s
```

**结论**：削峰的前提是"消费能力 × 可接受延迟 ≥ 峰值总量"。若消费能力远低于峰值，MQ 只是把雪崩推迟 3 分钟。**容量规划必须同时算生产、消费、保留三件事**。

## 4. 边界条件与反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 生产端异步发送且不校验结果 | 消息静默丢失 | 关键业务同步发送 + 失败落库/本地消息表 |
| 消费端自动提交 offset | 处理失败也提交 → 消息丢失 | 手动 ack，处理成功后提交 |
| 消费逻辑无幂等 | 重复消费导致重复扣款 | 唯一键去重表 / 状态机 / 唯一约束 |
| 用 Redis 分布式锁做唯一幂等手段 | 锁过期/Redis 故障后失效 | 只作辅助，主手段用 DB 唯一约束 |
| 一条消息处理时间 > `max.poll.interval.ms` | 触发 rebalance，消息重复 | 减小 `max.poll.records` 或异步化 + 手动 ack |
| 扩消费者但分区不够 | 空转 + rebalance 风暴 | 先扩分区（注意 key 映射）或提升单实例吞吐 |
| 死信队列无人消费 | 数据静默丢失 | DLT 消费者 + 告警 + 定期巡检积压 |
| 顺序消息用全局单队列 | 吞吐被单线程锁死 | 按业务主键分区，局部有序即可 |
| 消息体塞大对象（> 1MB） | Broker 限流、网络与存储放大 | 消息只传 ID + 变更摘要，消费方回查 |
| 把 MQ 当事务的替代品 | 无法保证与 DB 的原子性 | 本地消息表 / 事务消息（见 09 篇） |

## 5. 落地检查表

**生产端**

- [ ] `acks=all`（Kafka）/ 同步发送（RocketMQ），关键业务有发送结果校验
- [ ] `enable.idempotence=true`（Kafka）或消息带唯一 `msgId`
- [ ] 发送失败有落库 + 补偿路径（本地消息表 / 定时重发）
- [ ] 顺序消息显式指定 key，且 key 为业务主键
- [ ] 消息体 < 100KB，只传 ID 与必要字段

**消费端**

- [ ] 手动提交 offset / 手动 ack，处理成功后提交
- [ ] 幂等实现（去重表 / 状态机 / 唯一约束），且与业务操作同事务
- [ ] 可重试与不可重试异常分类处理，重试有次数上限与退避
- [ ] 死信队列有消费者 + 告警 + 巡检
- [ ] `max.poll.records` × 单条耗时 < `max.poll.interval.ms`
- [ ] 消费逻辑内无长事务、无同步 RPC 链

**运维**

- [ ] 监控：消费延迟（lag）、积压量、消费 TPS、失败率、rebalance 次数
- [ ] 分区数 ≥ 预期最大消费者实例数
- [ ] 副本数 ≥ 3，`min.insync.replicas` ≥ 2
- [ ] 保留策略（retention）覆盖最坏情况下的消化时间
- [ ] 有积压应急预案（扩分区 / 临时搬运 Topic / 降级跳过非关键消息）

## 6. 三个追问

1. **为什么用 MQ 做异步，而不是线程池 / `@Async`？**
   线程池是**进程内**异步，进程重启即丢任务，且无法跨服务解耦。MQ 提供持久化、可重放、跨服务解耦、削峰。代价是引入"最终一致"与"运维一套中间件"。判断依据：**任务是否需要持久化与重试**——需要就上 MQ，不需要（如发通知、写日志）用线程池更简单。

2. **引入它之后，运维成本由谁承担？**
   MQ 把"同步调用的确定性"换成了"异步的不确定性"：消息可能延迟、重复、乱序、丢失。这些不确定性最终由**业务代码（幂等/补偿/对账）与 SRE（积压/延迟/死信监控）** 共同承担。一个团队引入 MQ 却没有幂等规范和对账任务，等于把 bug 从"偶发报错"变成"偶发资损"。

3. **当它失效时，系统如何优雅退化？**
   生产者失败 → 落本地消息表，由定时任务补偿（最终必达）；Broker 不可用 → 降级为同步调用（限流保护下游）或写本地队列；消费积压 → 非核心消费者暂停（降级），优先保障交易链路。**关键是"消息不能凭空消失"**——任何失败都必须有落库或告警。

### B. 跑验证：看本地消息表的状态流转

```bash
# 1) 起 MQ（micro 档才有 namesrv + broker）
scripts/up.sh micro

# 2) 启动（rocketmq.name-server 指向 18876）
POLARIS_DEMO=true scripts/run-monolith.sh --bg

# 3) 下一单
curl -s -X POST http://127.0.0.1:18080/api/order \
  -H 'Content-Type: application/json' \
  -d '{"userId":"u_88231","merchantId":8821,"skuId":90001,"quantity":1}'

# 4) 观察 outbox：应该从 PENDING 变成 SENT
docker exec -it polaris-mysql mysql -uroot -proot polaris_order -e "
SELECT id, msg_id, topic, status, retry_count, next_retry_at
FROM t_local_message ORDER BY id DESC LIMIT 10\G"
```

期望：新记录 `status=0`（PENDING）→ 1~2 秒后变 `status=1`（SENT）。
**如果一直是 0**，说明 relay 没跑起来或 broker 连不上 —— 这正是"消息丢了"最常见的真因：
业务以为发出去了，其实连消息表都没人转发。

再把 broker 停掉重跑，能看到 `retry_count` 增长、`next_retry_at` 按 1s/5s/15s 退避：

```bash
docker stop polaris-rocketmq-broker
# 下一单，然后观察 retry_count 与 next_retry_at
docker start polaris-rocketmq-broker
```

### C. 看结果：这张表就是"消息没丢"的证据

`services/order-service/src/main/resources/db/migration/V101__init_order.sql` 里三个设计细节值得单独看：

| 设计 | 为什么 |
|---|---|
| `id BIGINT AUTO_INCREMENT`（而不是雪花） | relay 用 `ORDER BY id ASC` 保证同一聚合根的消息按产生顺序发出。**雪花在同一毫秒内不保证单调递增** —— 这是 A0 规范里明确列出的例外 |
| `UNIQUE KEY uk_msg_id (msg_id)` | 重复写入直接失败，而不是产生两条一样的消息 |
| `KEY idx_status_next (status, next_retry_at)` | relay 每 1s 扫一次待发送。没有这条索引，扫描就是全表 —— 消息表涨到千万级时会把库拖死 |

### D. 一句话结论

「消息不丢」不是 MQ 的保证，而是**发送方的保证**：
业务数据与"要发的消息"在同一个本地事务里落库，再由 relay 负责投递 ——
中间任何一步失败，消息都还在表里，能重试、能对账、能人工补发。
MQ 只负责"尽量送到"，**端到端的正确性靠消费端幂等 + 对账兜底**。

> **诚实说明（缺口）**：本篇的消费端演示还不完整。
> `OrderTimeoutConsumer`（延迟消息消费）、`OrderReconcileJob`（T+1 对账）
> 与业务侧 `OrderEventPublisher` 尚未落地，计划在 M6 补齐。
> 目前**能跑通的是发送侧**：本地消息表 → relay → broker → `notify-service` 的两个消费者。
