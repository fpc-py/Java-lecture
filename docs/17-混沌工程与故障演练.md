# 17 · 混沌工程与故障演练

> **阶段**：稳定性建设 / 故障预防
> **痛点**：降级开关写了三年，从没验证过是否真的生效；熔断阈值配了，但从没在真实流量下触发过；等到真故障时，"以为有"的保护一个都没起作用。

---

## 1. 真实故障场景

### 场景 A：降级开关"存在但无效"

大促前，架构评审确认"推荐服务有降级方案：出问题就关开关，返回热门榜单"。大促当天推荐服务超时，值班同学打开开关——**接口仍然超时**。

排查发现：开关只包住了"调用推荐服务"这段代码，但外层还有一个 `@Transactional` 包裹了整个方法，超时依然把事务与线程拖住；而且开关是从本地 `application.yml` 读的，没接配置中心，**修改需要重启**。

**根因**：降级方案从未被验证过。**没演练过的预案，等于没有预案。**

### 场景 B：熔断阈值配错了，永远不会触发

```java
DegradeRule rule = new DegradeRule("callRecommend");
rule.setCount(2000);       // 慢调用 RT 阈值 2000ms
rule.setSlowRatioThreshold(0.9);
rule.setMinRequestAmount(100);
```

实际下游正常 RT 是 50ms，故障时 800ms（远未达到 2000ms），**熔断永不触发**，请求全部卡在 800ms。用户等待 800ms 而不是快速拿到兜底数据。

**根因**：阈值没有基于真实 RT 分布，且**从未在演练中验证过是否触发**。

### 场景 C：演练影响了生产

某团队在生产环境直接 `chaosblade` 给订单服务的数据库加了 3 秒延迟。没想到这个库是**共享库**，支付服务也在用。演练 5 分钟，支付成功率掉了 40%，造成真实客诉。

**根因**：没有评估"爆炸半径"（blast radius）。**混沌工程的第一原则是"可控"**，而不是"真实"。

### 场景 D：演练只做了单点，链路一压就崩

逐个验证了"DB 慢""Redis 挂""下游超时"三个单点，都能正常降级。但大促时**三个同时发生**（真实故障往往如此），系统直接雪崩——因为降级后的兜底逻辑本身也依赖 Redis。

**根因**：单点演练无法暴露"组合故障"与"降级路径本身有依赖"的问题。

## 2. 原理剖析

### 2.1 混沌工程与测试的本质区别

| 维度 | 传统测试 | 混沌工程 |
|---|---|---|
| 目的 | 验证"已知行为是否正确" | 发现"未知的脆弱点" |
| 方法 | 给定输入，断言输出 | 注入真实故障，观察系统行为 |
| 环境 | 测试环境 | **优先生产**（真实流量、真实依赖） |
| 结论 | 通过/失败 | 稳态是否被破坏、保护是否生效 |
| 心态 | 证明它没问题 | **假设它有问题，去找到它** |

**混沌工程的正式定义（Principles of Chaos Engineering）**：

```
① 建立稳态假设（用指标定义"系统正常"）
② 模拟真实世界的故障（网络、磁盘、进程、依赖）
③ 在生产环境做实验（真实流量才能暴露真实问题）
④ 自动化、持续运行
⑤ 最小化爆炸半径
```

### 2.2 稳态假设：没有它就不是实验

**稳态（Steady State）必须是可量化的**：

```
❌ 错误："系统正常工作"
✅ 正确："下单接口 5 分钟内 P99 < 300ms，成功率 > 99.5%，订单积压 < 100 条"
```

```
实验流程：
  ① 测量稳态（注入前 10 分钟）
  ② 注入故障（如：库存服务延迟 500ms）
  ③ 持续观测（注入期间 + 注入后 10 分钟）
  ④ 判定：
     ├─ 稳态未破坏 + 保护生效（熔断触发、降级返回） → 假设成立
     └─ 稳态被破坏 → 发现了真实的脆弱点（这是收获，不是失败）
```

### 2.3 爆炸半径（Blast Radius）的四层控制

| 层次 | 控制手段 |
|---|---|
| **范围** | 单实例 → 单可用区 → 全集群；单接口 → 单服务 → 全链路 |
| **流量** | 只影响 1% 请求（按 header/uid 灰度标记） |
| **时间** | 限制时长（如 3 分钟），到点自动停止 |
| **对象** | 只影响测试账号/内部员工（生产环境的第一步） |

```java
// 精准流量注入：只对带 chaos 标记的请求生效（ChaosBlade JVM 实验支持）
// 请求头加 X-Chaos: true → 只有这个请求被注入延迟
```

### 2.4 四种故障类型与对应的系统能力

| 故障类型 | 注入方式 | 验证的能力 |
|---|---|---|
| **资源型** | CPU 满载、内存占满、磁盘 IO 高 | 容量水位、弹性伸缩、超时 |
| **网络型** | 延迟、丢包、DNS 失败、连接拒绝 | 超时、重试、熔断、多活切换 |
| **依赖型** | DB 慢/挂、Redis 挂、MQ 不可用 | 降级、缓存兜底、消息重投 |
| **应用型** | 抛异常、返回错误、方法延迟 | 异常处理、幂等、状态机 |

**优先级建议**：先做"依赖型 + 应用型"（成本低、收益高），再做"网络型"，最后做"资源型"（需要真实流量与容量余量）。

**四类常用实验（附完整命令与恢复方式）**：

```bash
# ---------- ① CPU 满载（验证限流与弹性） ----------
./blade create cpu load --cpu-percent 80 --timeout 120
# 恢复：到点自动恢复，或
./blade destroy <uid>

# ---------- ② 方法延迟（验证超时与熔断，最常用） ----------
# 给 OrderService.query 方法加 500ms 延迟，只影响 20% 的调用
./blade create jvm delay --time 500 --classname com.example.order.OrderService \
    --methodname query --percent 20

# 只对特定参数生效（精准流量）
./blade create jvm delay --time 3000 --classname com.example.pay.PayService \
    --methodname pay --param-names orderNo --param-values '202610240001'

# ---------- ③ 抛出异常（验证兜底与幂等） ----------
./blade create jvm throwCustomException --exception java.lang.RuntimeException \
    --classname com.example.stock.StockClient --methodname deduct

# ---------- ④ 网络延迟（验证超时与重试） ----------
./blade create network delay --time 3000 --interface eth0 --local-port 6379
# 恢复
./blade destroy <uid>        # uid 在创建输出里，务必记下
./blade destroy --all        # 紧急情况下全部恢复
```

### 3.3 演练的成熟度阶梯

```
Level 0：没有演练，靠真实故障学习
Level 1：预发环境单点演练（手动执行、手动观测）
Level 2：预发环境链路演练（组合故障、有剧本、有验收标准）
Level 3：生产环境小流量演练（1% 流量、自动止损、定期执行）
Level 4：生产环境持续混沌（Chaos Monkey 式随机注入、自动化闭环）
Level 5：故障演练成为发布流程的一部分（每次大版本发布前跑一遍）
```

**大多数团队的现实目标**：Level 2–3。**跳过 Level 2 直接做生产演练，是场景 C 的典型来源。**

### 3.4 自动化：把演练变成常规动作

```yaml
# 每周自动跑一次（GitLab CI 定时任务）
chaos-weekly:
  stage: chaos
  rules: [{ if: '$CI_PIPELINE_SOURCE == "schedule"' }]
  script:
    # 1. 记录基准
    - ./scripts/baseline.sh > baseline.txt
    # 2. 注入（带 timeout 自动恢复，防止忘记 destroy）
    - ./blade create jvm delay --time 500 --classname com.example.order.OrderService
        --methodname query --timeout 180 > uid.txt
    # 3. 观测 3 分钟
    - sleep 180
    # 4. 校验：稳态是否被破坏
    - ./scripts/verify-steady-state.sh || exit 1
  after_script:
    - ./blade destroy --all || true      # 无论如何都要恢复
  allow_failure: true                     # 演练失败不阻塞发布，但要告警
```

> **`--timeout` 与 `after_script` 双保险**是防止"忘记恢复"的关键。实践中，忘记 destroy 是演练事故的第一大原因。

## 4. 边界条件与反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 第一次就在生产全量注入 | 可能造成真实事故 | 预发 → 生产 1% → 逐步扩大 |
| 没有稳态假设就注入 | 无法判断"是否正常" | 先定义可量化指标 |
| 注入不设 timeout | 忘记恢复，长时间影响 | `--timeout` + `destroy --all` 兜底 |
| 只演练单点 | 掩盖组合故障 | 逐步做链路演练（2–3 个故障叠加） |
| 注入前不通知 | 值班同学把演练当故障，误操作 | 提前通知 + 标记流量 + 演练窗口 |
| 共享资源上做注入 | 影响其他业务（场景 C） | 明确爆炸半径，隔离实例 |
| 演练后不跟进改进项 | 问题被记录但不解决 | 改进项进任务系统，有 owner 与 deadline |
| 只演练"能降级"的场景 | 避开真正脆弱的地方 | 优先演练"最担心发生"的场景 |
| 演练环境与生产差异大 | 结论不可信 | 至少保证中间件版本、数据量级接近 |
| 用演练代替监控 | 演练是抽查，监控是全时 | 两者互补，不互相替代 |

## 6. 三个追问

1. **为什么要在生产做混沌实验，预发不够吗？**
   预发与生产的差异是**本质性的**：真实流量分布、真实数据量级、真实依赖拓扑、真实的"别人也在跑"。预发能验证"逻辑是否正确"，但验证不了"容量是否够、降级是否真的生效、告警是否真的会响"。所以实践路径是：**预发验证机制（Level 2）→ 生产验证真实行为（Level 3）**，而不是二选一。

2. **引入它之后，运维成本由谁承担？**
   混沌工程的成本不在工具（开源免费），而在**组织能力**：需要有人设计剧本、有人执行、有人观测、有人跟进改进项，且需要"允许在生产和预发制造故障"的组织授权。这部分通常由 SRE/稳定性团队牵头，业务团队配合。**没有组织授权就做混沌工程，等于给自己埋雷。**

3. **当它失效时，系统如何优雅退化？**
   演练本身失控（影响面超出预期）→ 立即 `destroy --all` + 触发回滚；改进项没落地→ 下次演练重点回归；工具不可用 → 退化到"手动故障注入"（改配置、停依赖、限流到 1）。**混沌工程的底线是"任何时刻都能一键恢复"，这个能力必须先验证。**

### B. 跑验证：一次完整的最小可行演练

演练的四段结构（对应 §3 的模板），下面用真实的命令走一遍。

**① 稳态假设（先量，再注入）**

```bash
scripts/up.sh min
POLARIS_DEMO=true scripts/run-monolith.sh --bg
scripts/loadtest.sh --mode create --steps 16 --duration 20
```

记录这一轮的数字作为基线（本案例实测：8 并发 45.8 QPS、P50 157ms）。

**② 故障注入（可逆、有明确边界）**

```bash
scripts/stop-monolith.sh
POLARIS_DEMO=true scripts/run-monolith.sh --bg --polaris.promotion.simulate-delay-ms=3000
```

注入的是"优惠服务变慢 3 秒"，影响面仅限弱依赖，**不触碰数据库与库存**。

**③ 预期行为（可验证，不是"应该没事"）**

```bash
scripts/loadtest.sh --mode create --steps 16 --duration 20
curl -s http://127.0.0.1:18080/actuator/bulkpools | python -m json.tool
```

期望三条同时成立：

| 断言 | 期望 | 若失败说明 |
|---|---|---|
| `biz-rec` 池 active | **8/8 打满** | 故障没注入成功 |
| `biz-stock` 池 active | **0** | 舱壁失效，弱依赖污染了强链路 |
| 下单 P99 | **< 400ms** | 超时/降级没生效 |

**④ 止损与回滚**

```bash
scripts/stop-monolith.sh
POLARIS_DEMO=true scripts/run-monolith.sh --bg      # 去掉注入参数
scripts/loadtest.sh --mode create --steps 16 --duration 20   # 回到基线
```

止损必须**一条命令、10 秒内**完成。做不到这一点的演练设计，等于在生产上赌运气。

### C. 看结果：演练前后

| 指标 | 稳态 | 注入 3s 延迟 | 注入 + 舱壁失效时 |
|---|---|---|---|
| P99 | **335ms** | **335ms**（不变） | 687ms |
| rec 池拒绝 | 0 | **0** | 713 |
| 强链路受影响 | 无 | **无** | 全链路超时 |

中间那一列才是"演练通过"的样子：**故障发生了，用户没感觉**。
右边那一列是修复前的真实证据（`2026-10-27-1405-loadtest-create-weak-3s`），
它证明这个断言不是摆设 —— 不加舱壁，P99 真的会翻倍。

> **诚实说明（缺口）**：`chaos/` 目录为空，§3 里那 6 个剧本
> （进程 kill、网络延迟、磁盘满、依赖 500、时钟漂移、DNS 失败）
> 尚未落成可执行脚本。目前唯一能跑的注入是"弱依赖延迟"这一个，
> 因为它只需要一个配置项就有、且天然可逆。

### D. 一句话结论

混沌工程与"乱搞生产"的区别只有一条：**有没有可验证的稳态假设**。
没有假设的注入只是事故；有假设、有止损、有观测项的注入才是实验。
本案例能跑通的那个实验（弱依赖慢 3 秒）之所以有价值，是因为它同时给出了
「该看到什么」（断言表）和「看到了说明什么」（失败归因），
而不是"注入一下看看会不会挂"。
