# 故障证据索引

本目录下的每一份文件都是**真实执行产生**的，不是手写示例。
采集脚本、执行命令、可复现参数都写在各自的目录里。

## 为什么要有这份索引

故障类文档最常见的失效方式不是"写错了"，而是"写对了但无法验证"：

> "线程池被打满时，你应该先看 `jstack`。" —— 然后呢？满的时候长什么样？

一句话如果没有对应的**当时快照**，读者只能选择相信或不相信。
所以本仓库存证据不存结论：结论写在十二讲里，证据放在这里，
每条证据都能反查到"它证明了哪一句话"。

## 证据怎么产生

| 脚本 | 产出物 | 用途 |
|---|---|---|
| `scripts/capture-evidence.sh` | `summary.md` + `0x-*.txt` | JVM 运行态快照（jstack / NMT / GC / 类直方图） |
| `scripts/loadtest.sh` | `curve.md` + `curve.csv` | 阶梯压测曲线（QPS / P50 / P90 / P99 / 错误率） |
| `scripts/redis-load.sh` | `summary.md` + `distribution.csv` + `freq.txt` | Redis 访问分布（Zipf 倾斜）+ 原生基准对照 + 热 key 交叉验证 |
| `scripts/oversell.sh` | `summary.md` + 三个 `*.json` | 超卖复现：同一需求的三种实现打同样的并发 |
| `scripts/cache-breakdown.sh` | `summary.md` + `deltas.tsv` | 缓存击穿 / 雪崩 / 穿透的五场景对照 |

这些脚本的共同约定：

- 目录名 = `YYYY-MM-DD-HHMM-<tag>`，按时间排序即执行顺序
- 同一件事的"修复前 / 修复后"是**两个目录**，不许覆盖 —— 否则就丢掉了对比这条最有价值的信息
- 数字旁边必须有"在哪一层测的"：同一台机器上，容器内 `redis-benchmark`
  能跑 15.6 万 rps，宿主机经 Docker 端口转发只能跑 6711 ops/s，差 23 倍。
  脱离测量层次谈吞吐是没有意义的
- 判据要挑**量级对得上**的那个指标：证明"1 次回源"就不能用本底噪声 7 次的
  `Com_select`，得换成按 SQL 指纹计数；而证明"6% 的抖动"根本不该看个位数

### 2026-10-27-1402-loadtest-query

| 项 | 内容 |
|---|---|
| 场景 | 库存查询接口（纯读，无事务） |
| 阶梯 | 8 → 128 并发 |

| 并发 | QPS | P50 | P99 |
|---|---|---|---|
| 8 | 1724 | 3ms | 14ms |
| 16 | 3027 | 4ms | 13ms |
| 32 | 3194 | 8ms | 27ms |
| **64** | **3323** | 17ms | 43ms |
| 128 | 3192 | 36ms | 105ms |

| 项 | 内容 |
|---|---|
| 证明什么 | **天然拐点在 64 并发**：再往上加并发，QPS 从 3323 回落到 3192，而 P99 从 43ms 涨到 105ms（翻 2.4 倍）。多出来的并发全在排队 —— 这就是单实例的容量天花板，也是"加并发不会加吞吐"的教科书形状 |
| 安全水位 | 按 0.7 折 → **约 2300 QPS**（拐点是函数，不是拍出来的） |
| 对应讲次 | L04（单机极限）、ch02 |

> 一个容易被忽略的细节：查的是 8→128，但真正有信息量的是 **64 → 128 这一段**。
> 前面几档 QPS 一直在涨，说明"没到瓶颈"；只有这一段同时看到
> "吞吐退坡 + 延迟翻倍"，才能确认瓶颈真的在这台机器上。

## 已知的采集局限

诚实标注比假装完备有用：

1. **`performance_schema` 的 digest 计数在并发下会少记约 6%**。
   实测：串行 200 次精确记 200，50 并发 200 次只记到 187。
   原因是统计先在每个数据库线程的本地缓冲区累加、再周期性合并到全局表。
   所以 `cache-breakdown` 的所有数字都应理解为**下限**。
   对"1 次 vs 200 次""200 次 vs 4000 次"这类结论毫无影响，
   但如果要证明"恰好等于 1"，得串行跑一次才作数。
2. **`cache-breakdown` 的命中基线会带抖动**。库存快照 TTL 只有 3 秒，
   测量窗口一旦跨过 TTL 边界，A 场景就会多出 1 次回源。
   这不是 bug，是短 TTL 的固有代价 —— 也说明压测结论要看量级，不能盯着个位数。
3. **`redis-distribution` 的命中率恒为 100%**。灌完数据就压、没有 key 过期，
   所以那个脚本造不出 MISS。击穿/穿透/雪崩必须靠 `cache-breakdown.sh` 主动制造 ——
   这两件事不能指望一个脚本全包。
4. **`loadtest` 每档只有 12s**。够看拐点，不够看长稳（内存泄漏、连接泄漏、
   定时任务抖动都要小时级才能暴露）。长稳单独做，不混在阶梯里。
5. **单机数字不代表容量规划**。`capacity-model.md` 里的估算必须写明采集环境，
   否则换个笔记本就复现不出来。
6. **停服 0×502 未验**（优雅停机）。Windows 下不带 `/F` 的 `taskkill` 对 `java -jar`
   不触发 shutdown hook，需可靠的 SIGTERM 环境。已挪到 M9（探针）与 M10（混沌）一并验证。
7. **超卖复现依赖业务窗口**。`oversell.sh` 默认 `--window 30`，
   如果某轮 NAIVE 没超卖，说明并发没造出来 —— 把窗口调大重跑，
   **不要**拿"这次没超卖"当结论。
