# 取证摘要 · cache-breakdown

| 项 | 值 |
|---|---|
| 采集时间 | 2026-10-27 20:32:41 +0800 |
| 判据一 | `performance_schema` 按 SQL 指纹计数：`SELECT ... FROM t_stock WHERE sku_id = ?` 被执行了多少次 |
| 判据二 | **单飞合并数**（缓存层自报：多少个并发请求被合并到了同一次执行） |
| 本底 | 空转 2 秒测得 **0** 次（按指纹计数，期望 0） |
| 已知误差 | 并发下 digest 聚合会少记约 6%（串行 200 次精确记 200，50 并发只记 187）—— 所有数字应理解为**下限** |

## 结果

| 场景 | 请求数 | 不同 key | 库回源次数 | 单飞合并 | 回源率 |
|---|---|---|---|---|---|
| A 命中基线 | 200 | 1 | **1** | 3 | 0.5% |
| B 击穿·单key并发回源 | 200 | 1 | **1** | 199 | 0.5% |
| C 雪崩·批量失效 | 4000 | 200 | **190** | 0 | 4.8% |
| D 穿透·有空值缓存 | 4000 | 200 | **189** | 0 | 4.7% |
| E 穿透·无缓存对照 | 4000 | 200 | **3573** | 0 | 89.3% |

## 结论

1. **命中基线**：200 次请求，库回源 **1** 次 —— 这就是「缓存有用」的参照系，后面所有数字都跟它比。
   这 1 次来自「缓存恰好在 3 秒 TTL 边界上过期了一次」：短 TTL 会让命中基线本身带抖动，
   这也是为什么压测结论要看量级，不能盯着个位数较真。
   这就是「缓存有用」的参照系，后面所有数字都跟它比。
2. **击穿**：200 个并发同时回源同一个刚失效的 key，库只多扛了 **1** 次 SELECT。
   单飞把 200 次并发回源收敛成 1 次（自报合并 199 次）。没有它，这个数字就是 200。
   **前提是回源足够慢**：本场景人为注入 50ms 延迟。本机主键查询只要 1ms 时，
   第一个请求早已把缓存填好，后面的直接命中 —— 击穿根本不会发生。这也是判断要不要上单飞的第一步：先量回源耗时。
3. **雪崩**：200 个 key 同时失效、4000 次请求，库回源 **190** 次。
   它**约等于 key 的数量**：每个 key 只被重建一次（差额在 digest 少记的 6% 以内）。
   本场景的请求分配让每个 key 同一时刻只有 1 个请求，单飞没有可合并的对象（合并 0 次）——
   雪崩的危险是**总量**，不是单点并发，这正是它和击穿的区别。
   但请注意，单飞拦不住「200 个 key 都失效」这件事本身 ——
   **单飞解决击穿，解决不了雪崩**；雪崩只能靠 TTL 抖动和预热。
4. **穿透**：4000 次查不存在的 SKU ——
   - 有空值缓存：库回源 **189** 次，单飞合并 0 次
   - 无任何缓存：库回源 **3573** 次
   同样的流量，库压力差 **18.9 倍**。
   空值缓存挡掉了其中 3384 次重复查询，剩下的 189 次是「每个不存在 key 的首次回源」——那部分挡不住，因为缓存也是空的。
   但它挡的是「重复查同一个不存在的数据」；
   如果每次换一个不存在的 ID，空值缓存一个都挡不住 ——
   那种场景要靠布隆过滤器（在 Redis 之前先挡一次）或参数校验。

> 三个故障的解法互不替代：击穿 → 单飞；雪崩 → TTL 抖动 + 预热；
> 穿透 → 空值缓存 + 布隆过滤器。把它们混成一句「加个缓存就好了」，
> 正是线上出事的起点。
