# 20 · 贯穿主线：架构思维作为"操作系统"

> 前面 19 篇讲的是"技术"，这一篇讲的是**做出技术决定的那套底层逻辑**。
> 提纲里那句话是整份材料的题眼：**企业级 Java 的竞争力，恰恰体现在那些"配置之外"的判断上。**

## 1. 为什么"会用"和"能决策"是两件事

```
会用：知道 Redis 怎么配、Sentinel 怎么设阈值、Seata 怎么开注解
能决策：知道什么情况下不该用 Redis、阈值该由谁定、引入 Seata 后谁来承担代价
```

这两者的差距，在代码层面看不出来，在**事故现场**和**架构评审**上暴露无遗。

| 场景 | "会用"的回答 | "能决策"的回答 |
|---|---|---|
| 要不要上微服务 | "现在都拆微服务" | "你的团队 8 人、模块容量相近、变更总是一起——拆了就是分布式单体" |
| 缓存要不要加 | "加一层 Redis 就快了" | "瓶颈是 DB 的写放大，加缓存只解决读；先解决写，缓存后置" |
| 要不要上 Seata | "AT 模式最省事" | "这个流程可以改成异步，用本地消息表 + 对账，成本低一个数量级" |
| 限流配多少 | "配 1000 吧" | "压测容量 2500，取 0.7 得 1750；超了由谁扩容，也有明确 owner" |

**判断标准**：你的方案能不能回答"为什么不是另一个"，以及"它失效时谁来兜底"。

## 2. 三个追问的完整方法论

### 追问一：为什么选这个技术，而不是另一个？

**不要用"社区流行度"做理由**，用"约束条件"做理由。

#### 选型评分卡（可直接用）

| 维度 | 权重 | 评分要点 |
|---|---|---|
| 是否解决当前瓶颈 | ×3 | 它针对的问题，是不是我真正的瓶颈？（先定位瓶颈，再选型） |
| 团队掌握度 | ×3 | 现有成员能否在 3 个月内独立排障？还是必须依赖外部专家？ |
| 运维成本 | ×3 | 需要新增多少组件、监控、值班、升级工作？ |
| 失效模式 | ×3 | 它挂了会发生什么？降级路径是否清晰？ |
| 生态与人才 | ×2 | 招人容易吗？遇到问题有资料吗？ |
| 长期演进 | ×2 | 三年后还在维护吗？社区活跃度？ |
| 成本（钱） | ×2 | 机器、许可、云服务费用 |

**用法**：两个候选方案各自打分，**差距 < 10% 时选更简单的那个**。因为简单方案的隐性成本更低，而所有评分都有误差。

#### 一个真实的决策示例

> **问题**：订单履约链路需要异步解耦，选 Kafka 还是 RocketMQ？

| 维度 | Kafka | RocketMQ |
|---|---|---|
| 解决瓶颈 | 吞吐最高 | 吞吐足够（十万级） |
| 团队掌握度 | 有 2 人用过，但没运维过分区规划 | 有 4 人用过，含一个能处理 broker 故障的 |
| 运维成本 | 需 ZK/KRaft + 分区规划 + 监控体系 | 相对简单，社区中文资料多 |
| 失效模式 | 分区不可用、rebalance 风暴 | 主从切换，客户端自动重连 |
| 关键能力 | 无事务消息、无延迟消息 | **有事务消息 + 任意延迟消息**（订单超时刚需） |
| 结论 | 适合数据管道 | **选它** |

**决策记录里要写的是"排序理由"**，不是"对比表格"。比如："延迟消息是订单超时关单的刚需，Kafka 需要外部方案（自建时间轮或扫表），这会把一个中间件问题变成一个业务代码问题——这是决定性的。"

### 追问二：引入它之后，运维成本由谁承担？

**每一个技术决策都在向某一侧转移复杂度**。这个转移必须被显式记录。

#### 复杂度转移表（评审必填）

| 决策 | 转移给谁 | 具体成本 |
|---|---|---|
| 引入 Redis 缓存 | SRE + 研发 | 缓存集群运维、大 key 巡检、一致性排查、命中率调优 |
| 拆分微服务 | 研发 + SRE | 流水线 × N、看板 × N、跨服务排障、契约管理 |
| 引入 MQ | 研发 | 幂等、对账、积压监控、死信处理 |
| 引入 Seata | 研发 + DBA | 全局锁竞争调优、undo_log 清理、补偿失败处理 |
| 上 K8s | SRE | 集群运维、网络（CNI）、存储、升级 |
| 上 Service Mesh | 平台团队 | 控制面运维、证书轮转、Envoy 调优、排障复杂度 |

**评审时必问的三句话**：

```
① 这个组件挂了，谁在凌晨 3 点起来处理？
② 它需要的监控、告警、看板，谁来做？做完谁看？
③ 升级它需要协调几个团队？上次升级是什么时候？
```

如果三个问题都答不上来，这个决策还没准备好。

### 追问三：当它失效时，系统如何优雅退化？

**降级预案不是事后补的，是架构设计的一部分。**

#### 失效模式分析（FMEA 简化版）

| 依赖 | 失效表现 | 影响面 | 降级策略 | 用户感知 |
|---|---|---|---|---|
| MySQL | 连接超时 | 全部写操作 | 只读降级 + 缓存兜底 | "暂时无法下单" |
| Redis | 超时/连接拒绝 | 缓存失效，DB 压力上升 | 跳过缓存 + 限流保护 DB | 变慢，但可用 |
| 推荐服务 | 5s 超时 | 推荐位空白 | 返回热门榜单（本地缓存） | 内容不个性化 |
| 支付网关 | 回调失败 | 订单卡在"支付中" | 主动查询补偿 + 延迟关单 | "支付结果确认中" |
| MQ | 不可用 | 异步链路中断 | 本地消息表 + 定时补偿 | 延迟生效 |
| 认证服务 | 不可用 | 无法登录 | 本地公钥验签（JWT 自包含） | 无感知 |

**设计时的三个动作**：

```
① 列出所有外部依赖（含"内部的"其他服务）
② 对每个依赖回答："它挂了，我的用户看到什么？"
③ 为每个"不可接受的影响"设计降级路径，并写进代码（不是文档）
```

**"优雅退化"的反面是"硬失败"**：

| 硬失败 | 优雅退化 |
|---|---|
| 依赖超时 → 请求挂 30 秒 → 504 | 依赖超时 → 200ms 熔断 → 返回兜底数据 |
| 缓存挂了 → 全量打 DB → DB 挂 | 缓存挂了 → 限流 → 只放行核心流量 |
| 消息队列挂了 → 业务直接失败 | 消息队列挂了 → 写本地表 → 恢复后补发 |

## 3. ADR：把决策变成可追溯的资产

**Architecture Decision Record（架构决策记录）** 是解决"三个月后没人记得为什么这么设计"的唯一有效手段。

### 3.1 ADR 模板（一页纸）

```markdown
# ADR-012：订单履约链路引入 RocketMQ 而非 Kafka

- 状态：已采纳（2026-10-20）
- 决策人：@张三（架构）、@李四（SRE）、@王五（订单域 owner）
- 关联：[ADR-008 异步化改造]、[故障复盘 FR-2026-031]

## 背景
订单履约需要异步解耦，且存在两类刚需：
1. 订单 30 分钟未支付自动关单（延迟消息）
2. 支付成功后通知库存/积分/物流（事务消息，保证本地事务与消息一致）
当前日均 200 万条，峰值 8000 TPS，预计三年内增长 5 倍。

## 备选方案
A. Kafka 3.x：吞吐最高，无原生延迟/事务消息（事务消息需自行实现 outbox 模式）
B. RocketMQ 5.x：原生支持延迟消息（任意时间）与事务消息
C. 自研基于 DB 轮询 + 定时任务：无新组件，但 8000 TPS 下 DB 压力不可接受

## 决策
选择 B。

## 理由
1. 延迟消息与事务消息是刚需，Kafka 需要引入 outbox 表 + 定时扫描，
   等于把中间件问题转成业务代码问题（额外维护成本 + 一致性风险）。
2. 团队有 4 人具备 RocketMQ 运维经验（含 broker 故障处理），
   Kafka 仅 2 人且无运维经验。
3. 吞吐 8000 TPS 远低于 RocketMQ 上限，Kafka 的吞吐优势在本场景不构成决策依据。

## 代价与风险
- 引入新中间件：需新增 3 节点集群、监控看板、值班手册。
- 运维成本承担方：SRE（集群）+ 订单域研发（消费端幂等、积压处理）。
- 风险：RocketMQ 5.x 的 proxy 模式在生产验证不足，首期使用 4.x 兼容模式。

## 失效与退化
- Broker 集群不可用：生产者降级为同步调用 + 限流；写本地消息表，恢复后补发。
- 消费积压：优先保障支付链路消费者，履约链路消费者降级暂停。

## 重新评估的触发条件
- 日均消息量 > 2000 万，或出现 RocketMQ 无法满足的新需求（如流式回溯分析）。
```

### 3.2 ADR 的维护规则

| 规则 | 说明 |
|---|---|
| 一页纸 | 超过两页没人看 |
| 只在"有争议/有代价"的决策上写 | 不用给每个 CRUD 写 ADR |
| 写在代码仓库里 | `docs/adr/`，随代码 review |
| **不修改历史 ADR** | 变更时新增 ADR，把旧的标为 "Superseded by ADR-0xx" |
| 定期回看 | 每季度看一次"触发条件是否已满足" |

**ADR 最大的价值不是"记录决定"，而是"记录当时的约束"**。三年后回头看，你会发现很多决策在当时是对的——因为当时的约束（团队规模、流量、预算）已经变了。

## 4. 技术决策的六种反模式

| 反模式 | 表现 | 后果 |
|---|---|---|
| **简历驱动开发** | 为了用新技术而重构（"我要用一下响应式"） | 引入复杂度，收益不明，维护者离职后无人能改 |
| **流行度驱动** | "社区都在用" | 忽略了团队能力与场景差异 |
| **大厂复制** | "阿里这么做的" | 大厂的约束（流量、团队、预算）与你完全不同 |
| **过度设计** | 10 万用户上分库分表 + 微服务 + 服务网格 | 复杂度超过业务需要，交付速度骤降 |
| **拒绝演进** | "一直这么用，没出过事" | 技术债累积，最终以更大代价偿还 |
| **只有一个方案** | 评审时只有一条路 | 没有对比就没有判断，风险不可见 |

**对抗方式**：

```
① 每个重大决策必须 ≥ 2 个备选方案（包括"什么都不做"）
② 必须写出"这个方案在什么条件下会失败"
③ 必须说明"谁承担运维成本"
④ 必须有"重新评估的触发条件"
```

## 5. 故障复盘：把事故变成组织能力

**复盘的目的不是追责，是修正系统**（包括技术系统与流程系统）。

### 5.1 复盘模板

```markdown
# 故障复盘：2026-10-18 订单服务大面积超时（P1，影响 42 分钟）

## 一、时间线（精确到分钟）
| 时间 | 事件 |
|---|---|
| 14:02 | 监控告警：订单接口 5xx 率 > 5% |
| 14:05 | 值班确认，拉起应急群 |
| 14:12 | 定位到库存服务 RT 从 30ms 涨到 4s |
| 14:18 | 执行止血：熔断库存调用 + 降级返回 |
| 14:31 | 5xx 率恢复至 0.3% |
| 14:44 | 全量恢复，告警解除 |

## 二、影响面
- 受影响接口：下单、订单详情（依赖库存）
- 失败请求数：约 12.4 万次
- 用户影响：约 3.1 万用户下单失败，客诉 87 起
- 资损：无（未产生错误扣款）

## 三、根因（5 Why）
1. 为什么下单超时？→ 库存服务 RT 从 30ms 涨到 4s
2. 为什么库存服务变慢？→ 一条未加索引的 SQL 全表扫描（表已增长到 800 万行）
3. 为什么索引缺失？→ 该 SQL 是三个月前新增的，未做 EXPLAIN 评审
4. 为什么没评审？→ PR 模板里没有 SQL 检查项（只有代码规范）
5. 为什么没被发现？→ 库存服务的慢 SQL 阈值设为 2s，且无告警

## 四、止血与恢复
（记录实际执行的动作与耗时，用于评估应急能力）

## 五、改进项（必须有 owner + deadline）
| 改进项 | 类型 | Owner | Deadline | 状态 |
|---|---|---|---|---|
| 补索引 + 上线前 EXPLAIN | 技术 | @李四 | 10-19 | 完成 |
| PR 模板增加 SQL 检查项 | 流程 | @张三 | 10-25 | 进行中 |
| 慢 SQL 阈值降至 200ms 并告警 | 监控 | @王五 | 10-22 | 完成 |
| 库存服务加熔断（RT 阈值 300ms） | 技术 | @李四 | 10-20 | 完成 |
| 生产库全表扫描巡检（每周） | 流程 | @DBA | 11-01 | 待开始 |

## 六、做得好的 / 需要改进的
- 好：告警在 3 分钟内触发；熔断降级预案有效（虽未提前配置，但代码里已有兜底）
- 改：定位耗时 10 分钟（缺少"按接口维度的 RT 指标"）；止血靠人工判断，无自动化
```

### 5.2 复盘的三个质量标准

| 标准 | 说明 |
|---|---|
| **时间线可验证** | 每个时间点有日志/告警/操作记录支撑，不是回忆 |
| **根因到"系统性"** | 不能停在"某同学忘了"，要问"为什么流程允许他忘" |
| **改进项可验收** | 有 owner、有 deadline、有验收标准，且下次故障前完成 |

> **"人为失误"不是根因，是症状**。真正的问题是"系统允许这个失误造成这么大的影响"。

## 6. 从"会用"到"能决策"的成长路径

```
阶段1：会用（0–2 年）
  特征：能按文档配置，能解决问题，但不知道为什么这样配
  训练：把本文的 19 篇当成手册，遇到问题按 SOP 走一遍

阶段2：会调（2–4 年）
  特征：能根据压测数据调参数，能定位性能瓶颈
  训练：每解决一个线上问题，写下"根因 + 为什么之前的配置没防住"

阶段3：会选（4–6 年）
  特征：能对比方案，能说清代价，能预判失效
  训练：为每个技术决策写 ADR；参与别人的评审并挑战"为什么不是另一个"

阶段4：会设计（6 年+）
  特征：能在业务约束下设计可演进的架构，能定义"什么不做"
  训练：负责一次完整的架构演进（含拆分、迁移、灰度、回滚）
```

**加速的关键动作**（每个阶段都适用）：

| 动作 | 为什么有效 |
|---|---|
| 写 ADR | 强制你把"直觉"变成"可检验的论证" |
| 做故障复盘 | 真实故障是最好的老师，但必须挖到系统性根因 |
| 做容量规划 | 逼你把"感觉"变成"数字" |
| 参与架构评审 | 看别人怎么权衡，比看十本书有用 |
| 读源码（关键路径） | 排障时不至于"只知道现象" |

### B. 跑验证：决策是否可追溯，用命令检查

```bash
# 1) ADR 是否就位（决策有没有留下物证）
ls -1 docs/adr/

# 2) 每篇文档是否都回答了三问（缺哪一篇）
python tools/check_docs.py

# 3) 代码里是否声明了它服务哪一讲（反向可追溯）
python tools/gen_code_map.py --check
```

第 3 条命令的输出最有意思：它会列出**没有声明文档归属的类**。
这份清单本身就是一次"决策可追溯性"的体检 ——
一个类如果说不清它为什么存在，通常意味着当时的决策没有被记录下来。

### C. 看结果

| 主张 | 可验证的物证 | 现状 |
|---|---|---|
| 决策要记录当时的约束 | `docs/adr/` | **1 篇**（ADR-001），其余待补 |
| 结论要能被证伪 | `docs/fault/evidence/`（10 组，含"已知局限"） | 已就位 |
| 文档不能指向空气 | `tools/check_docs.py`（317 处路径引用） | 已就位 |
| 代码要能反查到设计 | `tools/gen_code_map.py`（145 个类，95 个声明归属） | 已就位，47 个待补 |
| 事故要能复盘到系统性根因 | 12 篇讲次文档的 §1 场景 | 每篇 3–4 个真实场景 |

### D. 一句话结论

架构思维的落地标志不是"能画出架构图"，而是**三年后有人问「当初为什么这么定」时，
仓库里有东西可查**：一份一页纸的 ADR、一条能跑的验证命令、一组带局限说明的证据。
本案例把这三样东西都放进了同一个仓库，并且用脚本保证它们不会安静地失效 ——
这才是"把方法论变成工程资产"的具体含义。

## 8. 结语

技术会过时：Java 8 到 21 用了九年，Spring Boot 2 到 3 用了四年，Redis 的主从到 Cluster 换了架构。**但"在约束下做可解释的决策"这件事，不会过时。**

这份材料的每一篇都在做同一件事：把一个"看起来是配置问题"的现象，还原成"一个需要判断的工程问题"。当你能独立完成这个还原，你就不再是"会用某个框架的人"，而是"能为系统负责的人"。

**下一步建议**：

1. 选一篇你最有感触的，结合你手上的系统，做一次真实的检查（用文末的检查表）；
2. 为一个你正在纠结的技术决策写一份 ADR（一页纸即可）；
3. 把最近一次故障按第 5 节的模板复盘一遍，挖到系统性根因。
