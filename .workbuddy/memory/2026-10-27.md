## 本轮修掉的 8 个真实缺陷（全部是"只在真跑时才暴露"）

1. **`@MapperScan("com.polaris.trade")` 误伤契约接口**
   `InventoryClient` 被注册成 MyBatis Mapper，报
   `Invalid bound statement (not found): ...InventoryClient.priceOf`。
   修法：`annotationClass = Mapper.class` 只认显式标注的接口。
   **错误信息说"找不到 SQL"，真实原因是"这个接口不该是 Mapper"** —— 极具误导性。

2. **`ResultWrapAdvice` 包装 String 返回值导致 ClassCastException**
   转换器按**控制器声明返回类型**选，`String` → `StringHttpMessageConverter` → `(String) body` 强转失败。
   而且异常先被 Spring Security 的 `ExceptionTranslationFilter` 捕获重抛，堆栈全是安全帧，看着像鉴权问题。
   修法：`beforeBodyWrite` 里对 `String` 手动 `objectMapper.writeValueAsString(Result.ok(text))`。

3. **`/error` 端点也被包装** —— 掩盖原始异常，只留一条 ClassCastException。已排除。

4. **状态机缺 `CREATED → PAID`** —— 渠道同步受理成功时状态是一步到位的，
   初版只允许 `CREATED → PAYING → PAID`，导致"下单后立刻支付"100% 失败。已补，并加回归测试。

5. **补偿任务只看 PAYING** —— 漏掉"支付成功但 `onPaid` 回滚、订单停在 CREATED"这一类，
   会走到"钱收了、单关了、库存退了"。新增 `confirmBeforeClose()` 扫 25~30 分钟窗口。
   **已用真实脏数据验证**：订单 CREATED + 支付单 SUCCESS，任务在 2 分钟内自动推进到 PAID。

6. **`rocketmq.producer.group` 缺失** —— `RocketMQTemplate` 的自动配置条件是
   `name-server` **和** `producer.group` 同时存在，只配前者时启动报"未找到 RocketMQTemplate"，
   错误信息完全没提 producer.group。

7. **RocketMQ broker 三连坑**
   - named volume 属主是 root，镜像默认 `USER rocketmq` → `/home/rocketmq/store/lock (Permission denied)`，
     然后 shutdown 阶段抛几个无关 NPE 把真正的第一条 ERROR 埋掉 → compose 加 `user: root`
   - `brokerIP1` 配容器名 → 宿主机 `UnknownHostException`；不配 → 注册成容器内网 IP，宿主机连不上
   - 最终方案：`listenPort=18911` + `brokerIP1=127.0.0.1` + compose 映射 `18911:18911`（**内外同号**）

8. **JVM 参数里的中文绝对路径** —— 仓库路径含"专题"，
   Windows 上 JVM 用 `sun.jnu.encoding`(GBK) 解析命令行，`-Xlog:...:file=D:\aafpc\Java专题\...`
   乱码成非法路径，JVM **在日志系统初始化阶段**就退出（此时 `-Dfile.encoding` 还没生效，救不回来）。
   修法：`run-monolith.sh` 先 `cd ROOT`，所有路径参数改相对路径。

## 环境坑（非代码，但会浪费大量时间）

- **Docker Desktop 必须由用户手动启动**：其后端依赖 `wsl.exe`，被本机沙箱安全策略拦截，不可绕过。
  启动后 `docker start polaris-mysql polaris-redis` 即可恢复。
- **`SERVER__PORT=62861` 环境变量污染**（父进程注入）：Spring Boot 宽松绑定把它当 `server.port`，
  **优先级高于 application.yml**，于是 yml 里的 18080 被静默覆盖，表现为
  `Port 62861 was already in use`（62861 其实是宿主上另一个进程的端口，必然撞车）。
  `env | grep SERVER_PORT` 查不到（名字是双下划线）。
  修法：`run-monolith.sh` 里 `env -u SERVER__PORT -u SERVER_PORT` + `--server.port` 显式传。

### 实测结论（已落证据）

| 场景 | 结果 |
|---|---|
| 超卖 NAIVE | 200 并发全部"成功"，卖 200 件只有 100 件货，**超卖 100 件**，账目差 -196 |
| 超卖 LOCKED | 成功 46、**失败 154（等锁超时）**，超卖 0，吞吐 12.9/s |
| 超卖 ATOMIC | 成功 100（正好卖光），超卖 0，吞吐 93.4/s → **比加锁快 7.2 倍** |
| 缓存命中 | 200 请求 → 库回源 1 次 |
| 击穿 | 200 并发同一 key → 库回源 **1 次**，单飞合并 **199 次** |
| 雪崩 | 200 key 同时失效 + 4000 请求 → 回源 190（≈key 数） |
| 穿透 | 4000 请求 → 189 次回源 vs 无缓存 **3573 次**（18.9 倍） |

### 这一轮踩到的坑（都是真问题，已写进代码注释）

1. **`Com_select` 做判据不可用**：全局计数器，订单补偿任务每分钟一批 SELECT，
   撞上测量窗口能贡献 10 次；而"击穿收敛成 1 次"的答案就是 1，同量级，扣完只剩 0。
   换成 `performance_schema` 按 SQL 指纹计数（`DIGEST_TEXT LIKE 'SELECT%t_stock%'`），本底恒为 0。
   **但并发下 digest 会少记约 6%**（串行 200 精确记 200，50 并发只记 187）——
   统计先在各 DB 线程本地缓冲再合并。所有数字只能当下限看。
2. **`urllib` 每次新建 TCP 连接**：4000 请求 = 4000 次握手，Windows 上直接
   `WinError 10053/10054`，4000 个只成功 18 个，看起来像"服务端扛不住"。
   改 `http.client` 每线程 keep-alive 长连接后 4000/4000。
3. **Barrier 参与数必须等于真正启动的线程数**：第一版按 key 分组再分发，
   `key-span=1` 时 200 个请求全进了 0 号线程，另 199 个线程拿到空列表被过滤，
   barrier 仍按 200 建 → 死等到 join 超时（120s）、成功率 0。
4. **`${AVA_BASE}${i}` 是字符串拼接不是加法**：得到 `stock:910001`，
   删的根本不是目标 key，"失效"这一步静默失败，测出来的是冷启动而不是雪崩。
5. **L1 本地缓存掩盖击穿**：`redis-cli DEL` 只删 Redis，删不掉进程内 Caffeine。
   击穿场景必须用一个从未读过的 SKU，否则 200 个请求全命中 L1，看着像"单飞没用"。
6. **回源太快时击穿不会发生**：本机主键查询 1ms，第一个请求早把缓存填好，
   单飞只合并到 13 次。加 `simulateLoadMs=50` 才看得到 199 次合并 ——
   **"要不要上单飞"的第一步是先量回源耗时**。
7. **`--hotkeys` 需要 LFU**：`allkeys-lru` 下直接报错；`lfu-log-factor` 默认 10 会把计数
   压成 5~6 一档，热 key 全糊在一起 → 改 `allkeys-lfu` + `lfu-log-factor 0`。
   但**多轮压测会把 freq 打满到 255**，第二轮就分不出来了 → 压测前必须清 key
   （`redis_dist.py --clean`，SCAN + 批量 DEL，不用 KEYS）。
8. **shell 里中文引号**：字符串里写 `"..."` 会截断，heredoc 里的 Python 更糟
   （无法被 py_compile 检查，跑完才发现）。统一用「」，摘要渲染一律拆成独立 .py。
